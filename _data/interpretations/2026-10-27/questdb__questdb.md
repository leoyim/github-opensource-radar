## 1. 它解决什么问题

时序数据的特点是写多、按时间范围聚合、需保留多年历史。通用关系库在高频写入与范围扫描上要么写不动，要么查询慢；专用 TSDB 又常把数据锁在私有格式里。QuestDB 用零 GC 的 Java 内核配合 C++/Rust 热点路径，做列式时间分区存储，并支持 Parquet/Iceberg/Arrow 开放格式。

## 2. 为什么是现在

17,477 星、今日 +3。README 主打「每秒数百万事件写入、毫秒级实时计算、多年历史仍可查」，并把分层存储与开放格式放在显眼位置——这回应了时序场景最常见的两个顾虑：写入吞吐与数据锁定。

## 3. 关键能力

- 高吞吐写入：README 称每秒可摄取数百万事件
- 单一 SQL 引擎覆盖写入、流处理与分层存储
- 列式时间分区 + 并行 WAL，查询走多核 SIMD 与 JIT 过滤
- 开放格式：原生 Parquet 分区、Apache Iceberg 与 Arrow 互通
- 数据路径无第三方依赖
- 丰富的客户端与第三方工具集成（README 单列）

## 4. 架构与实现

零 GC Java 内核，热路径用 C++/Rust 实现；数据以内存映射的列式分区落盘；WAL 并行写入，冷分区可转 Parquet（开源版用 ALTER TABLE，企业版自动分层到对象存储）。这种「写入与查询分离设计、格式开放」的组合是其性能与可迁移性的来源。

## 5. 上手路径

1. 先用 Docker 起单机，按时间分区建表并灌入真实速率的数据
2. 用实际聚合查询（降采样、窗口函数）对比现有方案，别只看写入吞吐
3. 需要长期留存时规划 Parquet 转换与对象存储分层

## 6. 风险与边界

- 通用事务型与分析型混合负载不适合，SQL 方言也有别于 PG
- 企业版功能（自动分层）在开源版需手工操作，运维成本不同
- 内存映射依赖页缓存，容量规划不当会放大延迟

## 7. 谁该用 / 谁别碰

行情、IoT、监控指标这类写多读聚合的场景；需要强事务与复杂 join 的业务系统应继续用 PG/分布式 SQL。
