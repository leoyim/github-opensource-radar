## 1. 它解决什么问题

Redis 在 2024 年从 BSD 切换到 source-available 许可，直接冲击把它当基础设施用的商业产品：云厂商不能再自由分发，企业内部对法务风险敏感的项目开始寻找替代。但替换缓存的成本极高——客户端、命令语义、持久化格式、集群协议全都是耦合点。

## 2. 为什么是现在

今日 +13 星，951 天的项目。数据类连续走弱，它作为「许可证安全」的代表仍保有稳定基数。回榜更多是惯性而非事件：Valkey 已成为 Linux 基金会项目，被主流云厂商采纳，这类基础设施项目的热度曲线本就平缓。

## 3. 关键能力

- 从 Redis 分叉，保持原有命令语义与客户端兼容，迁移成本主要是替换二进制
- 高性能数据结构服务器，面向缓存与实时负载
- 保留原生数据结构全集，并提供插件机制扩展新结构与访问模式
- BSD-3-Clause，商业使用与再分发无附加限制
- 官方提供性能对比看板与不稳定分支的持续性能追踪

## 4. 架构与实现

单线程事件循环 + 可选多线程 IO 的经典 Redis 架构（分叉时继承），fork 策略使其能在保持协议兼容的前提下独立演进。插件系统是它与原版差异化的主要方向，允许在不改内核的情况下加数据结构。

## 5. 上手路径

1. 替换前先比对你用到的命令与模块（RediSearch、RedisJSON 等）在 Valkey 侧是否有对应实现——模块生态是最容易踩空的地方
2. 用只读副本做一次真实流量回放，确认延迟分布而非平均值
3. 持久化格式兼容不等于可以随意回滚，升级前留好 RDB/AOF 备份
4. 客户端一般无需改动，但要确认客户端对 HELLO/版本协商的处理

## 6. 风险与边界

- 模块生态不如原版丰富，依赖 Redi* 模块的架构迁移成本高
- 两套实现长期分叉后，新特性会出现不兼容
- 许可证优势只对「再分发」场景有意义，自用场景收益有限
- 运维工具链（监控、备份、云托管）的成熟度需按你的栈验证

## 7. 谁该用 / 谁别碰

在意许可证风险、需要再分发或嵌入 Redis 兼容存储的商业产品；纯自用缓存且不涉及分发的场景，迁移收益需单独论证。
