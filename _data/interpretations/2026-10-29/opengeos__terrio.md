## 1. 它解决什么问题

GIS 生态被 GDAL 及其 C 依赖深度绑定：编译要一堆系统库、跨平台构建困难、想在浏览器里处理地理数据几乎不可能。而 GDAL 本身是几十年积累的庞然大物，没有替代品，只能忍受。对于只需要「读写、转换、重投影」这三件事的场景，为一个 C 依赖链付出全部代价并不划算。

## 2. 为什么是现在

15 天 208 星，本期以快照差值估算热度。它出现的位置和 soundcraft、openidea 一致：用内存安全语言重做被 C/C++ 绑定的重资产工具。地理数据上 Web 是明确增量场景——浏览器里做地图预处理、离线 GIS 工具，此前基本无路可走。

## 3. 关键能力

- 纯 Rust 实现，读写、转换、重投影地理空间栅格与矢量数据，另含点云
- 无 C 依赖，Rust 能编译的目标都能编，包括 WebAssembly
- 目标是覆盖主流 GIS 格式，README 说明转换链路已可用
- 以 GDAL、PROJ、PDAL 为参照系，并以 GDAL 作为测试对标
- README 明确标注早期：读写与转换可用，处理类操作仍在开发（见 ROADMAP）
- MIT 许可

## 4. 架构与实现

按数据模型分层：栅格、矢量、点云各自有独立的读写适配器，重投影层对标 PROJ 的坐标系统能力。全部纯 Rust 的取舍是牺牲格式覆盖广度（GDAL 有数百种驱动）换取零依赖与 WASM 可编译性。当前阶段是「格式 IO 完备、算子不全」。

## 5. 上手路径

1. 先只在「格式转换 + 重投影」这类你已知输入输出的场景试用，别指望它替代 GDAL 全流程
2. 拿 GDAL 对同一份数据做交叉验证，README 说它自己也这么测
3. WASM 目标先做小数据量验证，内存模型与流式读取的边界需实测
4. 处理算子按 ROADMAP 分批接入，不要按 GDAL 的习惯假设某个算子存在

## 6. 风险与边界

- 明确的早期项目，算子不全，生产使用风险高
- 格式覆盖远不及 GDAL，冷门格式大概率不支持
- 重投影精度与 EPSG 数据集完整性需自行验证，坐标错误在地理场景代价极高
- 15 天 208 星，API 会变

## 7. 谁该用 / 谁别碰

想把 GIS 能力放进浏览器、WASM 或受限环境，且只需格式 IO 与重投影的开发者；需要完整 GIS 分析能力的仍应留在 GDAL。
