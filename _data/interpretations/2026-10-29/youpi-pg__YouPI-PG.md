## 1. 它解决什么问题

印度的小商户收款有三重成本：支付网关按笔抽成、T+1 结算占用现金流、以及「钱到底到没到」需要人工对账。UPI 本身是即时到账的，抽成来自中间的网关层。理论上商户可以直接收 UPI 转账，但那样就失去了自动确认订单的能力——客户说付了、银行说没到，纠纷无解。

## 2. 为什么是现在

今日 +40 星、40 天 2,689 星。本地支付去中介化是个长期主题，但真正把它做成可用产品的不多。这个项目的解法（读银行短信做对账）之所以可行，依赖印度银行业普遍发送交易短信与 Gmail 通知这两个本地事实——这也意味着它几乎无法移植到其他市场。

## 3. 关键能力

- 零平台手续费，货款直连商户银行账户结算，不经中间账户
- 通用 JavaScript 结账集成，任意前端框架可接
- 动态二维码收款，适配线下与远程两种场景
- WhatsApp 预结账 OTP 验证，降低无效下单
- 银行观察者：读取安卓 SMS 与 Gmail 的银行通知，自动判定到账并核销订单
- 并发控制：同一 VPA 同时只允许一个客户付款，其余进入数据库支撑的 FIFO 队列并实时推送排队位置，以减少到账匹配的歧义

## 4. 架构与实现

典型的自托管单体 + 外部观察者模式：核心是订单与队列服务（数据库支撑 FIFO），对账靠旁路的 SMS/Gmail 观察者进程把银行通知转成支付事件。二维码与 OTP 是入口层。README 给出 Port Topology 与 Banking Observers 两节，说明它把部署拓扑与观察者配置当成一等文档。仓库无 LICENSE，采用前必须确认授权。

## 5. 上手路径

1. 先确认你的银行是否稳定发送交易短信与邮件，这是整个对账链路的前提；不稳定则不可用
2. 用测试账户跑通「下单 → 扫码 → 到账 → 自动核销」全链路，重点看重复通知会不会导致重复核销
3. 把 FIFO 队列的等待体验接入前端，否则并发时客户会以为付款失败而重复支付
4. 上线前明确争议处理流程：自动核对失败时的人工兜底是谁

## 6. 风险与边界

- 依赖短信与邮件解析做资金核对，抗干扰能力弱（运营商延迟、通知格式变更都会打断）
- 同一 VPA 串行收款降低并发上限，高峰期体验受限
- 无 LICENSE 文件，商用授权状态不明
- 自建支付链路涉及资金合规，需自行确认当地监管要求
- 仓库历经维护者变更（README 注明由 Zenuxs 接手），长期维护需评估

## 7. 谁该用 / 谁别碰

印度本地的小商户、社区团购、独立开发者接私域收款；其他地区没有 UPI 生态，基本无关。
