## 1. 它解决什么问题

需求文档最常见的失败不是写不出来，而是写的人觉得自己写清楚了。起草者带着满脑子的项目背景落笔，隐含假设一律省略；评审者要么是同一批人（共享同样的盲区），要么只看措辞。结果问题全部推迟到实现阶段才暴露，返工成本最高。EGM 把起草与审查在上下文上强制切开：Elephant 持有项目上下文起草规格，Goldfish 审查者只拿到草稿与被引用的源材料，看不到之前的对话，于是「你没写但我以为你写了」的部分被迫显形。

## 2. 为什么是现在

今日 +1,468 星，本期 AI 类第一、全榜最高日增，且来自 Google 内部（README 称数千工程师在用），属于「内部成熟工具外溢」而非新项目冷启。时间点也吻合：过去半年社区在讨论 agent 能不能写代码，现在开始有人把标准前移到「规格阶段能不能拦住错误」——同日的 learnharness 把同一思路用在教学，dashboard-design-skill 用在 UI 验收。

## 3. 关键能力

- 双角色上下文隔离：起草侧携带项目上下文，审查侧零上下文，仅看草稿与引用材料
- 以「暴露未言明的假设与盲区」为审查目标，而不是文风与格式
- 人在环上：架构权衡由人拍板、规格由人批准，之后才进入实现
- 适配多个宿主：README 的 Install 分节覆盖 Antigravity、Claude Code、Codex
- 文档分四块（Getting started / Setup / Architecture / Testing），并明确标注「验证能力的边界」
- Apache-2.0，可商用改造

## 4. 架构与实现

它是一个 skill/插件而非服务：没有后端、没有构建产物，运行方式是宿主 agent 读取技能定义后按流程产出规格草稿，再把草稿交给一个刻意剥离上下文的子 agent 做审查。仓库结构围绕「工作流与项目布局 / 安装与能力 / 技能与审查者如何组合 / 测试与验证边界」四节组织。具体审查提示词与判定标准未在 README 展开，需要读仓库内的 skill 定义文件。

## 5. 上手路径

1. 先装进一个你常用的宿主（Claude Code 或 Codex），用一个真实但不紧急的需求跑一遍完整流程
2. 重点观察 Goldfish 提出的问题里，有多少是你确实没写、而不是它理解错了——这个比例决定它对你团队的价值
3. 如果只有 20–30% 命中，说明你的规格习惯已经不错，收益主要在少数高风险需求上，不必全量推行
4. 把「审查者不得看到起草对话」这条规则抄进你自己的评审流程，它比这个插件更耐用

## 6. 风险与边界

- 双 agent 流程会让规格阶段变慢，短平快的小需求用它是净损失
- 零上下文审查者也会提出大量「材料里本来就有」的伪问题，需要人来过滤，过滤成本不低
- 绑定宿主插件机制，宿主改接口就要跟着改
- README 自述有「验证能力的边界」，不要假设它能替代人工架构评审

## 7. 谁该用 / 谁别碰

有 3 人以上协作、需求文档是正式交付物的团队，尤其是返工主要发生在「理解偏差」而非「技术难度」的项目。单人脚本、一次性工具不适用。
