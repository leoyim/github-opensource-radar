## 1. 它解决什么问题

Agent 生成的后台页面有一组高度可预测的坏习惯：每个 KPI 卡下面挂一句解释性文案、页面上摆一排「洞察」句子、图表配色随手取、空状态和加载态全部缺失、宽屏和手机两端只做一端。这些不是审美问题，而是「把数据屏当成文章写」的思维错位。而模型自己看不出这些——它读的是代码，不是渲染结果。

## 2. 为什么是现在

今日 +34 星、9 天 164 星，量级很小，但与昨日榜首 hallmark（反 AI 味落地页）构成清晰的配对：社区开始系统性沉淀「给 agent 的品味约束」，并且都选择用真实渲染结果做终审。这类项目当前星数普遍不高，但复用率高——一份 skill 会被反复装进不同项目。

## 3. 关键能力

- 覆盖完整的数据屏元件：KPI 卡、图表、热力图、子弹图、对比周期、排行榜、日期范围选择、筛选、空状态、宽屏与手机布局
- 「页面自己会说话」：取消 KPI 下的解释句与 insights 文案，说明一律收进 tooltip
- 监测式信息架构：总览 → 需要注意什么 → 细看 → 行动，问题标在数据本身上
- 感知参考层：编码阶梯、Few 的色彩规则、顺序/发散配色
- 每单活结尾强制截屏 QA，以屏幕呈现而非代码作为判定依据
- 从 127 个已上线看板蒸馏规则，可选输出 Web 或 SwiftUI

## 4. 架构与实现

纯 skill：没有运行时、没有依赖，靠宿主 agent 读取规范后生成页面，再用截图工具回读渲染结果做最后一轮检查。这个「生成 → 渲染 → 回读 → 修正」的闭环是它区别于普通 prompt 模板的关键，也意味着宿主必须具备截屏能力。

## 5. 上手路径

1. 先拿一个你现有的后台页做对照：让 agent 按规范重做同一页，只看截图差异，别看代码 diff
2. 把「截图 QA」这一步单独抽出来，接进你已有的页面验收流程——它比整套 skill 更容易落地
3. 团队内统一 tooltip 文案规则，否则「不写解释句」会变成「什么都不写」
4. SwiftUI 输出需单独验证，README 的规则主要面向 Web

## 6. 风险与边界

- 127 个看板的样本偏向 SaaS 分析型，重运营、重表格的后台未必适配
- 取消解释句对非专业读者不友好，面向高管的看板可能反而需要更多文字
- 依赖宿主截屏能力，纯 CLI agent 无法完成终审
- 9 天 164 星，规则集仍在演化

## 7. 谁该用 / 谁别碰

经常让 agent 生成后台或分析页、且有人能对成品做视觉判断的团队；纯 API 或纯库项目无关。
