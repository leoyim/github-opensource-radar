## 1. 它解决什么问题

text-to-SQL 的 demo 与生产之间隔着一个无法回答的问题：它到底准不准，以及不准的时候该改哪里。多数方案把「模型 → SQL」当成黑盒，schema 检索策略、语义层、校验与拒绝逻辑全部写死在代码里。业务方问「为什么这条查错了」，工程师只能重跑一遍再猜。而没有可测量的中间环节，就无法做回归测试。

## 2. 为什么是现在

107 天 111 星，本期以快照差值估算热度（无 trending 增量）。所处赛道正在升温：同期 pgbot 提供机器可读的库健康报告、dbt-charts 提供 agent 可写的看板定义，三者拼起来是「agent 直接面对数据」的完整链路。text-to-SQL 的竞争点已从「能不能生成」转向「能不能被测量」。

## 3. 关键能力

- 可替换的生成模型：托管或本地、单候选或多候选，均由配置决定
- 可调的 schema 上下文：检索多少、如何排序，是可读参数而非黑盒
- 可配置的语义增强：增强到什么程度、是否需人工认证
- 分级拒绝策略：校验器与其阈值可调，控制系统在不确定时拒绝回答的激进程度
- 每一段都是设置，因而每个阶段都可单独测量——这是它区别于其他 text-to-SQL 的核心
- 支持 DuckDB、Databricks 等后端（README 标签所示），Apache-2.0

## 4. 架构与实现

流水线式架构：问题 → schema 检索 → 语义增强 → SQL 生成（单/多候选）→ 校验器 → 拒绝或返回。每一段都有独立的配置项与可观测输出，因此可以逐段做消融实验。这种「可拆解」设计是它把 text-to-SQL 从 demo 推向可运维系统的关键。

## 5. 上手路径

1. 先准备一份带标准答案的问题集（50–100 条真实业务问题即可），这是所有调优的前提
2. 固定其他参数，逐段做消融：先只改 schema 检索量，看准确率曲线，再改语义增强
3. 拒绝阈值宁严勿宽：错答的业务代价通常远高于拒答
4. 多候选模式先测成本，token 消耗随候选数线性上升

## 6. 风险与边界

- 111 星、3 个月，早期产品，接口与文档仍在变化
