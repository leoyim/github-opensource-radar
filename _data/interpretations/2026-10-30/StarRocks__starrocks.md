## 1. 它解决什么问题

传统方案要在「把数据搬进数仓」与「直接在湖上查」之间取舍：前者快但管道重、数据冗余，后者省但查询慢。StarRocks 用向量化执行、CBO 与物化视图，在不搬数据的前提下做亚秒级多维分析，并用主键模型支持实时更新。

## 3. 关键能力

- 原生向量化 SQL 引擎，充分利用 CPU 并行
- ANSI SQL 兼容，支持 TPC-H / TPC-DS，兼容 MySQL 协议
- CBO 成本优化器
- 主键模型支持 upsert/delete 与并发更新
- 物化视图随导入自动刷新并透明改写查询
- 直接查询 Hive、Iceberg、Delta Lake、Hudi，无需搬迁
- 资源组隔离与多租户
- FE/BE 分离的 MPP 架构，易扩容

## 4. 架构与实现

FE（Java）负责元数据、查询解析与规划，BE（C++）负责存储与执行，二者分离可独立扩容。存储为列式，配前缀索引与 bitmap 索引；查询经 CBO 生成计划后在 BE 上向量化执行；物化视图的透明改写发生在 FE 的规划阶段。

## 5. 上手路径

1. 用 docker compose 起最小 FE/BE 集群，先跑通一条查询再谈性能
2. 拿你自家最慢的三条 SQL 做基准，官方「3 倍」的宣传不可直接采信
3. 主键模型与明细模型的选择只看一件事：是否存在更新需求
4. 物化视图先做高频聚合，滥建会拖慢导入并占用大量存储

## 6. 风险与边界

- 运维需理解 FE/BE 角色划分与内存配置，配错会导致查询 OOM
- 小数据量场景属过度设计，运维成本高于收益
- 湖上查询性能受远端存储与网络制约，冷数据仍会慢
- 跨大版本升级存在兼容坑，需按官方路径逐版升级

## 7. 谁该用 / 谁别碰

有实时分析需求、数据已在湖上的中大型团队。数据量在千万行以下的项目不必考虑。
