## 1. 它解决什么问题

关系型数据库在「朋友的朋友的朋友」这类多跳查询上要反复 join，深度一上去执行计划就退化。图数据库把关系存成一等公民，遍历成本与深度近似线性，因此在风控、推荐、知识图谱这类场景有明显优势。但它也把「怎么建模」的责任完全交给了你。

## 2. 为什么是现在

今日 +8 星，项目 5100 天，本体项目。它与 StarRocks、OpenSearch 同日出现，说明当日 data 类由存量项目撑场。另一个值得注意的点：过去「图数据库作为 agent 记忆底座」是被反复提及的叙事，而本期 AI 类第一的 hindsight 明确宣称要绕开知识图谱的局限——记忆层正在与图库解耦。

## 3. 关键能力

- 属性图模型（节点、关系、属性）
- Cypher 声明式查询语言
- ACID 事务
- 索引与唯一性约束
- 因果一致性集群
- APOC 与 GDS 图算法生态

## 4. 架构与实现

JVM 实现，页缓存加事务日志；存储层按节点、关系、属性分文件组织，关系以双向链表挂在节点上，因此遍历无需索引查找。Cypher 编译为执行计划后由运行时算子执行。集群采用因果一致性模型，读己之写但不保证全局线性一致。

## 5. 上手路径

1. 先用 docker 起单机，导入一份你真实的关系数据，别用玩具数据评估
2. 用 EXPLAIN / PROFILE 看多跳查询的执行计划，确认它真的避免了你原本的 join 爆炸
3. 建模先画关系类型与方向，别直接照搬关系型的 ER 图——这是最常见的失败起点
4. 大写入量注意事务粒度，单事务过大比 SQL 更容易拖垮内存

## 6. 风险与边界

- 非关系型场景性能不及列存或文档库，用错场景代价很高
- 运维与调优门槛高，JVM 堆与页缓存配置需要经验
- GPL-3.0 对分发有约束，商业嵌入需评估
- 图建模一旦错了，数据迁移成本远高于关系型改表

## 7. 谁该用 / 谁别碰

有明确多跳关系查询需求（风控、推荐、知识图谱）的团队。只是「有点关联数据」的场景不需要图库。
