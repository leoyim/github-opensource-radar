> **一句话**：终端里的 AI 不该直接执行命令，而该先给你一张带风险等级的卡片。

## 1. 它解决什么问题

远程终端工具长期是割裂的：SSH 一个客户端、SFTP 一个、串口一个、RDP 一个，排障时要在多个窗口间跳。而把 AI 塞进终端后，最大的风险变成「模型直接执行了危险命令」，且往往无感知。nyaterm 同时解决这两个问题：多协议收进一个原生客户端，AI 输出必须先变成结构化命令卡并获批准。

## 2. 为什么是现在

今日 +169 星，项目 185 天。同期 coucou 让人在手机端批准 agent 权限、OpenMausBot 给 bot 一台隔离虚拟机、shannon 只认可复现的 PoC——「给 agent 的手脚加闸门」是本期跨类别最一致的主题，nyaterm 是终端这个场景下的答案。

## 3. 关键能力

- 统一会话：SSH、本地 shell、Telnet、串口、RDP、VNC、SFTP、隧道、OTP
- Ask 模式：生成命令、解释选中输出、分析报错
- Agent 模式：对活动会话执行「观察-决策-执行」循环
- 最近输出快捷操作，无需手动复制即可让 AI 解释
- 命令卡片含风险等级、执行控制与「存为快捷命令」
- Agent 流程中执行需批准，执行后单独出最终答复
- 用 @ 引用其他终端会话进入 AI 上下文
- 多 provider 管理，支持自定义 OpenAI 兼容端点

## 4. 架构与实现

Rust + GPUI 原生渲染（Zed 编辑器的 UI 框架），会话与连接管理在本地完成，不依赖服务端。AI 层做了 provider 抽象，Agent 循环对当前会话做有界观察（可配置输出行数），把生成的命令包装成卡片交由用户批准后执行。凭据经加密同步。

## 5. 上手路径

1. 先用 Ask 模式（只读）一周，观察它解释报错与生成命令的准确率，再考虑 Agent 模式
2. Agent 模式只在测试机开，风险阈值调到最严，观察它提出的命令是否合理
3. 用 @ 引用多台机器的会话做跨机排查，这是它相对单机客户端的实际增益
4. 生产机的密钥与凭据不要进入 AI 上下文，先确认它的上下文边界

## 6. 风险与边界

- 185 天的项目，多协议并行实现的边界情况多，串口与 RDP 尤其容易出问题
- 命令风险分级是规则判断，误判为「低风险」的命令仍可能造成破坏
- 加密同步的密钥管理由用户承担，配错等于明文同步
- GPUI 在 Windows 上的成熟度待验证，跨平台体验可能不一致

## 7. 谁该用 / 谁别碰

需要同时管理多台机器、又想用 AI 辅助排障的运维与后端工程师。只用 SSH 连一台机器的场景收益不大。
