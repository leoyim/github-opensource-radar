## 1. 它解决什么问题

各家编码 agent 都自称会「先规划再写码」，但规划的质量与产物形态完全不可控：有人产出几句话，有人产出长文档，团队无法统一，更无法把合规要求钉进流程。spec-kit 的做法是把流程做成 CLI 生成的仓库内产物——规格、计划、任务都是可评审的文件，而不是对话里的一段文字。

## 2. 为什么是现在

今日 +335 星。本期它完成了一次架构级重构：从早期几条斜杠命令（/specify、/plan、/tasks）升级为 specify-cli，加入 extension、preset、workflow、bundle、catalog 五层机制，并明确区分「SDD 核心」与「修 bug / 想法评估」两个可选扩展。这说明 GitHub 的意图已从「提供一套提示词」转向「提供组织级流程基础设施」。同日社区侧 superpowers 在做同类事，路线之争开始显形。

## 3. 关键能力

- SDD 主流程：规格 → 计划 → 任务 → 实现 → 收敛
- 修 bug 与想法评估作为可安装扩展，不是必经阶段
- extension：加命令、质量门、完整流程，并可挂生命周期钩子
- preset：改模板、命令、术语与方法论，用于承载组织或监管标准
- workflow + overlay：自动化提示、命令与门禁，且能覆盖已装流程而不 fork
- bundle：把扩展、预设、工作流打成一个可分享的团队 setup
- catalog：社区与私有组件目录，支持鉴权与内网离线安装
- 集成层覆盖主流编码 agent，命令语法由集成决定

## 4. 架构与实现

specify-cli（Python 3.11+，经 uv 安装）在项目内生成 .specify 目录与各宿主 agent 的集成文件；命令由集成层暴露，扩展与预设按键值分层覆盖，项目级 override 可临时改单个模板。产物全部是仓库内的文本文件，因此可以直接进 code review 与审计流程。

## 5. 上手路径

1. 先在一个已有项目上跑 specify init，重点看它如何处理存量代码（README 有 existing-projects 指南）
2. 先用核心 SDD 流程，别一上来堆扩展——扩展是给已经跑通流程的人用的
3. 把团队的合规检查写成 preset（例如计划必须含可追溯性字段），而不是散落在提示词里
4. 引入社区组件前先审代码：README 明确写了目录列表不等于审计或背书

## 6. 风险与边界

- 对小需求是过重流程，规格文档的维护成本可能超过收益
- 扩展生态处于早期，质量参差，且会随 CLI 版本变化
- 生成物进仓库后会产生大量模板噪音，需要约定哪些文件纳入版本控制
- 多宿主集成意味着行为依赖宿主版本，升级需按 pin 的版本走

## 7. 谁该用 / 谁别碰

需要把开发流程标准化、留痕、并接受审计的团队，尤其受监管行业。个人项目用它收益有限。
