## 1. 它解决什么问题

直接用 JDBC 写持久层，复杂查询与结果映射冗长，内存对象与数据库状态的一致、事务边界、时态数据与审计、多租户与行级安全都要自己实现；过早优化又常常把基础逻辑写坏。

## 2. 为什么是现在

本期 6,488 星、3,838 fork、208 个 open issue，5,888 天的项目仍以 velocity 口径入榜；README 特别强调「允许在基础持久化逻辑写完之后再做性能优化」，在当下大量数据框架把 agent 写进定位的对照里，这种先正确性后优化的次序反而更清晰。

## 3. 关键能力

- 把关系数据暴露为自然且类型安全的形式，复杂查询与结果处理更直接
- 内存改动与数据库同步，遵守事务 ACID 属性
- 自动处理时态数据与审计日志，支持多租户与行级安全
- 保留 SQL 的表达力与代码复用，允许在基础逻辑完成后再做性能调优
- 作为 Jakarta Persistence 生态核心实现，配套 Envers 等模块

## 4. 架构与实现

位于 JDBC 之上的 ORM 层：实体映射与会话管理负责把对象状态变更翻译为 SQL 并在事务边界内同步，查询层提供类型安全的条件构造与结果映射。缓存、延迟加载与批量策略作为后置的优化旋钮，不侵入业务侧的基础持久化代码；审计与多租户等横切能力由框架内模块提供。

## 5. 上手路径

1. 在一个 Spring/Jakarta 项目里引入 Hibernate，先只做实体映射与一个带事务的保存操作
2. 打开 SQL 日志，核对生成的语句与事务边界是否符合预期
3. 再写一条较复杂的类型安全查询，观察结果映射与延迟加载行为
4. 最后才按需启用缓存、批量抓取与审计/多租户模块，并逐项压测

## 6. 风险与边界

- 抽象层会遮蔽 SQL，缺少 SQL 日志与执行计划检查时容易出现 N+1 等性能问题
- 5,888 天项目、208 个 open issue，版本迁移（javax → jakarta）与升级路径需仔细规划
- 多租户与行级安全属框架级能力，配置错误的影响面覆盖全部数据访问
- 自动时态与审计会带来额外写入与存储成本，需评估容量

## 7. 谁该用 / 谁别碰

以 Java 为主、需要长期维护复杂领域模型与事务一致性的企业应用团队；以简单读写或极致 SQL 控制为主的服务，ORM 的抽象成本可能高于收益。
