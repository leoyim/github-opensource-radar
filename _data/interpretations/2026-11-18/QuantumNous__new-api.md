## 1. 它解决什么问题

团队里每个客户端各自配置上游 key 与 base URL，一旦要换供应商、加模型或统计成本，就得逐台改配置；授权也不好共享，缺少统一的访问控制与用量视图。

## 2. 为什么是现在

本期 52,103 星、12,723 fork、1,479 个 open issue，1,103 天的成熟项目仍录得今日 +79；README 把「应用、agent 与团队」并列为目标用户，并把渠道、分组、计价、配额写成标准操作，反映多模型接入已从个人玩法变成需要治理的基础设施。

## 3. 关键能力

- 统一接入 OpenAI、Anthropic、Google Gemini、Azure OpenAI、AWS Bedrock、Vertex AI、DeepSeek、Qwen 及其他兼容服务
- 控制台内添加渠道（上游 key、可用模型、分组）并运行渠道测试，验证连通性
- 模型路由与访问控制：按分组签发网关 API key，客户端只看到本网关的 /v1 端点
- 模型计价、配额与订阅管理，配合用量记录做成本归集
- 提供 Web 控制台，可用于团队共享授权模型访问或运营私有多模型服务

## 4. 架构与实现

位于客户端与上游供应商之间的自托管网关：控制台维护渠道、模型、分组与计价配置；请求到达后按模型与分组做路由与鉴权，转发到对应上游的兼容 API，回传时记录用量并结算成本。客户端只需配置为 OpenAI 兼容的 base URL 与网关签发的 key，上游细节对客户端不可见。

## 5. 上手路径

1. 部署后在控制台添加一个渠道，填入上游 API key、可用模型与分组，先跑渠道测试
2. 为该模型配置计价，并确认目标用户有配额或有效订阅
3. 在控制台签发属于同一分组、可访问同名模型的 API key
4. 把客户端 base URL 指向 http://localhost:3000/v1，用一次简单对话验证整条链路

## 6. 风险与边界

- 网关处于所有请求链路中央，其可用性、鉴权与日志策略直接决定整体安全边界
- 1,479 个 open issue 说明功能面广、边界情况多，升级前需看 changelog 与回归说明
- 上游模型计价与能力变化频繁，计价配置若未同步会造成成本统计偏差
- 集中存放多家上游凭据，一旦泄露影响面覆盖全部接入供应商
- AGPL-3.0 许可，二次开发或对外提供服务前需评估合规义务

## 7. 谁该用 / 谁别碰

需要把模型访问统一治理起来的团队、平台工程与 agent 基础设施维护者；单人、单一供应商且用量很小的场景，引入网关的运维成本可能不划算。
