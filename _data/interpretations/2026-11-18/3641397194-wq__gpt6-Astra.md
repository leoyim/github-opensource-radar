## 1. 它解决什么问题

多模型客户端常见的问题是模型名与实际调用不一致：写死的名称、过期的列表、以及中转返回什么全凭猜测，用户看不到一次请求究竟路由到了哪里；桌面与手机端又往往各是一套配置。

## 2. 为什么是现在

本期 2,290 星、477 fork、17 个 open issue，92 天项目、无历史基线；README 把「读取服务商 → 模型精确 ID 再发送」和「真实路由可视化」作为主要卖点，并同时提供 Windows/macOS/Linux 桌面端与 Android/iOS 客户端，反映多模型接入正从单点工具走向跨端工作台。

## 3. 关键能力

- 桌面端提供十五个模型席位、技能安装与备份恢复、真实请求路由可视化与 DeepSeek Harness 插件
- 移动端：Android APK 与 iOS SwiftUI 客户端，支持自定义中转、读取模型、流式对话、六类移动研究工作台与会话记录
- 连接流程为填写自有 Key → 读取服务商模型目录 → 用目录返回的精确模型 ID 发送
- 支持自选兼容服务商，可用型号、额度与价格以所接中转为准
- 模型焦点区并列展示推荐型号，需要时可切换；请求保留目录返回的准确 ID

## 4. 架构与实现

跨端客户端 + 中转接入层：桌面工作台负责模型席位管理、技能安装、路由可视化与插件，移动端以 APK 与 SwiftUI 源码形态提供相同的「读目录—选模型—流式对话」链路。凭据由用户自行填写，实际可用模型与计价来自服务商目录，客户端不内置模型能力；品牌与中转服务为项目方自建，亦可替换为任意兼容端点。

## 5. 上手路径

1. 先只填自己的 Key 并读取服务商模型目录，确认返回的型号与 ID 与预期一致
2. 用目录里的精确 ID 发一条简单对话，在路由可视化里核对请求实际去向
3. 再按需在桌面端安装一个技能、在移动端导入同一份中转配置，验证两端行为一致
4. 若使用项目方的中转服务，先自行确认计价与额度口径

## 6. 风险与边界

- 3.3.0-preview.3 预览版，README 明确说明界面截图中的名称与列表不代表实时账号权益或付费模型生成已验证
- 可用型号完全取决于所接服务商目录，标注的型号名称与真实能力可能不一致，需以返回的精确 ID 为准
- 项目方中转涉及付费与账号数据，凭据与会话内容的外发范围需自行评估
