## 1. 它解决什么问题

做原型、做 demo、做数据看板时，第一道卡点往往是「去哪儿找一个不用付钱、不用申请企业账号的接口」。这件事本身没有技术难度，但信息极度分散：每个 API 的免费额度、鉴权方式、是否还在维护，都要一个个点开确认。这个仓库用一份人工维护的分类清单把这个检索成本压到最低，按 Animals、Anime、Blockchain、Books 等几十个领域索引，并标注 Auth 与 HTTPS/CORS 支持情况。

## 4. 架构与实现

没有任何运行时，本仓库就是「Markdown 表格 + 校验脚本」的形态：所有条目集中在 README 的分类表格中，靠 CI 检查链接可达性与格式规范，站点由这些表格渲染。价值全在维护与筛选，不在代码。这种结构的优点是零依赖、可直接 grep、可被任何脚本解析；代价是无法表达条目间的复杂关系，且历史失效条目依赖人工清理。

## 5. 上手路径

1. 别直接在浏览器里翻——把 README 拉下来按 CORS 与 Auth 两列过滤，能砍掉一半不适合前端的条目
2. 免费额度要自己核实：清单只标鉴权方式，不标调用上限，很多条目写着 free 但实际每月只有几十次
3. 给 agent 用时优先看 MCP Servers 一节，比让模型自己拼 HTTP 请求稳定得多
4. 把选定的 API 连同额度与条款抄进自己的文档，清单本身不是可靠的事实来源

## 6. 风险与边界

- 条目失效是常态，链接可达不代表接口可用，需要逐个实测
- 免费额度与条款随时变更，清单不跟踪这类变化
- 不同 API 的数据许可差异很大，商用前须逐条确认，尤其地图、金融与媒体类
- README 顶部为商业推广内容，不代表中立推荐
