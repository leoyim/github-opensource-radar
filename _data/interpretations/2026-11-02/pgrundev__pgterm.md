# pgrundev/pgterm · 项目解读

> **一句话**：所有 Postgres 库的 htop：一个静态二进制，在终端里同时盯多个实例并跑只读诊断。

## 1. 它解决什么问题

DBA 的日常监控被切成好几块：指标在云厂商控制台，慢查询在 pg_stat_statements 里，锁等待要连上去手查，索引膨胀得自己写脚本。想同时看生产、预发、分析三个库，就得开三个终端加两个网页。pgterm 的取舍是把这些压进一个 TUI：一个静态二进制，配置好连接后在同一个界面里并列显示多库状态，复用 pgbot 的只读诊断规则给出「需要关注」的结论，同时提供 SQL、数据浏览与分支视图。无 agent、无常驻 daemon、无 web 面板。

## 2. 为什么是现在

66 天、365 星，本轮 +1。它代表一类正在回归的偏好：在 Grafana 与云监控已经足够强的今天，仍有人需要「SSH 上去就能看」的工具——因为故障现场往往连不上外部监控，或者权限流程不允许装 agent。它的安全姿态也写得很明确：健康检查完全只读、连接串永不落盘、配置文件只存环境变量名。这类「零信任部署 + 终端优先」的工具在受监管环境里需求稳定，但注定不会爆量。

## 3. 关键能力

- 单静态二进制，同时监控多个 Postgres 实例，界面并列展示
- 复用 pgbot 的只读诊断规则，给出带置信度的发现（如零扫描索引、相对基线退化的查询、回滚率偏高）
- 五个标签：Overview（指标总览）、PgBot（诊断）、SQL、Data（数据浏览）、Branches（分支）
- 总览含连接数、活跃数、库大小、运行时长、缓存命中率、锁等待、回滚率、空闲索引等指标条
- 完全只读的健康检查，任何检查都不能写库
- 不存连接串，配置文件（~/.config/pgterm/config.toml）仅保存环境变量名
- 支持 SSH 跳板机后的数据库，适合同机、tmux、SSH 场景
- 支持粘贴完整 export 行或 postgres:// URL 快速添加

## 4. 架构与实现

TUI 前端 + 多连接采样器 + 诊断规则引擎三段。采样器对每个配置的库周期性执行只读查询，结果进内存做时间序列与基线比较；诊断层不自己实现规则，而是调用 pgbot 的既有逻辑，保证与另一套工具结论一致；渲染层按标签页组织，把「当前值 / 阈值 / 趋势」压成一行指标条。凭据从不进入进程持久化状态，只从环境变量解析——这让它可以安全地留在跳板机上，但也意味着首次配置略繁琐。

## 5. 上手路径

1. 先用 demo 模式（README 提供 10 秒无数据库试用）看界面是否符合你的排障习惯
2. 凭据全部走环境变量，配置文件里只写变量名，避免把密码写进 dotfile
3. 指标条先调阈值再看趋势：默认阈值未必匹配你的实例规格
4. 诊断结果的置信度要看，MEDIUM 的结论（如回滚率 12%）可能只是业务特性而非故障
5. 多实例同时采样会带来额外连接与查询开销，生产库注意采样频率

## 6. 风险与边界

- 66 天新项目，pgbot 规则覆盖面有限，冷门问题（复制延迟、autovacuum 阻塞）可能识别不到
- TUI 的界面表达力有限，复杂排障仍需开 SQL 手查
- 许可证为 NOASSERTION，商用需确认
- 只做观测不做处置，缺少「一键修复」也意味着所有动作要自己做，误操作风险在人不在工具
- 采样频率设高会与业务查询争抢资源

## 7. 谁该用 / 谁别碰

需要同时盯多套 Postgres 的 DBA、在跳板机/受限网络里排障的运维、以及偏好终端工作流的后端工程师。
