## 1. 它解决什么问题

AI 辅助写代码之后出现了一个新问题：代码是 agent 写的，人是「验收」的，于是没人真正知道系统怎么拼起来的。问「用户下单时发生了什么」「改这里会崩哪里」，得到的诚实回答是不知道。读代码补课的成本又极高。floorplan 的解法是让模型通读仓库，把每个模块、文件、网络请求都起一个plain-English 的名字，再把它们之间的连接画成可点击的地图——目标不是给架构师看的 UML，而是给「用 AI 造出了东西但没读完全部代码」的人看的一层解释。

## 2. 为什么是现在

仓库仅 6 天、1,808 星，单日 +854，是全榜增速最快的冷启动项目。它精确踩在一个新痛点上：vibe coding 产出的项目数量暴涨，但可维护性缺口同步放大，而现有工具（架构图生成、代码可视化）都假设读者能读懂代码。它同时提供 Claude Code 与 Codex 两条插件市场安装路径，把自己做成了「编码 agent 的附属能力」而非独立工具——这是当下获取新用户最短的路径。

## 3. 关键能力

- 模型通读代码库后生成可交互地图，模块、文件、网络请求均带自然语言命名
- 连接关系可视化，点击节点可下钻到具体文件
- 面向三类场景：自建应用的自我理解、团队快速 onboarding、以及查看每次 agent 改动影响了哪些部分
- 附带 blueprints：对尚未开始写的应用，先出结构草案
- 通过 Claude Code / Codex 的插件市场安装（Add marketplace → 输入仓库名）
- 提供 live demo 与视频，隐私策略单独成节

## 4. 架构与实现

本质是「一次性静态分析 + 模型归纳 + 前端渲染」的离线管线：模型先扫仓库结构与依赖关系，把技术符号翻译成业务语义，产出一份描述节点与边的中间产物（落在项目内），前端再把它渲染成可缩放、可点击的交互图。没有常驻服务，没有后端数据库，因此可完全本地运行。插件形态意味着它不锁定单一 agent，但两端的提示词与工具描述需要分别维护。

## 5. 上手路径

1. 先在前端后端分仓的项目上试：打开包含两者的父目录，跨仓调用关系才画得出来
2. 第一次跑完先核对三处高风险映射：认证入口、支付/写操作、外部 webhook
3. 地图是模型归纳的结果，不是静态分析的精确输出，关键路径仍需人工对照源码确认
4. 团队使用时把地图产物入库，每次 agent 大改后重跑并 diff，比只看新增文件有效
5. 注意隐私章节：仓库内容会进入模型上下文，私有仓库需确认所选供应商的数据策略

## 6. 风险与边界

- 语义命名由模型生成，可能出现「名字很顺但含义错」的映射，比缺图更危险
- 仅 6 天的新项目，接口与产物格式都可能变，不宜过早接入团队流程
- 大型仓库的上下文成本高，可能只覆盖部分模块而给出看似完整的图
- 与 Archify、Understand Anything 等同类工具功能重叠，README 自带对比但立场不免偏自身
