## 1. 它解决什么问题

看番的痛点是站点散、App 各自为政：一个季度的新番分散在十几个采集站，每个站有自己的目录结构和播放器，想统一追番就得在多个 App 之间来回切。Kazumi 的做法是把「站点」抽象成规则——最多五行 XPath 选择器就能描述一个番剧源的目录、详情与播放地址，于是「支持多少站点」变成了「有多少人写规则」，客户端本身不必随站点改版而发版。

## 2. 为什么是现在

40,612 星、今日 +203，是个 907 天的老项目，属于长期在线而非突然爆红；但今天它出现在移动类第一，说明规则的社区供给已经跑通（规则导入 + 规则分享 + 在线更新都已完成）。真正的信号是它把「超分辨率」和「一起看」也做了，这已经超出「聚合播放器」的范畴。

## 3. 关键能力

- 规则编辑器 + 规则导入/分享，最多五行 XPath 即可接入一个新番剧源
- 番剧目录、搜索、时间表、字幕、分集播放、多视频源切换
- 弹幕渲染、倍速、高刷适配、配色方案、硬件加速
- 基于 Anime4K 的实时超分辨率，可在线开启
- 追番列表、历史记录、番剧下载、跨设备同步
- DLNA 无线投屏与外部播放器接管
- 覆盖 Android 10+ / Windows 10+ / macOS 10.15+ / iOS 13+（侧载）/ HarmonyOS 5.0（分支仓库）/ Linux 与 Web（实验性，Web 需自建服务端或 Docker）

## 4. 架构与实现

单一 Flutter 代码库覆盖移动、桌面与 Web，Dart 编写，播放层自绘 UI 并走系统硬解，超分挂在 Anime4K 着色器管线上。规则的抓取与解析在客户端完成，因此没有中心服务端，也就不存在「官方源被关停即全线失效」的单点；规则以文件形式在社区流转，仓库只负责解析与渲染。Web 端是唯一例外，需要一台电脑或 Docker 跑服务端，局域网内设备用浏览器访问。

## 5. 上手路径

1. 先只装客户端、用现成规则跑通一部番，确认你所在网络的直连情况，再考虑写自己的规则
2. 自建规则时从「目录页 → 详情页 → 播放地址」三段拆，先用浏览器验证 XPath 再粘进编辑器，五行限制逼你先想清楚选择器
3. iOS 与 HarmonyOS 需要侧载，签名有效期有限，长期使用要准备重签流程
4. Web 端别暴露在公网，它设计为局域网自用，没有账号体系与鉴权

## 6. 风险与边界

- 内容全部来自第三方采集站，规则指向的源随时可能失效或改版，追番体验取决于社区维护速度
- 番剧本身多为未经授权传播，规则分享事实上在扩散侵权入口，GPL-3.0 也挡不住内容层面的风险
- 侧载版本（iOS / HarmonyOS）依赖自签名，证书吊销后需重新打包
- 超分与硬解在高刷屏上耗电明显，长时间播放对移动设备不友好

## 7. 谁该用 / 谁别碰

跨多设备追番、愿意自己维护规则的极客用户；以及想在电视/投屏上统一入口的家庭用户。只想「装了就能看」的人不适合，规则失效时需要自己动手。
