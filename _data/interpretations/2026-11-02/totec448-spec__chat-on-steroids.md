## 1. 它解决什么问题

网页版 ChatGPT 只能对着聊天框说话，它看不到你的仓库、跑不了测试、留不住终端会话，长任务一旦上下文压缩就前功尽弃。这个项目的定位是把「本地执行能力」通过 MCP 接进 ChatGPT：让模型在真实项目里读文件、改代码、跑测试，而不只是给建议。

## 2. 为什么是现在

5,124 星、71 天新仓，今日净增 0——热度来自存量而非当日爆发，属于「被看到过、但今天没人再传」的阶段。它的价值点在于两条路径同时做了：MCP 走标准协议接本地工具，浏览器扩展则直接观察并操作 ChatGPT 网页 UI，绕开了官方尚未开放的接口。

## 3. 关键能力

- 通过 MCP 把本地能力（读写文件、跑测试、常驻终端、桌面操作）暴露给 ChatGPT
- Chrome / Edge / Brave 扩展，观察并自动化 ChatGPT 网页界面
- Workers：把独立任务拆给多个 worker，各自保留上下文，结果回收后接着干
- Goal 跟随未完成工作、Loop 在给定范围内循环，长任务可中途下达修正
- Compact & Resume 把会话与 worker 历史带进新对话，规避上下文压缩
- 七步图形化 Setup：装扩展 → 授权目录与权限范围 → 建隧道与受限 API key → 连接 → 在 ChatGPT 插件页添加应用

## 4. 架构与实现

TypeScript + Electron 做本地宿主进程，浏览器扩展负责 UI 侧观察与操作，两者通过 MCP 协议对接；对外开放的口子是一条隧道加一个受限 API key，所以 ChatGPT 侧拿到的是「一个受限的远程 MCP 服务」，而不是你的整台机器。Workers 与 Goal/Loop 是宿主侧的调度层，把一次对话拆成多个带独立上下文的执行单元。

## 5. 上手路径

1. 先在隔离目录里试，只授权一个测试仓库，确认工具调用行为符合预期再扩到主工作区
2. 建 API key 时把额度与作用域都收窄，隧道等于把你本机的 MCP 服务挂到了公网入口上
3. 开 Workers 之前先想清楚任务边界，独立子任务才适合分发，有强依赖的活拆开只会互相等待
4. 把它当「监督式自动化」用：工具调用要逐条看，别让它在无人值守时改生产分支

## 6. 风险与边界

- README 自己写明「使用风险自担」：通过浏览器扩展驱动 ChatGPT 网页 UI，可能与服务方条款冲突，接口改版即失效
- 隧道 + API key 的组合本质是把本地执行能力暴露到外网，配置不当等于开了个无鉴权的远程 shell
- 多 worker 并行会成倍消耗额度与本地资源，且并发写同一仓库时容易互相踩踏
- Electron + 扩展 + 隧道三层都在快速变动，早期版本的行为稳定性不宜指望

## 7. 谁该用 / 谁别碰

已经把 ChatGPT 当主力、又想在真实仓库里让它动手的开发者；愿意读条款、能自己收窄权限的人。只想「问答式写代码」的用户收益有限，配环境的成本高于收益。
