## 1. 它解决什么问题

中小团队的数据库性能问题，通常靠三样东西兜：云厂商的慢查询面板（只覆盖托管库）、DBA 手工跑的脚本、以及出事之后的临时排查。缺的是一个能持续采样、把趋势与异常攒起来的自托管方案——尤其当实例同时在 IDC 与多云、且不全是托管服务时。DBPilot 的定位就是这个缺口：持续采样实例，把 AAS 负载分解、Top SQL、执行计划变更跟踪、缺失索引建议、索引使用与碎片、阻塞与死锁分析、慢查询日志集中到一个 Web 控制台里。

## 3. 关键能力

- 持续采样实例，性能趋势与 AAS 负载分解
- Top SQL 与执行计划变更跟踪
- 缺失索引建议、索引使用率与碎片分析
- 阻塞分析与死锁分析
- 慢查询日志集中查看
- 支持 SQL Server、MySQL、PostgreSQL 三引擎（含引擎能力矩阵）
- 单进程部署，无外部依赖栈；提供 Docker 与源码构建
- 内置 MCP server，供 AI agent 查询诊断数据；另可通过 NuGet 嵌入自有系统
- 密码与 master key 分离配置

## 4. 架构与实现

单体 .NET 服务：采样器按周期从各引擎的系统视图（如 SQL Server 的 DMV、PostgreSQL 的 pg_stat_*）拉取指标，归一化后写入内置存储；分析层在此之上做基线比较与规则判定；Web 控制台渲染趋势与明细；MCP server 作为同一份数据的另一个出口，把诊断结论暴露给 agent。设计取向是「一个进程装完」，牺牲水平扩展换取部署与运维的简单——对中小规模场景是合理取舍。

## 5. 上手路径

1. 先只接一个非核心实例跑一周，用它的开销数据判断是否适合生产——README 有专门的 overhead 章节
2. master key 与登录密码在首次启动就改掉，别用示例值
3. AAS 分解要先建立基线，没有基线的「异常」判断基本无效
4. MCP server 暴露给 agent 前限制其只读，诊断数据里含 SQL 原文，可能带敏感信息
5. 三引擎能力不对等，SQL Server 侧功能最完整，MySQL / PG 需对照矩阵确认

## 6. 风险与边界

- 93 星的极小项目，长期维护与社区支持都不确定
- 采样本身会给被监控实例带来开销，高频采样在弱配置库上可能反成负担
- 单进程部署是单点，进程挂了监控也一起消失
- MCP server 让 agent 可访问诊断数据，等于把内部 SQL 与库结构交给模型上下文
- C# 技术栈对非 .NET 团队的二次开发门槛较高
