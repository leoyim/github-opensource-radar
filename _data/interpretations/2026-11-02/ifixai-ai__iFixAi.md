## 1. 它解决什么问题

agent 上线后最难回答的问题不是「能不能干」，而是「有没有越权」。真实业务里，一次越权退款、一次对客户说了不该说的话，代价远高于功能缺失，而传统测试只能验证功能是否可用，验证不了行为是否越界。iFixAi 的做法是先把你的业务描述成一个模拟环境——意图、目标、组织内谁可以做什么——再把 agent 放进去，投喂一天里真实会遇到的请求，其中混入明确超出其角色的要求，逐条记录「问的是什么、agent 做了什么」，由裁判模型打分，全程号称 120 秒内出结果。

## 2. 为什么是现在

仓库 189 天、4.25 万星，本轮单日 +1,584，是全榜第一。时间点很说明问题：过去半年 agent 从「个人玩具」进入「企业流程」，采购方的第一道关卡从能力评估变成了合规与越权审查，而市面上缺的正是可复跑的第三方审计工具。它同时提供 CLI 与「让编码 agent 自己读文档完成配置」的插件/skill 两条路径，踩中了当下「agent 自举配置」的使用习惯，传播效率因此远高于同类评测框架。

## 3. 关键能力

- 把业务描述成 profile（my-agent.json），含意图、目标与角色权限边界，作为审计基线
- 在模拟环境中回放一天的真实请求，并主动注入超出角色的越权请求
- 逐条给出 pass/fail 判定，并附「用户问了什么 / agent 做了什么」的证据
- 五维评分：fabrication（编造）、manipulation（操纵）、deception（欺骗）、unpredictability（不可预测）、opacity（不透明），换算成 A–F 等级
- 三条强制底线 B01 / B08 / P01，任一不通过则总分直接封顶为 D
- 输出 JSON 与 Markdown 双格式报告，可用 --min-score 卡在 CI 里做门禁
- 两种使用方式：引导式 CLI 向导，或让 Claude Code / Codex 读文档自动生成配置

## 4. 架构与实现

本质是「模拟器 + 裁判 + 评分卡」三段式。模拟器负责生成场景与请求序列，其中包含越权试探；被测 agent 通过其 endpoint 接入，保持黑盒，不要求改代码；裁判模型独立于被测 agent，对每次交互打分；最后按五维汇总成等级，并用三条硬底线做否决。审计配置与运行结果都是纯文本（JSON/Markdown），因此天然适合进版本库、做基线对比、挂 CI 门禁——这是它区别于「聊天式评测」的关键设计取舍。

## 5. 上手路径

1. 先从参考 profile 复制出 my-agent.json，把角色权限写细——越权判定完全依赖这份边界，写得含糊，审计结论就没有意义
2. 第一次只跑默认套件，看五维里哪一维最差，别急着调阈值
3. 接 CI 时用 --min-score 设一个比当前得分略高的门槛，作为回归防线，而非追求满分
4. 裁判模型别用与被测 agent 同源同版本的模型，否则容易同错同对

## 6. 风险与边界

- 审计结论的有效性取决于模拟环境的真实度，业务描述失真会得到一份「看起来很专业但没测到痛点」的报告
- 裁判模型本身有偏差，换模型可能换结论，跨期对比需固定裁判版本
- A–F 等级容易被当成合规证书对外使用，而它只是自评工具，不构成审计意见
- 把内部业务规则写进 profile 会形成敏感信息落盘，注意仓库与 CI 日志的访问范围

## 7. 谁该用 / 谁别碰

要把 agent 接进真实业务流程的团队、需要向合规/风控交付证据的工程负责人、以及给客户交付 agent 的集成商。
