## 1. 它解决什么问题

手工点控制台创建云资源，问题是不可复现、不可评审、不可回滚：环境之间靠人脑记差异，一次误删要翻半小时操作日志。Terraform 的做法是把基础设施写成声明式配置，用资源图算出「当前状态」到「期望状态」的差异，生成执行计划供人审阅后再落地。这份配置可以进版本库、走 PR、被团队共享复用，从而让基础设施第一次具备软件工程的那套约束。

## 2. 为什么是现在

4,616 天、5 万星，本轮 +151。它今天上榜没有特殊事件，属于基础设施类目在榜单尾部的常态占位。但有个背景值得放在这里：许可证从 MPL 改为 BUSL 之后，OpenTofu 分叉已经稳定，企业选型时「用哪个」重新变成需要决策的问题；同时 Terraform 的定位正在被 AI 编码 agent 侵蚀——agent 直接调云 API 建资源，比写 HCL 更快，IaC 的价值重心因此从「描述资源」向「审计与回滚」偏移。

## 3. 关键能力

- 声明式配置描述基础设施，配置可版本化、可评审、可复用
- 执行计划（plan）：先展示将要发生的变更，再决定是否 apply
- 资源图：自动构建依赖关系，对无依赖资源并行创建与修改
- 提供商生态覆盖主流云与自建方案，支持自定义 provider
- 状态文件记录真实资源映射，支持远程后端与状态锁
- 官方文档、教程、认证考试与论坛支持完整

## 4. 架构与实现

核心是「期望状态 vs 实际状态」的收敛引擎：解析 HCL 配置 → 构建资源依赖图 → 读取 state 得到实际状态 → diff 出执行计划 → 按图拓扑序并行 apply。Provider 是插件化的，通过 gRPC 与核心通信，因此新增云厂商不需要改核心。状态文件是整个模型的单点：它既是缓存的资源映射，也是唯一的真实来源，因此远程后端与锁机制是生产环境的必备件。

## 5. 上手路径

1. 状态文件必须放远程后端并加锁，本地 state 是团队协作最常见的翻车点
2. 先 plan 再 apply 是纪律不是建议，plan 输出要进 PR 让人看
3. 按环境拆目录而不是拆工作区，工作区容易让人误以为隔离了实际资源
4. provider 与模块版本全部锁定，否则不同机器 plan 出不同结果
5. 敏感值走 secrets 后端，不要写进 tfvars 提交到仓库

## 6. 风险与边界

- 许可证为 BUSL（README 标注 NOASSERTION），商业使用有明确限制，需评估是否转 OpenTofu
- 状态文件损坏或被并发写入会直接导致资源失控，恢复成本极高
- plan 与实际 apply 之间仍可能因外部变更产生漂移，需要定期 refresh
- 复杂模块的抽象层层嵌套后，改一行配置可能触发大范围重建
- 用 agent 生成 HCL 时容易出现「看起来合理但会重建资源」的写法，plan 必须逐条看

## 7. 谁该用 / 谁别碰

管理多云或复杂基础设施的运维/SRE 团队、需要把环境配置纳入代码评审的组织、以及给客户交付可复现部署方案的集成商。
