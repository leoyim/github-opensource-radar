## 1. 它解决什么问题

项目自述的定位是「礼品兑换平台」：你生成兑换码发给用户，用户在网页输入兑换码和自己的 X 用户名，系统自动完成 Premium 赠送的下单与付款。技术上它解决的是一套完整链路——兑换页自助、管理后台批量生成与统计、凭据 AES-256-GCM 逐条加密、付款前校验金额与商户、付款确认只提交一次。功能上是完整的，问题在它实现这些功能所需的前提。

## 2. 为什么是现在

31 天、1,283 星，本轮无快照差值（heat 按创建速度估算为 195.3）。它出现在榜单上说明这类「支付自动化 + 账号代操作」工具在中文社区仍有稳定需求，常见于代充、代开会员的灰色生意。但必须指出：它要求用户提交 X 账号的 auth_token 与 ct0 Cookie，以及真实银行卡的卡号、有效期、CVC、持卡人姓名与账单地址，并在服务端加密保存、多卡随机轮换。这个组合已经超出「工具」范畴。

## 3. 关键能力

- 兑换页：用户输入兑换码与 X 用户名后自助完成，实时显示处理进度
- 管理后台：生成/停用兑换码、批次管理、统计面板、订单状态查看
- 凭据逐条 AES-256-GCM 加密存储
- 付款前逐项校验金额与商户，付款确认只提交一次（防重复扣款）
- 多张银行卡在服务端加密保存并随机轮换，可复用同一账单资料
- 代理支持：直连或 sing-box 任意 outbound（anytls、socks、http、shadowsocks、vmess、vless、trojan）
- 本地演示模式：内置内存示例数据，不连接真实服务

## 4. 架构与实现

单体 Web 服务 + 自动化执行器：前端是兑换页与管理后台，后端负责兑换码核销、作业排队与状态机推进；执行器用 X 的登录 Cookie 冒充账号身份发起赠送流程，用配置的 Stripe 公钥与银行卡完成支付，多卡轮换用于规避单卡限额或风控。凭据加密落库，因此运行者需要同时保管数据库密钥与密码文件。整套设计的隐含前提是「以他人身份执行支付」，这也是它风险的根源。

## 5. 上手路径

1. 不建议部署。它需要你交出 X 账号 Cookie 与真实卡信息，这两项的组合等价于把账号与支付能力外包给一台服务器
2. 如果只是想学习其工程结构，只看本地演示模式（内置内存数据，不连真实服务）即可，不要配置真实凭据
3. 任何情况下不要把 auth_token、ct0、CVC 提交给第三方部署的实例——那等于直接送出账号与卡
4. 若已使用过，立即在 X 侧登出所有会话并重置密码，同时联系发卡行核查异常授权

## 6. 风险与边界

- 要求提交账号 Cookie 与完整卡信息（含 CVC），这是钓鱼与盗刷的标准信息集
- 以他人身份批量代付违反 X 与支付机构的服务条款，账号封禁与资金冻结是预期结果
- 多卡随机轮换是典型的规避风控特征，可能触发发卡行的反欺诈处置
- 服务端集中存储多张可用卡，一旦泄露或被运营者滥用，后果由卡主承担
- 代充/代开业务本身常与洗钱、诈骗资金流转关联，参与者可能承担法律责任
- README 中「请只填真实信息」的表述，进一步说明它需要真实凭据才能工作
