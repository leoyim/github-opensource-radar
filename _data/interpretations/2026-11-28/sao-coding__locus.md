## 1. 它解决什么问题

数据库客户端在连生产库时最容易出事：手滑点到删除、误执行一条没加条件的 UPDATE、或者大结果集把界面卡死导致误操作。多数客户端的做法是给个「危险操作确认」，然后一切照旧。

## 2. 为什么是现在

11 天、115 星、2 fork、10 个开放 issue，Rust 与 AGPL-3.0，Windows 专用。体量很小，但它对生产库的处理方式在本期所有项目里最具体。

## 3. 关键能力

- 支持 MySQL/MariaDB、PostgreSQL、SQLite、Redis、Oracle、SQL Server
- 结果边查边流进虚拟化网格，慢查询不阻塞输入与切页
- 取消会真的在服务端终止查询，而不只是停止渲染
- 生产连接默认只读，写入需限时解锁并逐条确认
- 每个写入语句进审计日志，单窗口加垂直标签与命令面板

## 4. 架构与实现

Rust 加 GPUI 自绘界面，单个小体积 exe。连接层按数据库类型适配驱动，结果集走流式返回，再用虚拟化网格渲染，因此内存占用与结果规模解耦。写入门禁是一层语句分类器：按语句文本判定是否写入，已知有副作用的函数（nextval、pg_terminate_backend、GET_LOCK 等）单独列出——README 也明说 SELECT 调用的未知函数不做副作用检查，这是诚实的边界声明。

## 5. 上手路径

1. 首次连接生产库就把它标为 Production，让默认只读立即生效
2. 用一条无害的 UPDATE 验证限时解锁与逐条确认是否按预期拦截
3. 大表查询时观察网格是否真的流式加载，而不是等全量返回
4. 从源码构建时注意 GPUI 的平台依赖，目前只支持 Windows

## 6. 风险与边界

- 11 天的新项目，边界情况与驱动兼容性覆盖有限
- 语句分类只看文本，通过 SELECT 调用未知函数仍可能产生副作用
- AGPL-3.0，内部使用之外的分发需评估许可义务
- 仅 Windows，且发布校验依赖 minisign 与构建来源，需自行核对

## 7. 谁该用 / 谁别碰

经常连生产库排查问题、又不想每次都提心吊胆的开发者；需要审计「谁在什么时候改了什么」的团队。
