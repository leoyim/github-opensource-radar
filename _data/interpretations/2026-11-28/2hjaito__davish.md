## 1. 它解决什么问题

管理一台 Linux 服务器，通常要在 ssh、scp、docker logs、systemctl、nginx 配置、cron 之间来回切，或者装一个 Web 面板——后者意味着在服务器上多开一个端口、多一套要打补丁的面板程序。

## 2. 为什么是现在

32 天、478 星、46 fork、32 issue，Go 与 GPL-3.0。它选择的是最保守的一条路：只依赖 sshd 与 SFTP，所有界面逻辑跑在本地。对「不想在服务器上多装东西」的人来说，这个约束本身就是卖点。

## 3. 关键能力

- 终端、文件、服务、Docker、日志、cron、nginx、端口、磁盘、登录安全、SSH 密钥、软件包、git 集中在一处
- 无 agent：服务端只需 sshd 与 SFTP，不开新端口、不落文件
- 破坏性操作执行前展示确切命令，命令日志可导出为可重放脚本
- 密码与口令只存系统钥匙串，sudo 密码不保存
- 离开即锁：独立锁密码、macOS 支持 Touch ID，唤醒/空闲/快捷键触发

## 4. 架构与实现

本质是一层「把 SSH 命令结构化」的桌面外壳：本地进程通过 SSH 执行受控命令集并解析结果，界面按领域（服务、容器、文件）组织。因为不装 agent，所有状态都要现场采集，所以首次打开会有明显加载；也因为不落文件，卸载即干净。命令预览与导出脚本这两项，是把「可审计」做进了交互流程。

## 5. 上手路径

1. 先在一台非生产机上跑通连接与文件浏览，确认密钥与钥匙串行为符合预期
2. 把生产机连接标成需要额外确认的级别，再用一次重启服务验证预览是否到位
3. 导出一次命令日志，检查它是否真的能独立重放
4. 服务器只需 sshd 与 SFTP，若走非标准端口或跳板机，先配好再谈其他功能

## 6. 风险与边界

- 全部能力压在 SSH 通道上，弱网或高延迟下体验明显下降
- 无 agent 意味着部分指标靠临时命令采集，高频刷新成本高
- GPL-3.0，商用或闭源集成需评估许可义务
- 32 天的项目，边界情况（异常退出、并发操作）仍在收敛

## 7. 谁该用 / 谁别碰

管几台到几十台 Linux 服务器、又不想装 Web 面板的开发者与运维；对「服务器上少装东西」有硬性要求的场景。
