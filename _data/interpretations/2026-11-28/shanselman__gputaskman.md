# shanselman/gputaskman · 项目解读

> **一句话**：把 GPU 显存从「占了多少」拆到「被谁占了、占在哪一层」。

## 1. 它解决什么问题

任务管理器只会给出一个总量：15 GB 已用。可在跑本地模型时，真正要回答的是权重占多少、KV 缓存占多少、浏览器与合成器各占多少，以及为什么大量显存被放在系统内存里。缺了这层归因，调上下文长度、换量化方案、判断是否该换卡都只能靠猜。

## 2. 为什么是现在

25 天、3,889 星、196 fork、12 issue，Python 与 MIT，作者是长期做 Windows 开发工具链的工程师。它把按进程的显存与引擎活动，和已加载的运行时、模型文件、LLM 缓冲区对上，恰好补在这类工具的空档上。本期它是 ai 方向里唯一一个「观测层」而非「推理层」的项目。

## 3. 关键能力

- 按进程列出显存占用与 GPU 引擎活动，并标注运行时的加载情况
- 把 LLM 的模型权重与 KV 缓存分项拆出，回答「显存去哪了」
- Windows 侧接 NVIDIA/AMD 遥测与 Intel WDDM 活动；Linux、WSL 原生支持
- Apple Silicon 走 macOS 分支，NixOS 提供 flake
- 安装路径三条：PyPI、Windows 便携包、克隆后运行

## 4. 架构与实现

终端 UI 之下是一组平台适配层：Windows 走厂商遥测接口加 WDDM 活动计数，Linux 读 DRM 的 fdinfo 按客户端归集。README 把归因的边界写得很清楚——缺失 client identity 时无法归因、fd 传递与共享缓冲会重复计数、主节点（通常是合成器）的副本被 root 持有的 logind 保存、老内核缺 drm-shared-vram 字段只能降级处理，这些情况都被显式标为「不完整」而不是给一个看起来精确的数。WSL 的按进程匹配另有一套说明。

## 5. 上手路径

1. 先 pip 装一份跑起来，对照任务管理器确认总量口径一致，再去看分项
2. 跑本地模型时开一次，确认 KV 缓存随上下文长度变化的幅度符合预期
3. 在 WSL 里核对「按进程 VRAM」是否与宿主机侧数字对得上，这是它最容易出偏差的一段
4. 遇到标为不完整的进程，先看是不是 fd 传递或共享缓冲导致，别据此判断泄漏

## 6. 风险与边界

- 属观测工具，不解决显存不足本身；结论质量取决于内核与驱动的 fdinfo 完整度
- AMD 侧依赖 fdinfo，老内核会缺字段，数字可能偏低
- WSL 的进程匹配依赖宿主与发行版两侧信息，跨版本行为可能变化
- 单一作者维护，Windows 驱动与厂商接口变动时跟进速度是变量

## 7. 谁该用 / 谁别碰

在本地跑模型、需要判断显存被谁吃掉的开发者；做 Windows 图形或游戏、要按进程核对显存占用的工程师。
