## 1. 它解决什么问题

传统 CSS 的难点不在语法而在命名与作用域：随着页面增多，选择器层层叠加、样式表只增不减，改动一处常牵连别处。组件化框架缓解了部分问题，但样式与结构分离带来的跳转成本仍在。原子类方案把选择面收敛到一组有限的工具类，代价是 HTML 变得冗长、需要先接受一套约定。

## 2. 为什么是现在

项目 3,319 天、98,169 星，本期 +152。它与 Vite、Svelte、Angular、Bun 同期上榜，是本期「前端基础层集体回流」的一部分。README 极为克制，只给出定位、社区与贡献入口，说明它已处于「不需要再解释自己」的阶段；判断它是否适合，更多要看团队对约定的接受度，而不是功能清单。

## 3. 关键能力

- utility-first 的 CSS 框架，用组合工具类快速构建自定义界面
- 样式决策靠近标记，减少跨文件跳转与选择器层级叠加
- 提供文档站、社区讨论与贡献指南，响应式等能力由工具类覆盖
- 可与 PostCSS 及主流构建工具集成，标签含 functional-css、utility-classes

## 4. 架构与实现

TypeScript 实现、MIT 许可。README 只有 Documentation、Community、Contributing 三节，属典型的成熟项目导航式文档；可确认的是它把样式能力拆成大量单一职责的工具类，由构建期扫描源码生成实际用到的 CSS，因此产物体积与页面数量不成正比。具体的编译管线、配置与主题扩展不在摘录里，应以官方文档为准。标签显示与 postcss、responsive 等生态组件协同。

## 5. 上手路径

1. 按官方文档接入当前构建工具，先在一个独立页面里试用工具类
2. 确认扫描路径配置正确，检查生产构建产物是否只含用到的类
3. 为团队约定类名书写顺序与复用粒度，避免标记中堆出难以审阅的长串
4. 需要抽象重复组合时，优先用组件封装而非自定义 CSS 类，保持约定一致

## 6. 风险与边界

- 原子类让 HTML 变长，未建立书写约定时可读性与 code review 成本会上升
- 依赖构建期扫描，动态拼接的类名可能不被收集，需按文档约束写法
- 设计系统改动会波及大量模板，主题与断点应提前规划
- README 摘录极简，版本间配置差异（如配置文件格式）须查官方迁移指南
