## 1. 它解决什么问题

业务数据常被迫拆成多套系统：OLTP 一套、分析一套、向量检索再一套，中间靠同步管道搬运，既产生数据孤岛，也让一致性边界变模糊。当上层是代理应用、访问量难以预估时，拆库带来的容量规划与跨库协调成本会进一步放大。

## 2. 为什么是现在

项目 4,080 天、40,715 星，本期 +2，为全榜日增最低项之一。值得注意的是描述已改写为「为不可预测增长的 agentic 负载而建」，标签新增 agent-context、agent-memory、agentic——老牌分布式数据库把定位迁到代理场景，是本期最明确的「底座换叙事」信号。README 仍以分布式事务、ACID、水平与垂直扩展、强一致等传统能力为主线。

## 3. 关键能力

- 开源、云原生的分布式 SQL 数据库，面向高可用、水平与垂直扩展、强一致与高性能
- 分布式事务采用两阶段提交协议保证 ACID
- 原生支持事务、分析与向量搜索，减少数据孤岛与跨系统搬运
- 描述强调面向 agentic 负载，标签含 agent-context、agent-memory、agentic

## 4. 架构与实现

Go 实现、Apache-2.0 许可，40,715 星、7,527 个开放议题。README 明确是分布式 SQL 数据库，核心是两阶段提交支撑的 ACID 分布式事务，以及计算与存储可分别扩展的云原生结构；最新定位把分析与向量搜索纳入同一引擎，因此事务型与分析型负载不必跨库同步。agent-context / agent-memory 标签指向代理的记忆与上下文存储用途。具体拓扑、TiKV 与 PD 等组件分工以架构文档为准。

## 5. 上手路径

1. 按 Quick Start 起一个最小集群，先验证分布式事务与 SQL 兼容性
2. 用自有读写模型压测水平扩展时的延迟与一致性表现
3. 分别验证分析查询与向量检索路径，确认是否真能替掉现有旁路系统
4. 若用于代理记忆与上下文，再核对容量规划与多租户隔离方案

## 6. 风险与边界

- 7,527 个开放议题与完整分布式栈，运维复杂度显著高于单机数据库，需专门能力
- 「事务 + 分析 + 向量」同库是收益也是耦合，任一负载异常可能影响整体
- 代理场景的定位较新，agent-context / agent-memory 相关能力成熟度需实测
- 跨版本升级涉及存储格式与协议兼容，应按官方路径逐步推进

## 7. 谁该用 / 谁别碰

需要一套库同时承载事务、分析与向量检索、且有分布式运维能力的数据平台团队。
