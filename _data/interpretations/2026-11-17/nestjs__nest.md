## 1. 它解决什么问题

Node.js 起步容易，规模化容易散：路由、校验、鉴权、异常处理各写一处，团队一多就变成风格拼盘。想换框架又要重写业务逻辑。

## 2. 为什么是现在

本期 77,115 星、8,727 fork，3,572 天；在大量轻量框架涌现的当下仍在榜，说明「结构化后端」的需求稳定存在，且它与 Express、Fastify 之间保留了渐进迁移路径。

## 3. 关键能力

- 模块、控制器、服务分层，依赖注入由容器统一管理
- 校验、鉴权、异常处理等横切关注点各归一处，可组合复用
- 可从 Express 逐条路由迁移，也可整体接入 Fastify
- 可作为 Next.js 应用的后端，承接路由处理器
- 配套 CLI、文档与长期维护的生态

## 4. 架构与实现

基于装饰器与元数据描述模块与依赖关系，运行时由 IoC 容器装配；底层 HTTP 适配器可替换，业务代码不绑定具体服务器实现。

## 5. 上手路径

1. 用 CLI 生成一个最小项目，先跑通一个带 DTO 校验的接口
2. 把现有 Express 的一条路由迁过来，验证中间件与异常处理的差异
3. 再引入一个横切关注点（如鉴权守卫），确认分层是否成立

## 6. 风险与边界

- 装饰器与元数据依赖编译配置，工具链升级时需要同步调整
- 抽象层较多，小项目容易过度设计
- 生态包质量参差，引入第三方模块需评估维护状态
- 与轻量框架相比启动与内存开销更高

## 7. 谁该用 / 谁别碰

需要长期维护、多人协作的 Node.js 后端团队；一次性脚本或极简 API 用轻量框架更合适。
