## 1. 它解决什么问题

agent 改代码时靠 grep 与逐文件阅读建立上下文，仓库一大就出现三类浪费：token 消耗高、工具调用轮次多、改完不知道影响了哪些调用点。上下文窗口再大也追不上代码库的增速。

## 2. 为什么是现在

本期 78,419 星、308 天，当日新增 101 星，MIT。它把索引内核用 Rust 写、以 npm 分发并做签名与 provenance 校验，说明「本地代码索引」正在成为 agent 的标准配件而非可选插件。

## 3. 关键能力

- 预索引代码知识图谱，代码变更后自动同步
- 面向 agent 的精准上下文：按调用关系取片段，而不是整文件喂入
- 覆盖 Claude Code、Codex、Cursor、Gemini、Copilot 等多家宿主
- 100% 本地运行，代码不出机器
- 发布产物带签名与构建证明，npm 包内置 Node 运行时

## 4. 架构与实现

Rust 内核负责解析与建图，索引落在本地；宿主通过插件或 MCP 调用检索接口，返回结构化上下文。分发侧把 Node 运行时一并打包，避免宿主环境差异导致装不上。

## 5. 上手路径

1. 在中型仓库上装一次，比较接入前后同一任务的 token 消耗
2. 抽查它给出的调用链是否准确，尤其是动态派发与反射场景
3. 把索引目录排除在版本控制与备份之外，避免体积膨胀
4. 团队统一版本，避免不同成员索引 schema 不一致

## 6. 风险与边界

- 图谱准确性依赖解析器对各语言的支持程度，弱类型与元编程场景易漏边
- 宿主插件生态变化快，升级后可能出现接口不兼容
- 仓库极大时首次建索引耗时与磁盘占用需评估
- 宿主侧宣传矩阵较广，实际体验差异需自行验证

## 7. 谁该用 / 谁别碰

在中大型代码库上高频使用编码 agent 的团队；小仓库或一次性脚本收益有限。
