## 1. 它解决什么问题

开源大模型越做越大，个人与小队要么租云 GPU，要么退回小参数模型。想在自有硬件上跑接近旗舰规模的模型，通常要自己拼推理引擎、量化与显存调度，工程门槛远高于「下载一个模型」。

## 2. 为什么是现在

本期 3,226 星、当日新增 66 星，Apache 生态外少见的 CUDA 单语言仓库。它同时支持 NVIDIA 与 AMD、Windows 与多卡，并对外提供 OpenAI / Anthropic 兼容接口，说明本地推理正从「能跑」走向「能当服务用」。

## 3. 关键能力

- 按对话内容动态分层：活跃专家驻显存，次热放内存，其余落 NVMe
- 自动探测 GPU、CPU、内存与 SSD 规格并据此调参
- 单卡 8 GB 起，可扩展到 16 卡，支持 AMD 与 Windows
- 对外暴露 OpenAI 与 Anthropic 兼容 API，可并发多请求
- 一个面板管理多模型，含 GLM、DeepSeek、MiniMax、混元等系列

## 4. 架构与实现

每个模型配一套专用引擎，核心是专家路由与分层缓存：按 token 分布决定哪些专家常驻 GPU，冷专家换出到内存与磁盘，换取在有限显存下维持大模型可用性。前端是一个本地 dashboard，服务端对上层伪装成标准 API。

## 5. 上手路径

1. 先在单卡机器上跑最小配置，记录首 token 延迟与稳态吞吐
2. 用自家真实对话样本压测，观察换入换出是否造成明显卡顿
3. 需要接入现有应用时，把兼容 API 指向本地端口，先做旁路验证
4. 多卡或 AMD 环境要单独验证驱动与算子覆盖，不要假设与 NVIDIA 等价

## 6. 风险与边界

- 分层调度依赖高速 NVMe，机械盘或低速盘会让体验显著变差
- 「8 GB 可跑」指的是能启动与低并发可用，不等于高并发生产级
- 模型权重来源与量化版本需自行核对，仓库不提供权重合法性担保
- 项目对显卡驱动与 CUDA 版本敏感，环境升级可能直接破坏推理

## 7. 谁该用 / 谁别碰

有本地 GPU、对数据不出内网有要求、且愿意自己调优的开发者与小团队；不适合期望开箱即得云端级吞吐的场景。
