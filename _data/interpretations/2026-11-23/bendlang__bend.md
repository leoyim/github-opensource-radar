## 1. 它解决什么问题

当代码主要由 AI 生成，人类评审退化为读结论而非读实现，语法的正确性不再等于意图的正确性。自然语言有歧义，主流语言又没有可机械校验的规格层，于是「AI 有没有按我说的做」只能靠测试抽样。

## 2. 为什么是现在

本期 25,781 星、1,181 天，当日新增 53 星。Bend 2 把 dependent types 与 GPU 后端放在同一套语义里，README 直接给出与 C、Lean、Agda 的运行时与检查器对照，属于少数敢把「证明」做成常规编译流程的项目。

## 3. 关键能力

- 定律（laws）声明意图约束，比自然语言更精确
- 证明（proofs）机械校验实现是否满足声明，而非抽样测试
- 单核性能对标 C，多核与 GPU 走同一份源码
- 整个语言可跑在 GPU 上，含完整的内存统一
- 自带检查器，可验证数学证明且速度显著快于传统证明助手

## 4. 架构与实现

以强类型、纯函数与线性（linearity）为基础，编译到 HVM 风格的交互网络运行时，因此同一程序可在 CPU 与 GPU 上执行；证明检查与代码编译共用一套中间表示，避免规格与实现两套语义漂移。

## 5. 上手路径

1. 从官方安装脚本装工具链，先跑仓库自带的示例与基准
2. 挑一个已有小模块，用 laws 重写接口约束，比较校验通过的难度
3. 把证明检查接进 CI，观察对迭代速度的实际影响
4. 不要一开始就重写核心系统，先在新写的边界模块上试用

## 6. 风险与边界

- 生态与库覆盖远不及主流语言，工程化落地需要自建轮子
- 写证明的成本高于写测试，团队需要新的技能栈
- README 中的性能数字为目标值，实际表现依硬件与程序形态差异较大
- 安装脚本走 curl 管道执行，生产环境应改为校验后的包管理方式

## 7. 谁该用 / 谁别碰

关心「AI 生成代码如何被验证」的语言与编译器研究者、以及对正确性要求高于上市速度的团队；不适合常规业务开发。
