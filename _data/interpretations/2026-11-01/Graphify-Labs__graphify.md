## 1. 它解决什么问题

让 agent 理解陌生仓库，现状是 grep 加向量检索：grep 只能按字面匹配，向量召回给一堆相似片段却说不清为什么相关，塞进长上下文后片段之间还会互相矛盾。问题不在检索速度，而在表征——代码是结构化的，用相似度表达它，天然丢失了「谁调用谁」「这个配置影响哪个模块」。graphify 换的是表征方式：把仓库变成图，查询时沿边遍历，每条边都标明是源码明写的还是工具推断的。

## 2. 为什么是现在

212 天、14 万星，今日 +660，属持续热度而非爆发。这条线被反复推荐的原因不是营销，而是「agent 上下文工程」已经进入拼成本与拼准确率的阶段；同期 anthropics/skills、unslop、pixelfx 都以技能形态交付，技能生态正在扩容。

## 3. 关键能力

- 以 /graphify 技能插进 Claude Code、Cursor、Codex、Gemini CLI，无需改工作流
- tree-sitter AST 解析代码，确定性、不调 LLM、不出本机
- 输入覆盖代码、文档、SQL schema、配置文件、PDF、图片与视频
- 边分 EXTRACTED（源码明写）与 INFERRED（工具推断），可区分证据强度
- 无 embedding、无向量库，不需要额外的检索服务运维
- 支持两类查询：实体邻域展开，以及两个实体之间的路径追溯

## 4. 架构与实现

两段式。解析段按语言用 tree-sitter 出 AST，抽符号、导入、调用、配置引用，形成确定性图；补全段对文档、PDF、图片做抽取，落到同一张图并标记为推断边，避免与源码证据混为一谈。查询段提供三个操作：问一个问题（命中节点后展开邻域）、追溯两点之间的路径、解释某条边的依据。存储是图结构而非向量索引，所以既不需要 embedding 服务，也不需要向量库的集群运维——代价是首次建图的耗时与内存随仓库规模线性上升。

## 5. 上手路径

1. 先在 5 万行以内的仓库上跑一次，重点看它对动态导入、反射、依赖注入这类「AST 看不见的边」怎么处理
2. 挑一个你熟悉的老 bug，问「这个函数被谁调用」，把答案与 grep 结果逐条比对
3. 看 INFERRED 边占比：占比过高说明实体消解不可靠，结论要打折
4. 想当基线用的话，把图产物纳入 CI 并观察代码改动后是否稳定；不稳定的图无法做回归

## 6. 风险与边界

- 动态语言与反射重的项目，AST 图召回率会明显下降，且下降是静默的
- INFERRED 边是启发式，误连比漏连更危险，因为它看起来很像真的
- README 首屏是 Cloud 版 14 天试用，开源侧与云侧的能力边界需要读清，避免按云版能力做评估
- 大仓首次建图的耗时与内存没有给基准，实际可能成为采用门槛

## 7. 谁该用 / 谁别碰

需要 agent 在大型或陌生代码库里做审查、重构、影响面分析的人；小脚本仓库用 grep 更快。
