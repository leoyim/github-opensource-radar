## 1. 它解决什么问题

Prometheus 加 Grafana 是标准答案，但标准答案有前置成本：要写抓取配置、维护时序库、设计指标标签、调 retention，还得为一个 2GB 内存的小 VPS 单独规划资源。当被监控对象是十几台家用服务器、树莓派或边缘节点时，这套栈的运维开销常常超过被监控系统本身。beszel 的取舍是把「够用的监控」做成一个二进制加一个 agent。

## 3. 关键能力

- Web 界面加轻量 agent，开箱即用，配置量极小
- 历史数据：CPU、内存、磁盘、网络、负载与温度
- Docker 统计：按容器看 CPU、内存与网络历史
- 网络监测：从 agent 侧测响应时间与中断
- S.M.A.R.T. 磁盘健康与故障通知
- 告警可推送到多种通知服务
- 多用户、OAuth/OIDC 登录、可关闭密码认证、API 访问
- 自动备份到磁盘或 S3 兼容存储

## 4. 架构与实现

hub 与 agent 分离：hub 是带 Web UI 与数据库的单一服务，agent 是被监控机器上的小进程，通过 WebSocket 长连接推送指标，因此不需要在防火墙上开入站端口——这对 NAT 后的家用与边缘节点是关键设计。时序数据落在 hub 自带的存储里，按系统维度聚合，容器与磁盘健康作为附加采集项。多用户与 OAuth 在 hub 侧统一处理。

## 5. 上手路径

1. 先在一台机器上跑通 hub 加 agent，确认 WebSocket 能穿透你的网络环境
2. 把告警通道接上并做一次假触发，否则出事时才发现通知没配通
3. Docker 统计需要挂载 socket，注意这等于给 agent 容器较高权限
4. 长期使用前确认 retention 策略与备份目标，历史数据是这类工具的主要磁盘开销

## 6. 风险与边界

- 查询与仪表盘灵活度远低于 PromQL，复杂关联分析做不了
- 数据模型偏「按系统看」，跨机器聚合与自定义指标能力有限
- 挂载 docker socket 带来权限面扩大，多租户环境要谨慎
- hub 是单点，且没有官方高可用方案，规模上限需自行评估

## 7. 谁该用 / 谁别碰

个人与小团队的服务器监控、家用实验室、边缘节点集群；已有成熟可观测体系的公司不必替换。
