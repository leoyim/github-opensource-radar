## 1. 它解决什么问题

给模型加能力的方式长期只有两种：改提示词，或者接工具（function calling）。前者不可分发、不可测试，后者要求写代码并部署服务。中间那层「一段可复用的操作知识」无处安放——公司品牌规范、审稿流程、文档模板这类东西既不是工具也不是 prompt。Agent Skills 的答案是把它变成一个文件夹：指令、脚本、资源放在一起，由模型按需加载。

## 2. 为什么是现在

405 天、18.6 万星、今日 +754，为工具类第一、全榜第二。热度与生态扩张同步：本期 graphify、unslop、pixelfx、OpenMontage 全部以 skill 形态交付，说明这个容器已经被第三方接受，而不再只是官方示例集。

## 3. 关键能力

- 四类技能示例：创意与设计、开发与技术、企业与沟通、文档处理
- Agent Skills 规范正文，定义目录结构、元数据与加载约定
- 可直接复制的技能模板
- 配套文档：什么是技能、如何在 Claude 中使用、如何创建自定义技能
- 插件式安装入口，可从浏览器选择并安装

## 4. 架构与实现

规范的核心是「渐进式加载」：技能的元数据（名称、描述、触发条件）常驻上下文，正文与资源按需读取，脚本在需要时执行。因此一个仓库可以放几十个技能而不撑爆上下文——模型先看目录，命中后再加载细节。目录约定（SKILL.md 加 scripts、references、assets 子目录）让同一个技能能跨 Claude Code、API、桌面端复用，也让第三方工具能静态校验它。

## 5. 上手路径

1. 先读 spec 再读示例。示例展示的是写法，spec 定义的是契约，跳过前者会做出「在本机能用、换宿主就失效」的技能
2. 第一个技能写你每天重复的那件小事，验证「描述写得准不准」比「指令写得多细」更影响触发
3. 把确定性逻辑放脚本、把判断逻辑放指令，两者混写会让技能无法测试
4. 看在什么时机加载上下文：写太长的技能会挤占工作记忆，写太短的会漏掉关键约束

## 6. 风险与边界

- 规范仍在演进，早期写的技能可能随宿主实现变化而失效
- 技能一旦被加载就影响模型行为，供应链风险等同于引入代码依赖，来源需可信
- 示例集中在文档与创意场景，工程类复杂技能的范式还不成熟
- 不同宿主（Claude Code、API、第三方）对技能的支持程度不一致，跨端复用需实测

## 7. 谁该用 / 谁别碰

想让 agent 稳定执行特定流程的团队、要分发内部方法论的组织、做 agent 产品的开发者。
