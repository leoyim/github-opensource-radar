## 1. 它解决什么问题

运维与 SRE 的知识面横跨网络、内核、容器、云、CI 与可观测，任何一本教材都会在某个方向断档；而面试准备的实际痛点不是缺题，是不知道自己缺哪块。零散刷博客解决不了系统性查漏，题库类网站又偏算法。这个仓库走的是另一条路：按技术主题分文件，把每个方向的题目与练习攒在一起，让人能按主题横向扫一遍。

## 2. 为什么是现在

2,585 天、8.6 万星、今日 +342。十年老仓仍在日增榜单，说明系统性查漏的需求没有被新工具替代——恰恰相反，agent 让「写代码」变便宜之后，判断系统为何出问题的能力更稀缺。它本期能上榜也与 Trending 页对老牌基础设施项目的放大有关。

## 3. 关键能力

- 2,624 道题目与练习，覆盖 Linux、Jenkins、AWS、SRE、Prometheus、Docker、Ansible、Git、K8s、Terraform、OpenStack、SQL/NoSQL、Azure、GCP、DNS、Elastic、网络与虚拟化
- 按主题分文件维护，便于按方向横向扫读
- 多数题目附答案或讨论，适合自测后对照
- README 明确声明多数题目不等同真实面试，降低误用预期

## 4. 架构与实现

结构极简：一个仓库、若干按主题命名的 Markdown 文件、一套贡献规范。没有构建、没有站点、没有题库服务，所以它的价值完全来自内容组织方式而不是工程质量。这种形态的好处是零依赖、可离线、可 fork 成公司内部题库；坏处是无法做进度跟踪与错题统计，需要自建。

## 5. 上手路径

1. 别从头读到尾。先按你负责的系统列出薄弱方向，再只读对应文件
2. 把「能答上来」和「能在生产上验证」分开标记，前者是知识，后者是能力
3. 用它的目录结构反推自己的知识缺口，比刷完 2,624 道更有效
4. fork 一份改成内部题库，配上你司实际的架构与故障案例

## 6. 风险与边界

- 内容跨度极大，深度不均，部分条目停留在名词解释层面
- 云厂商与工具版本迭代快，老题目的答案可能已过时，需按当前文档核对
- 题目面向面试而非故障处理，直接照搬会形成「会答题但不会排障」的偏差
- 仓库体量大，全量 clone 与检索体验一般
