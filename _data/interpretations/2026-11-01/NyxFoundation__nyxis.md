## 1. 它解决什么问题

AI 写的后端最容易出问题的地方不是业务逻辑，而是授权：handler 里少一个检查、路径参数没校验归属、角色判断写反——这类漏洞不会被类型系统拦住，测试也只覆盖想得到的情况。nyxis 的思路是把授权从「代码里的 if」搬到「经过证明的策略层」：开发者只写 Cedar schema 与策略，handler 只能调用被批准的动作，构建时校验证明。

## 2. 为什么是现在

6 天新建、314 星，热度按速度估算，规模还很小。它出现的时间点有意思：当 AI 大量生成后端代码时，「如何确信这段代码没有越权」成了新的瓶颈，形式化方法从学术话题变成工程选项。

## 3. 关键能力

- Cedar schema 同时充当表结构：实体类型即表，属性即列
- 策略与 schema 由人编写与批准，构成唯一的授权事实来源
- handler 可由 AI 生成，但只能调用 schema 中声明的动作
- lake build 一步完成编译、绑定已批准来源、审计应用代码与校验证明
- 客户端用 Supabase Auth 的 JWT 通过 HTTP 调用
- 开发者无需写 Lean，只需读懂构建失败的提示

## 4. 架构与实现

三层：形式化层用 Lean 描述数据模型与授权规则，并证明「任何通过类型检查的 handler 都不可能执行未被策略允许的动作」；绑定层在构建时把已批准的策略与实际代码对齐，发现漂移即失败；运行时层是常规 HTTP 服务，鉴权委托 Supabase Auth，数据落 PostgreSQL。核心技巧是把「授权」从运行时判断提升为编译期约束，使 AI 生成的代码在结构上无法越权。

## 5. 上手路径

1. 先读它的证明声明到底覆盖了什么——「授权安全」的范围边界比结论更重要
2. 用它跑一个只有两三个实体的小服务，体验 lake build 的失败信息是否可读
3. 重点验证策略变更流程：改一条策略是否需要重新证明、由谁批准
4. 评估它与 Supabase Auth 的耦合度，换认证方案是否要重做证明

## 6. 风险与边界

- 314 星、6 天，生态与文档都极早期，遇到问题基本只能读源码
- Lean 工具链的学习与构建成本真实存在，即使不写 Lean 也要能读懂报错
- 证明覆盖的是授权模型，不覆盖业务逻辑正确性，别把结论外推
- 与 Supabase Auth 强绑定，迁移成本未验证
