## 1. 它解决什么问题

一个人同时跑多个 agent 做业务时，缺的不是模型能力而是组织：目标谁下的、任务谁在做、花了多少钱、哪个 agent 有什么权限、上次的结论存在哪。这些信息现在散落在十几个会话窗口和本地笔记里，人脑充当调度器，规模一大就失真。Paperclip 把这些做成一个最小可用的组织：目标、任务、权限、成本、技能、历史集中在一个 Node 服务加 React 面板里。

## 2. 为什么是现在

244 天、11 万星、今日 +401。热度跟着「agent 自治业务」的讨论走：当 agent 能连续跑数小时，管理的边际成本就超过了写 prompt 的成本，工具化的时机就到了。

## 3. 关键能力

- 自带 agent 与外部 harness 混用：OpenClaw、Codex、Claude、Cursor 可同队协作
- 按 agent 分配目标与任务，任务视图接近任务管理器而非聊天窗
- 成本与预算监控，可按 agent 维度看消耗
- 权限、技能与历史集中管理，支持 24/7 运行与结果审计
- 手机端管理
- 插件系统，可挂知识库、追踪、队列等扩展

## 4. 架构与实现

Node 服务持有一个组织模型：agent 为成员，任务为工单，目标是组织级对象；每个 agent 绑定一个 harness（决定怎么被调用）与一组权限（决定能碰什么）。执行层把任务下发给 harness 并回收状态与成本，权限与预算在分发前校验。UI 是 React 单页，读写同一套 REST 接口，所以手机端只是另一个客户端，不需要第二套逻辑。插件挂在这条主链两侧，用于扩展知识来源与观测面。

## 5. 上手路径

1. 先用一个 agent 加一个真实目标跑通「目标→任务→产出→成本」闭环，别一上来铺十个
2. 把预算硬上限设好：agent 循环调用在账单上的体现是滞后的
3. 审计粒度先对齐「每次工具调用是否留痕」，这是它相对 tmux 的核心价值
4. 插件从队列开始加，那是并发上来后最先崩的地方

## 6. 风险与边界

- 24/7 自治意味着错误也会 24/7 累积，人工复核点必须显式设计，不能靠 agent 自觉
- 成本面板依赖各 provider 的用量接口，读数可能滞后或缺失，不能当唯一账本
- 若权限只在提示词层约束，它不构成安全边界，真正的隔离仍需容器与最小权限
- 项目自称面向自治业务，但业务责任与合规责任仍在使用者，工具不承担

## 7. 谁该用 / 谁别碰

已经用 agent 承担实际业务、需要审计与预算控制的人；只是写代码的个人开发者不必上这套。
