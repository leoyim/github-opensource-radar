## 1. 它解决什么问题

给 agent 做浏览器自动化，主流做法是截图加视觉模型定位坐标：贵、慢、不稳，页面一改布局就失效，模型还会一本正经地点到错误位置。agent-browser 换的是交互范式——先取无障碍树并给每个可交互元素一个引用（@e1、@e2），后续操作按引用进行，模型只需要读结构化文本，不需要理解像素。

## 2. 为什么是现在

294 天、4.5 万星、今日 +79。它与本期 lightpanda（自研无头内核）、Mika（手机端操作 app）一起，说明「agent 操作界面」正在从视觉方案转向结构方案；Vercel Labs 的出品也让它更容易被前端团队直接采用。

## 3. 关键能力

- snapshot 取无障碍树并为元素生成引用，最适合 AI 读取
- click、get text 等操作直接按引用执行，无需坐标
- 点击失败早报错：元素被遮挡、隐藏、禁用或不在视口内时明确失败而不是假装成功
- connect 通过 CDP 接管已有浏览器，保留登录态
- 会话隔离与 close --all 批量清理
- 实验性 WebMCP：发现页面暴露的工具并调用，带上下文预算控制
- 多种安装方式：npm 全局、项目依赖、Homebrew、Cargo、源码编译

## 4. 架构与实现

Rust 原生 CLI，通过 CDP 驱动 Chrome（首次安装时下载 Chrome for Testing）。核心抽象是「快照即交互契约」：snapshot 产出带引用的无障碍树，后续命令按引用解析到具体节点，因此在两次快照之间页面若发生结构变化，操作会失败而不是误点——这是它比坐标方案可靠的根本原因。WebMCP 层把页面暴露的工具做成可按需发现的能力，并对上下文占用设了上限（工具数、字节数、描述截断），避免页面工具把上下文吃满。

## 5. 上手路径

1. 先用 connect 接管你已登录的浏览器，省掉登录流程，也最接近真实使用
2. 养成「操作前重新 snapshot」的习惯：引用在页面变化后会失效，这是设计而非缺陷
3. 把点击失败当作信号而不是障碍——它报的「被遮挡」通常正是你该处理的弹窗
4. 上生产前给每个站点写 3 条冒烟用例，验证 snapshot 能识别出关键元素

## 6. 风险与边界

- 无障碍树质量取决于页面实现，div 堆出来的站点可能没有可读结构
- canvas 与自定义渲染组件在无障碍树里几乎是黑盒，仍需视觉兜底
- 引用在页面动态更新后失效，长流程需要频繁重新快照，token 成本上升
- WebMCP 为实验特性，页面工具的行为与预算控制可能变化

## 7. 谁该用 / 谁别碰

做浏览器 agent、网页抓取、E2E 自动化替代方案的开发者；已有 Playwright 稳定脚本的团队收益有限。
