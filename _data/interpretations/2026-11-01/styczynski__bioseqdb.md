## 1. 它解决什么问题

生物信息的数据栈长期分裂：序列比对靠 BAM/FASTA 加专用工具（如 samtools、BLAST），样本与临床数据在关系库里，两者靠文件路径关联。想回答「这组变异在哪些患者中出现」就要跨系统搬运数据，既慢又容易错版本。bioseqdb 的做法是给 PostgreSQL 加一个序列类型，让相似序列检索变成一条 SQL。

## 3. 关键能力

- 紧凑序列类型，支持 DNA/RNA/蛋白序列存入列
- 列式存储与专用索引，用于相似序列检索
- SQL 层面做序列匹配，可与关系数据 join
- 提供 Docker 镜像，按发行版与 Postgres 大版本区分
- 附 SQL 演练文档：建表、插入患者数据、读元数据、读序列
- ARM64 与 x86-64 的 Linux、macOS 未签名 alpha 包

## 4. 架构与实现

作为 PostgreSQL 扩展实现：自定义类型负责序列的紧凑编码，列式存储减少扫描量，索引支持近似匹配而非精确相等。查询在数据库进程内执行，因此能直接参与 join 与事务，避免了「先导出文件再跑外部工具」的往返。C 与 VHDL 混合的代码结构说明它有部分硬件描述语言实现（用于并行匹配原型），这也是它被归到 VHDL 语言分类的原因。

## 5. 上手路径

1. 先用 Docker 按你的 Postgres 大版本起一份，版本不匹配是首要失败原因
2. 跑一遍 SQL 演练文档，确认序列检索的返回格式与精度符合预期
3. 拿一小份真实数据比对它与 BWA/BLAST 的命中结果，不要只看 demo
4. 评估写入吞吐：列式存储在批量导入与逐条插入下表现差异很大

## 6. 风险与边界

- 未签名 alpha 包，安全策略严格的环境无法直接安装
- 相似检索的敏感度与工具链（BWA 等）不在同一量级，不能直接替代比对流程
- 扩展升级与 Postgres 大版本升级耦合，运维复杂度高于普通表
- 207 星的小项目，长期维护与文档完善度都无法保证

## 7. 谁该用 / 谁别碰

希望把序列与临床数据放在同一库、且团队已有 Postgres 运维能力的生信团队。
