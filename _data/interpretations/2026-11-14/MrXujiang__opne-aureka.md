## 1. 它解决什么问题

业务人员拿到一张表想问「哪个渠道下滑最严重」，通常要等数据同学写 SQL、配图表、再整理成报告；而把表格传给在线 AI 服务又涉及数据外发。缺的是一个能在本机闭环、无需编程的轻量问答式分析工具。

## 2. 为什么是现在

106 天、71 星、本期无日增。它与本期 netra、dbt-doctor、narwhal 共同呈现数据方向的新切面：四项都把 agent / MCP / 自然语言查询写进定位，但落点分别是表格分析、流量观测、项目质检与数据库客户端，而非泛化 BI 平台的又一份克隆。

## 3. 关键能力

- 上传 Excel / CSV 后以自然语言提问，支持渠道对比、归因、异常检测、趋势预测等多意图路由
- AI Agent 自动完成意图识别 → SQL 生成 → DuckDB 查询 → 数据分析 → 图表推荐
- 基于 SSE 流式分阶段输出 SQL、表格、ECharts 图表与结论
- 一键沉淀为分析报告，可回溯历史会话
- 数据全程保存在本地 SQLite + DuckDB，README 强调隐私可控与私有化部署友好

## 4. 架构与实现

TypeScript 实现的前后端分离应用：前端负责表格上传、对话与 ECharts 渲染，后端以 Agent 工作流编排意图识别、SQL 生成与 DuckDB 查询，SSE 把中间结果流回界面；SQLite 存元数据与会话、DuckDB 承担分析型查询，两侧都不出本机。

## 5. 上手路径

1. 用仓库的一键启动脚本（自动装依赖、创建 .env、同时起前后端），先跑自带示例数据
2. 上传一份自己的 CSV，问一个可人工核对答案的问题，检查生成的 SQL 是否正确
3. 核对 ECharts 图表与结论是否一致，不要直接采信自然语言结论
4. 确认 .env 里的模型配置与数据目录位置，再决定是否接入内部数据

## 6. 风险与边界

- 仓库名拼写为 opne-aureka（疑似笔误），检索与引用时容易找错
- 自然语言转 SQL 的准确性缺乏保障，关键结论必须用原始查询复核
- 无日增、零 issue、71 星，维护活跃度与长期可用性存疑
- 虽称本地存储，但若接入外部大模型 API，数据仍可能随请求外发，需核对配置
- GPL-3.0 许可对二次分发有较强约束，商用前需评估
