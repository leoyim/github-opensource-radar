## 1. 它解决什么问题

直接用通用 LLM agent 做代码评审会反复出现三类问题：大改动里只看一部分文件、报告的行号或文件引用漂移、提示词稍变质量就大幅波动。这三者都不是靠换更强模型能解决的。

## 2. 为什么是现在

55,123 星、4,566 fork，当日新增 289 星，是本期工具方向唯一入选。项目源自阿里内部已服务数万开发者两年的评审助手，开源时同步给出由 50 个仓库 / 200 个真实 PR / 80+ 资深工程师标注 1,505 个问题构成的基准，说明它想证明的是覆盖率与定位精度，而非生成能力。

## 3. 关键能力

- 精确文件选择：确定哪些文件必须评审、哪些应过滤，避免大改动漏看
- 智能文件分绑：把相关变更组织成同一批次交给模型
- 行级精确的结构化评审意见，agent 可读全文、检索代码库并查看其他变更文件
- 内置多语言规则集，覆盖 NPE、线程安全、XSS、SQL 注入等
- CLI、Agent Skills，以及 workspace / 当前分支 / 分支区间等多种评审范围
- ocr scan 可对整个文件或目录做审计，不依赖 diff

## 4. 架构与实现

Go 实现的 CLI，前半段是确定性的 diff 解析、文件筛选与分绑流水线，后半段是带 tool-use 的 LLM agent；规则集作为独立静态检查层与模型结论合并，模型端点可配置且兼容 OpenAI / Anthropic 接口，输出统一为行级结构化评论。

## 5. 上手路径

1. 按 Prerequisites 配置一个模型端点，先用小改动试跑
2. 按 How to Use 选 workspace 或 current branch 模式，检查文件覆盖是否完整
3. 核对报告的行号与文件引用，确认没有位置漂移
4. 把内置规则集接进现有 CI，并保留人工复核环节

## 6. 风险与边界

- 模型端点需自配，调用成本与代码外发范围由接入方承担
- 内置规则集的语言与框架覆盖面有限，需按自己技术栈验证
- 基准由项目方组织标注，宜用自有 PR 做一次独立复核
- 342 个 open issue 说明接入面广、迭代快，升级前需回归验证

## 7. 谁该用 / 谁别碰

有 CI 基础、希望把 AI 评审接进现有流程但要保证覆盖率与定位精度的工程团队；单人小仓库直接用通用 agent 也能凑合。
