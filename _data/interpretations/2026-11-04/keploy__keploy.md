## 1. 它解决什么问题

集成测试的成本结构一直很别扭：写测试比写功能更费时间，造 mock 数据比调通接口更难，而且写完就开始腐化——接口一变，测试全红，维护成本反过来吃掉它带来的收益。keploy 换了个思路：既然线上已经有真实流量，为什么不把它录下来变成测试？它在网络层捕获 API 调用、数据库查询与流式事件，连同返回一起存成「测试 + mock」，重放时不需要真实数据库也能跑。

## 2. 为什么是现在

1750 天、19,281 星，本轮 +221。这类工具的温度取决于一件事——微服务拆分与遗留系统改造的规模。当一个系统被切成十几个服务、没人敢动其中一个时，「有回归网才敢重构」就成了刚需，而手写测试在这种体量下根本补不完。eBPF 让「无侵入捕获」从理论变成默认选项，这正是它相对上一代录制回放工具的位置优势。

## 3. 关键能力

- 在 eBPF 层捕获网络调用、数据库查询与流式事件，不需要改业务代码
- 录制内容自动转化为测试用例与数据 mock，形成可重放的回归集
- 语言无关：因为捕获点在系统调用与网络层，不对运行时作要求
- 提供 sandbox 隔离运行环境，避免录制流量写入真实数据
- 面向 API、集成与 E2E 三类测试场景，不局限于单元级
- 支持在 CI 中作为回归环节执行，配合既有的构建流水线

## 4. 架构与实现

核心是把「观察点」下移到内核：eBPF 程序挂在内核的 socket 与系统调用路径上，捕获进程与外部世界的每一次交互，因此绕开了语言 runtime 与框架的差异。录制产物被规范成「请求 + 依赖响应」的配对，重放时用录制的响应替代真实依赖，从而把集成测试降级成可离线执行的回放。这个设计的代价是黑盒：捕获到的是字节流，语义要由工具推断，遇到动态生成的值（时间戳、随机 ID）需要额外的相关性规则来对齐。

## 5. 上手路径

1. 先在测试环境录制，别直接对生产流量开录——即使是只读流量，也可能触发副作用
2. 录制后必须人工过一遍用例，剔除含随机值与敏感字段的请求，否则重放永远对不上
3. eBPF 需要足够的内核版本与权限（容器内通常要 privileged 或特定 capability），先在目标环境验证
4. 把重放纳入 CI 时给足超时：回放依赖录制的时序关系，慢查询会放大执行时间

## 6. 风险与边界

- 捕获的是字节流，语义靠推断，动态值（时间戳、随机 ID、token）会让重放不稳定
- 录制内容可能包含真实用户数据与凭证，存储与共享前必须脱敏
- eBPF 对内核版本与容器权限有要求，托管 Kubernetes 或受限环境可能无法启用
- 测试集随录制增长会迅速膨胀，缺少治理机制时维护成本会反超手写测试
- 重放验证的是「行为与录制时一致」，无法发现录制时就不存在的缺陷

## 7. 谁该用 / 谁别碰

做微服务改造与遗留系统重构、需要快速建立回归网的团队；接口众多、手写测试补不完的后端团队；以及想把 E2E 验证塞进 CI 又不想维护测试数据的平台方。
