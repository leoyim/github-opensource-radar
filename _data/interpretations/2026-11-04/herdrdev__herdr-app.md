# herdrdev/herdr-app · 项目解读

> **一句话**：窗口只负责排列，core 负责运行——关掉界面，终端和 agent 继续干活。

## 1. 它解决什么问题

同时跑多个编码 agent 时的现实困境是「谁在等我」：十几个终端标签页分散在不同仓库，每个 agent 都在某个时刻停下来等输入，而你不知道是哪一个。更麻烦的是进程生命周期与界面绑定——关窗口就杀掉终端，等于把所有在跑的任务一起终止。herdr 把这两个问题一起处理：空间/标签/分屏负责组织，agent 侧栏按状态汇总，运行权交给独立的 core 进程。

## 2. 为什么是现在

18 天、1,851 星，无基线（首次上榜）。它属于今年新出现的一个品类——「agent 工作台」：不再是终端模拟器，而是把多个 agent 会话、状态与人工介入点集中管理的界面。与同日的 agent-autoloop 相比，它解决的是同一问题的另一侧：一个管后台无人值守，一个管前台多任务可视。这类工具变热，本质是「一个人同时指挥多个 agent」从个例变成了常态。

## 3. 关键能力

- 空间对应一台机器上的一个仓库，内含标签页与可分屏的面板
- agent 侧栏汇总所有空间中的 agent，含其他 agent 派生的 worker
- 状态可视：Working / Blocked（等你）/ Done（你没看时完成）/ Idle
- 点击即看，无面板的 worker 以 peek 浮层打开；终端文本中的地址可 Ctrl/Cmd 点击直达
- 窗口与运行分离：关闭窗口不终止终端，重启或 core 崩溃后保留的分屏以最后目录重开 shell
- 支持 SSH 接入远端机器，远端空间在本地休眠时仍继续运行
- 支持 Linux（需桌面会话与可用 Vulkan 驱动）、macOS（Apple Silicon）、Windows x64

## 4. 架构与实现

架构上的关键切分是「UI 进程 / core 进程」：core 持有终端进程、空间结构与分屏布局，UI 只做呈现与输入。这带来两个直接结果——关闭窗口不影响运行，多端连接可共享同一套结构但各自保留焦点与缩放。agent 状态来自各 harness 的上报，因此侧栏的质量完全取决于 harness 是否愿意暴露状态。代价是复杂度前移：core 崩溃、重启后只能恢复「目录」而非「程序」，说明它选择不做进程状态持久化。

## 5. 上手路径

1. Linux 上先确认 Vulkan 驱动可用，否则应用起不来；容器或无桌面会话环境下不适用
2. 把「关窗口不等于停任务」当成默认心智，但注意关分屏/标签仍会终止其中的终端
3. 远端机器上的空间依赖 core 存活，本机休眠可以，远端掉线不行
4. 用状态侧栏做任务分流，但别完全依赖它——agent 是否上报状态取决于 harness 实现

## 6. 风险与边界

- 18 天的新项目，迭代期功能与数据格式都可能变动
- core 崩溃后保留分屏只恢复目录、不恢复程序，长任务仍可能中断
- agent 状态依赖各 harness 上报，未适配的工具在侧栏里不可见
- Linux 依赖 Vulkan 与桌面会话，服务器与容器环境不可用
- 安装方式以脚本管道执行为主，需自行审阅脚本内容

## 7. 谁该用 / 谁别碰

同时驱动多个编码 agent 的开发者、需要把远端机器与本机终端统一管理的基础设施工程师，以及在做 agent 工作台产品设计的团队。
