## 1. 它解决什么问题

给数据库加语义检索的主流做法是外挂一个向量库：导出数据、生成 embedding、写入另一个系统、查询时再跨系统拼结果。这条链路的成本不在模型，而在同步——数据一变就要重新导出，两份数据的一致性永远滞后。jev4pg 的路线相反：把语义算子做成 PostgreSQL 扩展，在库内直接提供过滤、抽取、排序、匹配与校验，数据不动，查询计划仍在数据库里。

## 2. 为什么是现在

42 天、260 星，无增量。这个方向之所以值得看，是因为它挑战了「向量数据库是默认答案」的假设：对已有 PostgreSQL 的团队，多引入一套存储意味着多一份运维与一致性负担，而 SQL 扩展能把增量成本压到接近零。它附带的 NL2SQL 基准与性能数据也说明作者清楚这类项目最容易被质疑的地方——效果与延迟。

## 3. 关键能力

- 41 个 JEV 语义算子，覆盖过滤、抽取、排序、匹配与校验
- 自然语言查询支持英文与简体中文
- 以 PostgreSQL 扩展形式安装，兼容 14–17
- 在库内原生执行，配合并行查询计划
- 可解释的向量表示，便于核对结果来源
- 附带 NL2SQL 基准与性能对比数据

## 4. 架构与实现

核心是把「语义判断」实现为 SQL 层的可调用算子，让优化器仍能参与计划生成，而不是把所有工作推给外部服务。这样做的好处是数据不搬家、事务与权限沿用数据库既有机制；代价是推理负载压在数据库进程侧，需要独立的资源隔离，否则语义查询会与 OLTP 争抢 CPU 与内存。NL2SQL 与语义算子是两个层次：前者是入口（自然语言 → SQL），后者是能力（SQL 内的语义判断），这个分工比「让模型直接生成 SQL 并执行」更可控。

## 5. 上手路径

1. 先在只读副本或测试库上跑，语义算子会占用数据库资源，直接压主库风险很高
2. 核对 NL2SQL 基准的测试集与你的场景是否接近，公开基准上的表现不等于自有数据上的表现
3. 给语义查询单独设资源组或连接池上限，避免拖慢在线事务
4. 先验证「可解释的向量表示」是否满足你的审计要求，再决定是否用于对外业务

## 6. 风险与边界

- 42 天的新项目，标注为开发预览，接口与算子行为都可能变化
- 推理负载进入数据库进程侧，缺少隔离时会与在线事务争抢资源
- 语义结果的稳定性依赖 embedding 模型版本，模型变更会导致历史结果不可复现
- NL2SQL 在复杂多表查询上的可靠性仍需实测，基准成绩与真实库结构差距较大
- 仅在 PostgreSQL 14–17 上可用，版本升级与扩展二进制兼容性是长期维护点
