## 1. 它解决什么问题

命令行 Agent 目前的使用形态是「人守着终端」：起一个会话、盯着它跑、随时回答追问，人一离开链路就断。想让它后台接活，缺的不是模型能力，而是调度——谁触发、交给哪个 agent、在哪个目录、什么时候必须叫人、人答完怎么接上原来的会话。这些胶水代码每个团队都在重复写。agent-autoloop 把它们收成一个零外部依赖的内核加一组插件。

## 2. 为什么是现在

1 天、392 星，首次上榜。它踩中的是「agent 从交互工具变成后台工人」这个转折点上最缺的一层：不是更强的 agent，而是让 agent 能无人值守运行的流程壳。设计上最聪明的一点是把「等人」做成非阻塞状态——需要决策时发一张卡片，回答前不占进程也不消耗 token，这直接解决了「挂着一个会话等人回复」的成本问题。

## 3. 关键能力

- 事件驱动内核，零外部依赖；事件源、Agent、通知通道、上线流水线全部插件化
- 规则即配置：在 `rules.json` 写清「什么事、交给谁、在哪个目录干」，支持 cron 与外部事件两种触发
- 一行配置接入新 Agent：只要能接收提示词并打印最后一条回复的 CLI 都可接，不需要 SDK
- 非阻塞等待：需人拍板时推送卡片到飞书、钉钉、企微、Slack、Discord 或桌面通知，回答期间不占进程、不耗 token
- 七套开箱模板：每日早报、GitHub Issue 跟进、线上告警排查、用户反馈处理、网站巡检、飞书周报、PR 自动交付
- 规则热加载，写错时沿用旧规则并发卡片提示，不会因配置错误中断在跑的任务
- `agent-autoloop status` 汇总轮数、token 与费用（含统计口径）

## 4. 架构与实现

分层极薄：内核只做事件队列、规则匹配与状态机，其余全部是插件。这个选择让「接一个新 Agent」退化成「写一行命令」，也让「换一个通知渠道」不必改内核。关键机制是会话续接与卡片状态机——agent 用一段约定的代码块（ask / notice / resolve / later / events）在最后一条回复里声明意图，内核据此决定是继续、等待还是预约唤醒。这种「用输出协议代替 SDK」的做法降低了接入门槛，代价是协议靠约定维持，JSON 写错时需要重写该段回复而不是重跑任务。

## 5. 上手路径

1. 先跑 `agent-autoloop try` 走一遍真实闭环（提问 → 退出 → 拍板 → 继续），确认卡片通道通再做正式规则
2. 把需要人拍板的动作收窄到真的高风险项（删数据、重启服务、花钱、对外发消息），否则卡片会变成新的噪音源
3. 规则写完后用 `check` 校验；即便写错也不会中断在跑的任务，但会持续提醒
4. 注意它默认只支持 macOS 与 Linux，且要求 Node 24，Windows 需自行解决

## 6. 风险与边界

- 1 天的新项目，规则语法与插件接口都可能调整，长期项目应锁定版本
- 后台 Agent 无人值守运行，一旦权限过宽（尤其是可执行命令与写文件），误操作影响面大
- 卡片审批是唯一的人工闸门，通知渠道不可达时高风险动作可能被阻塞或误放行
- 平台支持有限（macOS / Linux），依赖 Node 24，环境适配成本需自估
- token 与费用统计是自测口径，不宜作为账单依据
