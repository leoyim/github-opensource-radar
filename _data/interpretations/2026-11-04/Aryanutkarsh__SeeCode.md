## 1. 它解决什么问题

架构图的问题从来不是画不出来，而是画完就死：静态图片无法表达「请求怎么走」「哪一步可能失败」，读者只能靠想象补全时序。而用绘图工具手画一张能动的图，成本高到没人愿意为一次沟通付出。SeeCode 的假设是：既然图的信息源已经是一段结构化描述，为什么不直接从描述生成带交互的产物？

## 2. 为什么是现在

32 天、859 星，无基线（首次上榜）。它的分发方式比技术更值得注意：不是又一个绘图 SaaS，而是 Claude Code 插件与 Agent Skills——让 agent 在解释架构时顺手产出可交互的图。这解决了「谁来画」的问题：agent 本来就在生成结构描述，把它转成图只是多一步。数据可直接读 CSV/JSON 而不过模型，也说明作者清楚「让模型抄数字」是幻觉的常见来源。

## 3. 关键能力

- 从短 JSON 规格生成单个 HTML 文件，可悬停、点击、逐步走查
- 45 种图型：架构、部署、依赖、UML、ER、时序、状态机、泳道、时间线、甘特、看板、象限、鱼骨、Wardley 图、等距视图等
- 每种图型有各自的动画方式（流向追踪、消息逐条播放、图表生长），也可完全静态
- 导出 SVG、PNG、GIF、MP4，可直接用于文档与演示
- 图表数值可读 CSV 或 JSON，避免数据经过模型造成失真
- 主题切换与导入导出，支持对话式微调（「高亮支付路径」「改成深色」）
- 以 Claude Code 插件、Agent Skills 与 CLI 三种方式分发

## 4. 架构与实现

产物是单文件 HTML，意味着渲染逻辑、样式与数据全部内联，没有运行时依赖——这是它能「发给任何人打开就看」的前提。生成侧是「规格 → 布局 → 动画编排 → 导出」的流水线，45 种图型各自实现布局与动画策略。真正的工程难点不是画图，而是布局的稳定性：同一份规格在不同数据规模下要保证可读，这通常靠约束与分页策略而非自动布局算法。导出的 GIF/MP4 需要额外渲染路径，是这套体系里最容易出问题的部分。

## 5. 上手路径

1. 先用一两个你最熟的图型（如时序、架构）验证输出质量，再扩展到全 45 种
2. 把数据放进 CSV/JSON 让图直接读取，不要让模型转述数字——这是控制失真的关键一步
3. 导出视频前先确认尺寸与时长，GIF 在复杂图上体积会迅速膨胀
4. 作为插件使用时注意版本跟随：插件会自动更新到最新发布，行为可能随版本变化

## 6. 风险与边界

- 45 种图型的成熟度不均，冷门图型在复杂数据下可能出现布局拥挤
- 自动布局无法理解语义重要性，关键路径仍需人工指定高亮
- 单文件 HTML 内联全部资源，超大图例会让文件体积与首开时间上升
- GIF/MP4 导出依赖本地渲染能力，无头环境下可能失败
- 32 天的新项目，图型仍在快速增删，输出格式与规格字段可能变动
