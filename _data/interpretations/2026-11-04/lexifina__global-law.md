## 1. 它解决什么问题

法律检索的真正难点是时间：条文会改，改过之后旧版本散落在各处，问「2022 年 5 月 1 日这条怎么写的、是哪部法改的」通常要在多个网站、多份 PDF 之间手工比对。把法律放进版本控制能天然解决这件事——提交历史就是修订史，但前提是「一次提交恰好对应一部生效的法」，而这个建模一直没人系统做过。global-law 把这个映射当成基本约定，每个辖区一个仓库，提交带 In-force 日期。

## 2. 为什么是现在

7 天、1,750 星，无基线（首次上榜）。它此前因为同思路的美国法典版本上过 Hacker News 头条，本次是扩展到全球的版本——传播势能来自「这个想法显然正确，为什么以前没人做」。技术侧的关键变化是 MCP：把一个只读、可离线、18 个工具的法律检索服务端接进编码 agent，等于让「查法条」变成一个可被对话调用的能力，这比做另一个法律网站更有扩散性。

## 3. 关键能力

- 每个辖区独立仓库，一次提交对应一部生效的法律，按 In-force 日期索引
- 主仓库以 submodule 汇总各国语料，支持国家级、州级、市级三层结构
- 命令行工具：查某日全语料、读某日条文、逐行/逐词追溯作者法、比较两个日期之间的变更、列出区间内生效的法
- MCP 服务器提供 18 个只读工具，覆盖查找、按日期读取、逐词溯源、历史、全文检索与合规校验
- 首次读取时对语料历史建一次索引并缓存在 `.git` 内，后续查询走本地缓存
- 自带 Claude Code、Cursor、VS Code、Codex 的接入配置，打开目录即启动；无需联网

## 4. 架构与实现

核心是一个建模决策而非代码技巧：把「法条文本」和「生效日期」绑定在提交对象上，于是 git 的对象模型直接承担了时间维度——`git blame` 天然回答「谁改的」，`git diff` 天然回答「改了什么」，不需要另建一套修订表。命令行与 MCP 都只是在这棵提交图上做查询。代价也很清楚：语料体量大（单国数 GB），克隆必须带完整历史（不能用 `--depth`），首读要建索引；并且这套模型假设「一提交即一法」在各国立法体系中都能成立，遇到打包立法或溯及既往的修订时需要额外约定。

## 5. 上手路径

1. 先只克隆一个语料（`tools/countries.py add`），不要一上来 `--recurse-submodules` 拉全世界，体积是数 GB 级
2. 绝对不要用 `--depth` 浅克隆——日期是从完整历史里读出来的，浅克隆会让查询失效
3. 拉取后若语料被移动到新目录，需执行 `git submodule sync` 与 `git submodule update --init`
4. 从 MCP 的只读工具入手，别急着写解析脚本；先用「某日读某条 + 逐词溯源」验证语料质量

## 6. 风险与边界

- 语料准确性由各国官方文本的数字化程度决定，项目本身不具备校验法律文本正确性的能力
- 体量大且必须完整克隆，对磁盘与网络有实际要求，不适合轻量试用
- 「一提交即一法」的建模在某些立法体系中需要人工判断，边界情形可能不一致
- 代码为 CC0，但各辖区语料沿用其来源条款，商用需逐个核对
- 不是法律服务，条文检索结果不能替代专业意见，误用风险由使用者承担

## 7. 谁该用 / 谁别碰

做法律科技产品的团队、需要按时间维度核对条文的合规与法务人员、研究立法演化的学者，以及想把法律检索接进 agent 工作流的开发者。
