## 1. 它解决什么问题

现在的编码 agent 基本是「人守着终端」的形态：一句话启动、全程盯着、随时回答追问，人一走开链路就断。团队协作场景里这个形态不成立——需求来自 Issue、讨论发生在聊天工具里、审批要落在 PR 上，而 agent 只是一个临时的终端进程。dsh-superagent 换了个位置：它常住在一个仓库旁边，监听 GitHub 与飞书，把「有人请求」变成工作项，在自己的会话与目录里推进，最后回到发起对话的地方交付结果。

## 2. 为什么是现在

4 天、16,866 星，本轮 +3,170，全榜第一。爆发点很明确：这是 DeepSeek 官方账号发布的 agent 系统原型，且恰好落在「agent 从工具变成同事」这个叙事最热的时候。更值得注意的是它附带的方法论文档——把「尽量少占用人的注意力」写成显式约束，并给出「只在被要求或规则允许时行动、只在必须有人行动时才开口」的可执行边界。这类「克制」在 agent 项目里稀缺，反而是它最像产品的地方。

## 3. 关键能力

- 以 bundle 形式运行在 DeepSeek Harness 上，面向单个 GitHub 仓库常驻
- 监听 GitHub 事件，可选接入飞书，把请求转成带上下文的工作项
- 每个工作项在独立 agent 会话与独立目录中执行，互不干扰
- 结果回到发起对话的位置交付，例如直接提交一个 pull request
- 网页面板集中列出「需要人介入」的节点，而不是推送全部过程
- docs/000-philosophy.md 定义了 agent 的行动边界与运维者责任

## 4. 架构与实现

分层是「事件入口 → 工作项 → 会话隔离 → 回写」四段。事件入口做鉴权与白名单（「someone allowed」是显式前提），工作项承载上下文与状态，会话隔离保证并发任务不互相污染文件系统与对话历史，回写则把结果送回来处。设计上最值得学的是把「不打扰」当架构约束：默认静默、只在需要决策时暴露，这意味着系统必须有稳定的状态机来判断「什么时候真的需要人」，而这恰恰是多数 agent 项目省略掉的部分。仓库自述为 prototype，接口与行为都还会变。

## 5. 上手路径

1. 先读 docs/000-philosophy.md 再动手——它决定了这个 agent 什么时候会自己行动，配错了就是替你乱干活
2. 把「谁可以触发」的白名单收窄到最小，事件入口是这套系统唯一的外部攻击面
3. 先用一个低风险仓库试跑，观察它开出的工作项粒度是否符合你的预期
4. 认清这是 prototype：按 README 的说法配置步骤较多，且设计为「让 agent 陪你装」，不要把首次部署当成一次点选完成

## 6. 风险与边界

- 官方明示为原型，接口、行为与部署方式都可能随时变动，不宜直接用于关键仓库
- 常驻 agent 拥有仓库写权限与自主开 PR 的能力，权限边界一旦放宽，误操作的影响面是整仓
- 会话与目录隔离依赖 Harness 的实现，并发工作项下的资源竞争需要实测验证
- 飞书等外部事件源接入后，触发面从「代码贡献者」扩大到「任何能发消息的人」，需重新评估
- 4 天 1.6 万星里含大量围观与试用，真实长期使用反馈尚未沉淀
