## 1. 它解决什么问题

开源贡献的供给侧有个结构性错配：个人与小团队的产能呈潮汐状，有空的时候无处释放，忙的时候无人接手。现有激励要么是纯利他（无偿贡献），要么是纯市场（悬赏、外包），前者不可持续，后者把维护关系变成交易。Overflow 想在两者之间加一层缓冲——把闲置产能记成信用，需要时再兑回来。

## 2. 为什么是现在

60 天、142 星，本轮 +5。它的时点很有意思：LLM 订阅额度成了很多开发者的固定支出，而额度用不完是常态，「把剩余额度折算成对他人的帮助」这个想法只有在订阅制普及之后才成立。机制上它刻意避开了加密货币与真实货币——没有代币、没有支付通道，全部通过 GitHub Issue 与 PR 流转，这既降低了合规复杂度，也让信任建立在已有的协作平台上。

## 3. 关键能力

- 以 GitHub 账号登录，注册自己管理的仓库
- 配置两套标签目录（需求侧与供给侧），标签需预先在仓库中存在
- 自动安装 webhook，监听 issue 与 PR 事件驱动记账
- 信用账本记录「帮助他人」与「获得帮助」的双向流水
- 不引入真实货币与代币，规避支付与合规链路
- 基于 Next.js 与 GitHub API，部署形态简单

## 4. 架构与实现

系统是 GitHub 之上的一层账本：webhook 接收事件，标签目录定义「什么样的 issue 可以被认领」「什么样的交付算完成」，账本按事件累加信用。这个设计把复杂度外推给了标签约定——参与者必须先在仓库里维护好标签体系，机制才能运转。风险也集中在这里：信用的价值完全依赖双边共识，一旦某一侧失衡（大量人想花、没人想赚），账本就会贬值，而系统本身没有调节机制。

## 5. 上手路径

1. 先在仓库里把两套标签建好再注册——标签不存在时 webhook 无法正确归类事件
2. 从熟人小圈子开始跑，信用的可信度依赖参与者之间的既有信任
3. 把「什么算完成」写进标签说明，否则记账会变成扯皮
4. 观察一段时间内的供需比，单边失衡时机制会迅速空转

## 6. 风险与边界

- 信用体系没有锚定物，价值完全取决于双边共识，供需失衡时会迅速失效
- 依赖参与者诚实申报，缺少对抗性设计，刷信用的成本很低
- GitHub 平台的 API 与 webhook 限制是硬约束，规模化后可能撞到速率上限
- 142 星的早期项目，机制尚未经过真实规模检验
- 「用 LLM 额度折算贡献」的换算口径未在文档中明确，实际使用容易出现争议
