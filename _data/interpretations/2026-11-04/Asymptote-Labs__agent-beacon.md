## 1. 它解决什么问题

agent 的能力被三件事反复浪费：会话结束即遗忘、换一个工具就从头开始、同一个坑在不同人手里被踩很多遍。日志工具能记录但不提炼，笔记工具能提炼但需要人手动整理，两者之间缺一层「自动把会话变成可复用知识」的机制。Beacon 要做的就是把跨工具的会话历史统一采集，从中识别出工作流、纠错与调试模式，再以 agent 能检索的形式还回去。

## 2. 为什么是现在

176 天、3,237 星，本轮 +193。这个位置的价值随「一个人同时用好几个 agent 工具」的普遍化而上升：当 Claude Code、Cursor、Codex 各管一段时，记忆的割裂就成了真实成本。更关键的是它选择了 MCP 与 Agent Skills 作为输出接口——不是做一个新客户端，而是把记忆变成所有客户端都能取的公共层，这个站位让它可以跨工具存在。

## 3. 关键能力

- 跨 harness 采集：Claude Code、Cursor、Codex、OpenCode、Cline 等 20 多个工具
- 从会话历史中识别可复用工作流、纠错记录与调试模式，形成知识条目
- 通过 MCP 与 Agent Skills 向后续 agent 提供检索能力
- 完整会话回放：提示词、响应、工具调用、命令、编辑、审批、MCP 活动与 token 用量集中在一条 trace
- 本地优先：JSONL 持久化、目标端显式指定，不锁定单一 harness
- 安装路径区分交互式与静默式，系统包、MDM、CI 场景可免账号运行

## 4. 架构与实现

四段式：采集器按 harness 适配会话格式 → 归一化成统一的事件流（trace）→ 提炼层从中抽取知识条目 → 服务层以 MCP / Skills 暴露检索。归一化是全部难点所在：每个 harness 的事件模型不同，字段语义也不一致，适配器质量直接决定知识提炼的上限。存储选 JSONL 而非数据库，换来可移植与可读，代价是查询能力弱、规模上去后需要外部索引。商业模型是「本地可用、云端可选」，安装时明确给出 opt-out，这一点做得比较克制。

## 5. 上手路径

1. 先跑 `beacon endpoint install` 明确选择本地还是托管——数据去向是这个工具最重要的一个开关
2. 从单一 harness 开始接入，确认会话能被正确归一化后再扩大采集范围
3. 给采集内容设保留期，会话里常有密钥与内部地址，长期堆积会变成泄密面
4. 用 MCP 检索前先人工看几条提炼出的知识，确认提炼质量符合预期再让 agent 自动取用

## 6. 风险与边界

- 会话历史包含完整提示词、命令输出与文件内容，采集即扩大敏感信息的存储面
- 知识提炼依赖自动抽取，低质量条目会让后续 agent 学到错误模式，且难以察觉
- 多 harness 适配器的覆盖深度不一，冷门工具可能只采到部分事件
- 默认引导使用云端，涉及代码与对话内容外传，必须显式确认本地模式
- 跨工具记忆带来新的污染面：一个被污染的条目会影响所有接入的 agent

## 7. 谁该用 / 谁别碰

同时使用多个编码 agent、希望经验能跨工具累积的开发者；给团队搭 agent 基础设施、需要集中治理记忆层的平台工程师；以及研究 agent 长期记忆机制的研究者。
