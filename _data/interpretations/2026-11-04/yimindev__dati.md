# yimindev/dati · 项目解读

> **一句话**：不让 agent 直连数据库，而是给它一组带语义、带权限的工具。

## 1. 它解决什么问题

让 AI 直接写 SQL 查企业库，几乎必然失败在三个地方：它不知道业务语义（`status=3` 是什么意思）、不知道权限边界（这个人能不能看这张表）、也不知道该用哪个口径（活跃用户按登录算还是按下单算）。dati 的位置就在 agent 与数据库之间：把库接进来、补一层语义元数据、把常用查询配置成带参数的 SQL 工具，再以 MCP 服务发布出去，agent 调用的是「工具」而不是裸 SQL。

## 2. 为什么是现在

72 天、74 星，无增量。它属于一个正在成形的品类——数据库 MCP 网关。今年企业侧的真实动作不是让 agent 随便连库，而是「把数据访问收敛成受控接口」，这与前两年「给 agent 开放一切权限」的乐观形成对照。dati 的定位正好踩在这个转向之后的谨慎区间：语义层与权限层是前置的，工具是有限的。

## 3. 关键能力

- 连接数据库并补充语义元数据，让字段与指标具备业务含义
- 配置内置工具或参数化 SQL 工具，以工具形式对外发布
- 发布为 MCP 服务（Streamable HTTP），任意 MCP 宿主可直接接入
- 内置语义层、权限层、工具层三段结构，职责分离
- 支持 MySQL、PostgreSQL、ClickHouse、Doris
- 提供预置样例数据的演示实例，可先验证再接入自有库

## 4. 架构与实现

三段式网关：语义层把物理表映射成业务概念，权限层决定谁能调用哪些工具，工具层把参数化的查询封装成稳定契约。这样的分层让「加一个指标」不必改动上层 agent，也让「收回一个权限」不必重写查询。架构上的关键选择是把 SQL 预置为工具而非让模型现场生成——牺牲灵活性，换来可审计与可复现。代价是覆盖面受限：未预置的问题只能绕道，长尾分析需求会撞墙。

## 5. 上手路径

1. 先用官方演示实例验证 MCP 接入链路，再连自有库；语义元数据是配置成本的大头，别低估
2. 工具的权限粒度按「谁能看哪张表」设计，不要用单一高权限连接跑所有工具
3. 参数化 SQL 里的每个参数都要做类型与范围校验，这是唯一能防注入的位置
4. 给工具加上明确的一句话描述，agent 的选择质量几乎完全取决于描述质量

## 6. 风险与边界

- 74 星的早期项目，生产可用性与长期维护都存在不确定性
- 语义元数据需要人工维护，表结构变更后若不同步，工具会返回错误结果且难以察觉
- 预置工具模式限制了开放式分析，复杂问题仍需人工写 SQL
- MCP 服务对外暴露即扩大攻击面，鉴权与审计必须在网关层补齐
- 支持的引擎数量有限，异构数据源场景需要额外适配

## 7. 谁该用 / 谁别碰

要把企业数据库安全地开放给 AI 助手的数据平台团队、做 ChatBI 与经营分析的产品方，以及需要给内部 agent 建立受控数据访问层的架构师。
