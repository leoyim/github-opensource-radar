## 1. 它解决什么问题

本地跑大模型的真瓶颈不是算力，而是容量与带宽的错配：几百亿参数的 MoE 整模型常驻显存放不下，整块放进磁盘再读入又会被 PCIe 与 SSD 的读速卡死。colibri 的切入点是 MoE 的稀疏性——每个 token 只激活一小部分专家，那么只要保证「被激活的那部分」以最快速度可达，其余部分留在慢速介质上就不影响正确性，只影响速度。于是权重被分成三级：热专家驻 GPU，温专家驻内存，冷专家留在 NVMe 按需流入。

## 2. 为什么是现在

仓库 126 天、47,261 星，本轮 +802。时点上它踩的是同一件事的两面：一方面开源 MoE 权重已经足够好（GLM、Kimi、DeepSeek、Qwen 系列在同一天里被它列了十个引擎），另一方面消费级硬件的显存与模型体积的差距还在拉大。当「能不能跑」变成「跑得多慢」时，用磁盘换容量就成了可接受的交易。纯 C、无框架依赖、单文件对应单模型族的形态，也让它在「不想装一整套推理栈」的人群里传播得很快。

## 3. 关键能力

- 三级分层调度：GPU 显存存热专家、系统内存存温专家、NVMe 按需流式读冷专家
- 纯 C 实现，不依赖 PyTorch / CUDA 运行时框架，一个模型族对应一个独立源文件
- 已内置 13 个引擎：10 个语言模型（GLM-5.2/5.3、Kimi K3、DeepSeek V4 Flash 与 V4.1 Flash、MiMo-V2.6、Qwen3.8-Flash-Next、Qwen3.6、OLMoE 等），1 个图像模型（Qwen-Image-2.1），2 个决策模型（Laya、GLiNER2.5-Decide）
- 直接读取社区已发布的 GGUF 权重，不做二次转换
- 后端三选一：纯 CPU、Vulkan（跨厂商 GPU）、CUDA（NVIDIA）
- README 提供「哪款模型适合我的机器」选型指引，并维护多语言版本

## 4. 架构与实现

本质是把操作系统的按需分页搬到权重上：专家是页，NVMe 是后备存储，一次前向的激活顺序决定预取窗口。每模型一个 C 文件意味着适配层不抽公共抽象——换来零运行时开销和可预测的缓存行为，代价是新增模型要写代码而不是改配置。缓存策略偏静态，命中率最终取决于模型路由本身的局部性：专家选择越集中，分层越有效；越随机，NVMe 读就越频繁地落在关键路径上。这也是它性能方差大的根源。

## 5. 上手路径

1. 先按 README 的选型页核对目标模型在你「显存 + 内存 + 磁盘」组合下是否放得下；放不下时降量化等级通常比换硬件更划算
2. 存储是这套方案的下限：NVMe 顺序读可以接受，SATA SSD 勉强，机械盘基本不可用
3. 优先用上游已发布的 GGUF 原文件，自行转换容易引入格式与精度问题
4. 单模型单文件的组织方式意味着各引擎成熟度不一致，接入前先看该引擎近期的提交与 issue

## 6. 风险与边界

- 每一次冷专家读取都在 token 生成的关键路径上，磁盘随机读延迟会直接表现为交互卡顿
- 「不需要 GPU」是卖点也是边界：纯 CPU 路径能跑通，但吞吐无法与显存常驻方案相比
- 新模型支持依赖维护者逐个手写引擎，跟进速度受人力限制，不宜当作长期稳定的基础设施
- 126 天冲到 4.7 万星，传播速度远快于生态沉淀，实际可用性应以下游反馈和本地压测为准
- Apache-2.0 覆盖代码，但模型权重自身的许可需单独核对，两者不能混为一谈
