## 1. 它解决什么问题

并行跑多个编码 agent 时，最先崩的不是模型能力而是隔离：多个 agent 在同一工作目录里改同一批文件，冲突、覆盖、脏状态混在一起，事后无法判断谁改了什么。常见做法是手工复制仓库、手工切分支、手工清理，一旦并发数上去就不可维护。sandcastle 把这套动作收进一个函数：调用即分配隔离环境、按策略开分支、跑完把提交合回，环境随任务销毁。

## 2. 为什么是现在

8,816 星、231 天，本轮 +31。它出现的位置很准：agent 已经从「一次对话」进入「一次任务队列」，而队列需要调度器。真正让它区别于其他编排库的是 provider 抽象——同一套 API 既能落到操作系统原生沙箱（Bubblewrap、Seatbelt），也能落到容器与云沙箱（Daytona、E2B、Modal、Vercel），意味着「本地跑」与「云端跑」不再是两套代码。这个抽象层次的选择，比它当前的功能完整度更重要。

## 3. 关键能力

- 单一入口 `sandcastle.run()` 启动一次隔离的 agent 执行
- 可配置的分支策略，任务结束把分支上的提交合并回目标分支
- 原生沙箱 provider：Linux / WSL2 用 Bubblewrap，macOS 用 Seatbelt
- 容器 provider：Docker、Podman
- 云沙箱 provider：Daytona、E2B、Fly.io Sprites、Modal、Vercel
- provider 接口开放，可自建以适配内部基础设施
- TypeScript 库形态，可直接嵌入既有 Node 工程与 CI

## 4. 架构与实现

抽象只有三层：调用契约（run）、沙箱 provider（在哪执行）、分支策略（结果如何回收）。把「执行环境」抽成可替换接口是关键决策——安全边界与成本模型因此可以按场景切换，而不必改写编排逻辑。原生沙箱路线最轻，依赖操作系统已有的隔离能力，启动快但隔离强度取决于内核特性；云沙箱路线隔离彻底但引入网络与费用。合并回主干的策略是它最容易出事的地方：并发任务的提交冲突需要调用方自己设计重试或串行化。

## 5. 上手路径

1. 从一个串行任务开始验证合并行为，确认分支策略与冲突处理符合预期后再提高并发
2. Linux 上先确认 Bubblewrap 可用（容器内运行时常被禁用），否则会静默退回弱隔离
3. 给每个任务设定明确的超时与资源上限，agent 循环跑飞时沙箱本身不会替你止损
4. 如果目标是 CI 集成，优先选云沙箱 provider，避免宿主机内核特性差异带来的不确定性

## 6. 风险与边界

- 合并回主干的并发冲突没有银弹，冲突频发时仍需调用方做串行化或人工介入
- 原生沙箱的隔离强度取决于宿主内核与配置，容器环境中能力常被裁剪
- 云沙箱 provider 会引入外部依赖与费用，网络抖动直接表现为任务失败
- 库仍处早期，API 形态可能调整，长期项目应锁定版本
- agent 在沙箱内的行为不受本库约束，「隔离」解决的是文件系统与进程边界，不是行为正确性

## 7. 谁该用 / 谁别碰

要把编码 agent 接进 CI 或任务队列的工程团队、需要并行跑多个无人值守 agent 的平台开发者，以及在评估「本地沙箱还是云沙箱」的架构决策者。
