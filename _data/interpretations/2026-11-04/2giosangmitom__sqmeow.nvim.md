## 1. 它解决什么问题

日常开发里查数据的动作被切得粉碎：改代码在 Neovim，看表结构切 DBeaver，验证一条 SQL 再切回来，中间还有连接配置、结果复制、上下文丢失。对长期住在终端里的人，这种切换的成本远高于查询本身。sqmeow 的定位就是把这层动作留在编辑器内：连接、浏览、查询、编辑结果都在缓冲区完成，且不牺牲数据库类型覆盖。

## 2. 为什么是现在

55 天、162 星，本轮 +1。它出现在数据类榜单里更像一个信号而非热点：这一类需求的真实规模不大，但极稳定——Neovim 生态的数据库插件长期处于「有但不好用」的状态，dadbod 系列解决的是连接与执行，结果集交互一直薄弱。用独立 Rust 进程跑数据库操作、用 Polars 处理结果集，是这个插件相对上一代方案的技术差异点。

## 3. 关键能力

- 多类型数据库统一入口：SQL、NoSQL 与分析型库（ClickHouse、DuckDB、MongoDB、MySQL、MariaDB 等）
- 交互式结果集：浏览、过滤、排序、直接编辑数据
- 查询历史可回溯，不必重跑即可查看上次结果
- 结果集用 Polars 在本地做过滤与排序，减少往返数据库
- 连接与草稿跟随项目存放，便于多项目切换
- 配合 blink.cmp / nvim-cmp 做库表感知补全
- 数据库操作运行在独立 Rust 进程中，不阻塞编辑器

## 4. 架构与实现

分层是「Lua 前端 + Rust 引擎」：Lua 侧只管缓冲区与交互，数据库连接、查询执行、结果集处理全部交给独立的 Rust 进程，通过 RPC 通信。这样做的收益很直接——重查询不会卡住 UI，崩溃也不至于把编辑器带走。把结果集用 Polars 在本地处理，等于把「再看一眼不同排序」的成本从一次网络往返降到内存操作。代价是进程间数据序列化的开销，超大结果集下需要分页策略配合。

## 5. 上手路径

1. 先确认目标数据库的驱动是否已覆盖，冷门引擎可能只支持基础查询
2. 把项目级连接配置放在仓库外或加入 gitignore，连接串里常有凭证
3. 对超大表默认加分页与 LIMIT，结果集走进程间传输，没有上限时内存会先撑不住
4. 编辑结果集前先确认主键定义正确，否则写回可能命中错误的行

## 6. 风险与边界

- 55 天的新插件，数据库驱动覆盖广但深度不一，生产库上使用前需逐项验证
- 在编辑器内直接编辑数据风险较高，缺少事务预览时容易误改
- 结果集经进程间传输，超大结果会带来明显内存与延迟开销
- Rust 引擎需按平台编译或下载预编译产物，跨平台一致性依赖发布流程
- Neovim 插件生态变动快，依赖的补全插件接口可能变化

## 7. 谁该用 / 谁别碰

长期在 Neovim 中工作、需要频繁查库的后端开发者；希望减少 GUI 工具切换的数据工程师；以及给终端工作流做工具链整合的极客用户。
