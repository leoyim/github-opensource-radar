## 1. 它解决什么问题

视觉流水线里大量操作本质是「一批图像上的确定性变换」：缩放、裁剪、色彩空间转换、畸变校正、单应估计。手写实现的问题不在难，而在长：一旦链路变长、需要梯度回传、需要换设备，自己拼的 numpy / OpenCV 代码就开始脆——CPU 与 GPU 之间来回拷贝，梯度在某一步断掉，批处理维度对不齐。Kornia 把这些算子统一成 PyTorch 张量操作，让变换天然可微、可批量、可在同一设备上完成。

## 2. 为什么是现在

仓库 2,996 天、12,312 星，本轮 +272。一个八年的库还能出现在今日榜单，说明需求没被新框架吃掉：可微分视觉在数据增强、自监督预训练、端到端几何估计（SLAM、多视图重建、相机标定）里仍是底层能力，而这些领域的模型迭代反而在加速。它稳定的位置是「不是框架，是算子库」——不与训练框架竞争，因此不会随某一家的兴衰而废弃。

## 3. 关键能力

- 丰富的可微分图像处理算子：几何变换、滤波、色彩空间、增强
- 几何视觉算法：单应/基础矩阵估计、相机模型、畸变与校正
- 全部算子基于 PyTorch 张量，天然支持批处理、自动求导与 GPU 加速
- 可与现有训练流水线直接拼接，不要求改写模型结构
- 完整文档、教程、示例与活跃的社区维护
- Apache-2.0 许可，商用与二次分发无授权障碍

## 4. 架构与实现

定位清晰：不做模型、不做训练循环，只做算子。每个算子尽量保持「纯函数 + 张量进张量出」，因此可以嵌进任意计算图，也可以单独在推理阶段调用。代价是它与 PyTorch 的版本演进绑定较紧——算子依赖底层 API，框架变动会传导过来。另一个取舍是性能：为了可微与通用性，部分算子不会用上手写的 CUDA kernel 快，热点路径仍需自己优化。

## 5. 上手路径

1. 把它当算子库而不是框架：按需调用单个变换，不要为了用它而重构整条流水线
2. 批处理维度要显式检查——多数算子约定 B×C×H×W，混入非批数据时容易出错但不报错
3. 涉及几何变换时注意坐标系约定（像素中心与归一化坐标），这是踩坑最集中的地方
4. 训练与推理使用同一套算子，避免「增强用 Kornia、部署用 OpenCV」导致的行为差异

## 6. 风险与边界

- 算子覆盖广但深度不均，冷门几何算法的问题响应速度不如主流图像变换
- 依赖 PyTorch 版本演进，升级框架时需同步验证算子行为
- 为通用性牺牲了部分性能，高频热点仍需自写 kernel
- 坐标与归一化约定不统一的历史包袱仍在，跨算子组合时要逐一对齐
- 文档以英文为主，几何部分的数学约定需要读源码确认

## 7. 谁该用 / 谁别碰

做计算机视觉训练流水线的工程师、需要端到端可微几何估计的研究者，以及要把图像预处理搬上 GPU 以消除 CPU 瓶颈的团队。
