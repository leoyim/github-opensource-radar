## 1. 它解决什么问题

免费额度这件事的实际摩擦不在「有没有」，而在「怎么用得不越界」：每家 provider 有自己的模型名、限流窗口、配额口径，多接一家就多一套 key 管理与重试逻辑，很容易在某个 key 上悄悄超额然后整条链路失败。freellmapi 把这层收敛成一个 OpenAI 兼容端点：统一鉴权、统一模型标识、按请求挑当前可用的模型、遇到限流自动切下一家，并按 key 记录用量，让「还剩多少」变成可查的数字而不是猜。

## 2. 为什么是现在

47,070 星、196 天，本轮 +688。它对应的是一个真实的成本结构变化：模型能力在收敛，价格战让免费层变得足够可用，于是「先用免费额度把原型跑通」成了默认路径。而聚合层恰好是这条路径上最脏的一段活——34 家 provider、635 个端点的手工维护没有技术含量但不能出错，谁把它做成基础设施，谁就拿到入口。

## 3. 关键能力

- 单一 OpenAI 兼容 /v1 端点，chat、embedding、image、audio 统一入口
- 聚合 34 家 provider 的免费额度，共 635 个免费模型端点，可浏览 474 个模型族的目录
- 路由器按请求选择当前最优可用模型，遇限流自动故障转移到下一家
- 按 key 维度统计用量，用于踩住各家不同的免费上限
- 支持接入任意自定义 OpenAI 兼容端点，不局限于内置清单
- 密钥加密存储，不在配置里明文落盘

## 4. 架构与实现

结构上是「适配器 + 路由 + 计量」三层：每家 provider 一个适配器把异构 API 抹平成 OpenAI 形状；路由层持有各家的健康状态与剩余额度，按成本与可用性排序；计量层为每个 key 累计 token 并做阈值控制。真正的复杂度不在代码而在数据——635 个端点的模型名、上下文长度、限流规则会持续变化，维护成本是这类项目的隐性负债。故障转移设计得务实：它不追求最优模型，只追求「这次请求别失败」。

## 5. 上手路径

1. 先读作者的定位——仅供个人实验，别直接接生产流量，尤其别接有 SLA 承诺的业务
2. 为每个上游 provider 单独建 key 并留出余量，聚合层的价值一半来自配额隔离
3. 把路由的故障转移日志打开，否则限流发生时你只会看到「变慢了」而不知道换了哪家
4. 自定义端点接入前先用小请求验证返回结构，OpenAI 兼容往往只是「大致兼容」

## 6. 风险与边界

- 免费额度的可用性由上游单方面决定，模型下线、限流收紧、条款变更都不受本项目控制
- 聚合多家 ToS 的合规边界需要自行核对，商业使用尤其不能默认继承「免费」二字
- 按 key 计量只是自测口径，与 provider 侧的计费口径可能存在偏差，不宜作为结算依据
- 单点聚合意味着它挂掉时所有上游同时不可用，反而放大了可用性风险
- 密钥虽加密存储，但聚合层天然握有全部 provider 的凭证，部署位置的信任成本要自己评估

## 7. 谁该用 / 谁别碰

做原型验证与个人项目的开发者、需要低成本对比多家模型输出的研究者，以及给内部工具接一层「够用就行」的推理入口的小团队。
