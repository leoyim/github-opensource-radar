> **一句话**：结构优先、像素按需：默认只给语义树，要坐标和截图时才打开布局与渲染。

## 1. 它解决什么问题

agent 抓网页的成本结构一直很别扭：真实浏览器要完整排版、加载字体与图片、执行脚本，才能产出一张截图；而 agent 真正需要的往往只是「页面上有哪些可交互元素、它们之间什么关系」。为了拿这点信息渲染整页，代价是内存、时间和不稳定性。moli 把渲染拆成两档：默认只构建语义树，布局与绘制按需开启，需要坐标、截屏或 PDF 时再打开。

## 2. 为什么是现在

22,449 星、86 天，本轮 +229。它与同一天入选的 keploy 指向同一个方向——「替 agent 观察世界」这一层正在被重写。上一代方案是把无头浏览器整套塞进容器，问题是不透明、重、且难以做资源控制；新一代方案从协议层下手：moli 一个端点同时说 CDP、WebDriver Classic 与 BiDi，输出直接给 Markdown 或模型友好的语义树，把「给 agent 用」当成第一等需求而不是事后适配。

## 3. 关键能力

- 按需布局与渲染：默认不排版，节省内存与时间；需坐标或图像时再开启
- 同一端点支持四种接入协议：CLI、CDP、WebDriver Classic、WebDriver BiDi
- 多种导出格式：Markdown、semantic_tree_text（模型友好的紧凑语义树）、视口截图、整页截图、分页 PDF
- --eval 在页面就绪后执行表达式，等待 Promise 与后续导航，再执行导出，适合「点开再抓」的交互场景
- 资源策略、代理、profile、等待策略与 tracing 均可通过参数控制
- Rust 实现，Linux / macOS / Windows 三平台预编译二进制

## 4. 架构与实现

核心是把浏览器内核切成「结构层」与「呈现层」两个可独立启用的部分。结构层负责 DOM、CSS 计算与语义抽取，产出紧凑的语义树；呈现层才做真正的布局与绘制，用于坐标命中、截图与 PDF。`moli serve` 按需叠加能力：基础模式只做 DOM 优先的工作负载，`--layout` 打开几何与输入，`--resource` 才抓图片、字体、音视频。这种分层让资源占用与任务复杂度对齐，也让「只要文本」的场景不必为一个截图付出整页渲染的代价。代价是语义树与真实渲染之间存在偏差窗口——需要精确坐标时必须显式开布局。

## 5. 上手路径

1. 先用 `moli fetch --dump semantic_tree_text` 验证目标站点的可抽取性，再决定是否需要 `--layout`
2. 需要精确点击或坐标时务必开 `--layout`，否则几何信息不可信
3. 把 `--wait-until done` 与 `--wait-selector` 配合使用，单靠固定延时在动态站点上不可靠
4. 用 `moli serve` 承载长时间会话，避免每次 CLI 调用重建上下文

## 6. 风险与边界

- 语义树与真实渲染不一致时，基于语义树的判断可能在像素层面失效，需要显式开布局复核
- 资源策略默认偏保守，漏抓图片/字体可能导致截图与真实观感不符
- 86 天的新项目，526 个 open issue 说明使用面扩张快于问题收敛，生产接入需评估响应节奏
- 文档以英文为主，部分高级参数（profile、resource policy、tracing）说明分散在 --help 中
- 多协议兼容（CDP / WebDriver）是卖点，但各协议的覆盖度并不完全对称，跨协议切换要实测

## 7. 谁该用 / 谁别碰
