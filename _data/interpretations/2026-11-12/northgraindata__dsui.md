## 1. 它解决什么问题

一次日常排障常常横跨 Airflow、dbt、数仓与若干数据库：在四个控制台之间切换、把上下文靠人脑拼起来。既有的每个工具都在自己的领域里够好，缺的是把它们串起来的那一层，而不是再换一套平台。

## 2. 为什么是现在

81 天 36 星、1 fork，却有 22 个 issue，是本榜星标最低的项目之一，日增 0。它与本期其他数据项目共同呈现一个特征：低星、真实工程、目标窄；而「AI 原生控制平面」这种命名与它克制的实际定位之间，值得读者自己分辨。

## 3. 关键能力

- 通过 adapters 连接已有数据工具，统一查看基础设施、执行服务操作
- 典型动作包括查失败 DAG 或失败的 dbt run、检查表与跑查询、确认服务健康
- DSUI Agent 可在一次会话里跨多个已连接服务排查，把上下文拼在一起
- 插件与 SDK 扩展能力，Docker 部署示例配 dsui.yaml 与数据卷，另有 DuckDB 工作区示例
- 提供自托管部署、遥测说明与可选的 DSUI Cloud；README 明确不替代任何现有工具

## 4. 架构与实现

TypeScript 控制平面以 adapter 契约对接各服务，提供一个本地 Web 工作区承载日常操作与 Agent 会话；容器化部署，配置集中于 dsui.yaml。设计上把原生能力留在 L1、业务放 L2、扩展走插件契约。Apache-2.0 许可。

## 5. 上手路径

1. 用 Docker 起服务并挂载写好的 dsui.yaml，先只接一个只读的 DuckDB 或 ClickHouse 适配器
2. 试一次跨服务提问（例如「哪个 DAG 失败、对应表是否更新」），观察 Agent 如何拼接上下文
3. 按实际栈补齐适配器，并逐一核对每个连接所用凭证的最小权限
4. 需要新能力时再写插件或 SDK 扩展，同时确认遥测与 Cloud 的边界

## 6. 风险与边界

- 36 星、1 fork 却积累 22 个 issue，采用面很小且问题集中，关键路径需自行验证
- 控制平面需要持有多个服务的凭证，权限、审计与密钥轮换必须在设计阶段就定好
- 实际价值完全取决于适配器覆盖度，未适配的工具仍是孤岛
- 「AI 原生」是产品定位，跨服务排查结论仍需人工复核，不宜据此自动执行变更
- 自托管与 Cloud 的遥测、功能边界不同，部署前需读相应章节
