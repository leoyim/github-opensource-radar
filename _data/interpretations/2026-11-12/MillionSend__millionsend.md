## 1. 它解决什么问题

接了托管邮件 API 之后，发送能力、送达数据与用量账单都绑在供应商侧；想收回自托管，往往要连 SDK、Webhook 与模板一起重写。另一头，自建发送服务又容易在滥用邮件与信誉上翻车，缺的是一条既能低成本迁移、又把风控做成可选项的路径。

## 2. 为什么是现在

90 天、日增仅 +2，属本期低热项目，入榜靠的是 API 兼容这条明确的工程取舍而非热度。在本期多数前端项目都围绕「本地优先 / 零依赖」做文章时，它是少数把重点放在「换供应商的成本」上的作品。

## 3. 关键能力

- Resend 兼容 API：现有集成迁移只需改 base URL 与 key 两个环境变量，不需重写调用代码
- 自托管模式直接使用自己的 AWS SES；提供 Docker 一条命令启动，空目录即可起服务
- 托管侧可选的滥用判定：新团队首个窗口内的邮件与其广播、以及任何团队发往从未用过的目的地的邮件在 SES 接收前评分并等待判定（约半秒），其余发后抽样，发送不等待
- 判定开关 ABUSE_JUDGE=typesafe 由自托管者自行决定，默认关闭
- TypeScript / Hono.js 实现，AGPL-3.0 许可，社区与文档入口集中在 README

## 4. 架构与实现

TypeScript 服务层对上暴露 Resend 兼容的 HTTP 接口，对下对接 AWS SES；环境变量决定凭据、判定开关与部署形态。托管侧的评分模型为可选前置环节，判定失败时不影响其余邮件的正常发送路径。

## 5. 上手路径

1. 在空目录执行 README 给出的一条命令启动服务，先确认容器与端口可用
2. 填入自有 AWS SES 凭据、已验证域名与发信地址
3. 把现有 Resend 集成的两个环境变量改指向新服务，发一封测试邮件验证请求与 Webhook
4. 按业务风险决定是否开启 ABUSE_JUDGE，并持续观察退信与投诉指标

## 6. 风险与边界

- 自托管 SES 后，退信、投诉、发送配额与 IP 信誉都成为自己的长期运维工作，部署完成只算开始
- AGPL-3.0 对以服务形式提供有较强要求，商用前需评估许可影响
- 滥用判定默认关闭且依赖第三方模型，误判与漏判的影响需自行评估；开启后新目的地邮件会多约半秒等待
- 「改两个环境变量」覆盖的是发送 API，模板、Webhook、域名验证与统计口径未必完全等价，迁移前应逐项核对
- 90 天仅 9 个 issue、日增 +2，社区验证与长期维护节奏有限
