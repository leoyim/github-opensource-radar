# vercel-labs/json-render · 项目解读

> **一句话**：让模型只输出受组件目录与 schema 约束的 JSON，再把这份 JSON 渲染成界面。

## 1. 它解决什么问题

让模型直接生成界面代码，输出不可控：组件可能不存在、结构每次不同、也无法安全地流式渲染。更实际的做法是把「能用哪些组件」与「输出长什么样」变成开发者侧的硬约束，模型只负责在这套约束里填内容；同时还要让同一套约束能用在 Web、移动、文档与视频等不同渲染目标上，避免为每个目标重写一遍。

## 2. 为什么是现在

项目 298 天、19,457 星，本期 +149 为前端方向日增第一，1,030 fork。它把生成式 UI 从演示性能力推到了工程约束层：Guardrailed、Predictable、Fast 三条被写在特性最前面，而不是先谈效果。README 一口气列出 React、React Native、视频、PDF、HTML 邮件、终端与 3D 场景等多个目标，说明近期需求已从「生成一张卡片」转向「同一份规格多处渲染」。

## 3. 关键能力

- 组件目录限定：模型只能使用开发者登记在 catalog 中的组件与动作
- JSON 输出始终匹配既定 schema，结果可预测、可校验
- 随模型响应流式渐进渲染，不必等完整输出
- 同一组件目录可输出到 React、Vue、Svelte、Solid、React Native、视频、PDF、HTML 邮件、终端 UI、Next.js 应用与 3D 场景
- 内置 36 个可直接使用的 shadcn/ui 组件
- 规格表达式支持 $state 读取状态模型、$cond/$then/$else 条件分支、$template 字符串插值

## 4. 架构与实现

TypeScript 实现、Apache-2.0 许可，按核心包与渲染目标拆分为多个安装包（README 针对不同目标分别给出 npm install 组合）。README 章节几乎按输出目标逐节组织，最后以 Why json-render? 收束设计理由；关键取舍是把生成边界放在目录与 schema 两层，渲染层保持确定性，因此流式输出与跨平台复用都能成立。仓库 129 个 open issue，说明多目标适配仍在持续收敛。

## 5. 上手路径

1. 先按目标平台对应的 README 分节安装核心包与渲染包
2. 定义一份最小组件目录，只登记两三个组件，确认模型输出不会越界
3. 用 $state 与 $cond 写一条带状态与分支的规格，验证渲染结果
4. 需要跨端复用时再扩展到第二个渲染目标，并核对同一份 catalog 的一致性

## 6. 风险与边界

- 能力上限由组件目录决定，目录外的界面需求仍需开发者先扩展组件
- 多渲染目标意味着同一份规格在不同端的表现需分别验证，不能假定完全等价
- schema 表达式（$state、$cond、$template）引入了一层自定义语义，团队需要额外约定与文档
- 输出依赖模型遵循规格，仍应在渲染前做校验，不宜把「符合 schema」当作免检前提

## 7. 谁该用 / 谁别碰

需要在产品里让模型生成界面、但要求组件与结构完全可控的前端团队；以及希望一份规格同时输出到 Web、移动与文档等多处的场景。若界面完全由人工设计、没有动态生成需求，这套约束层反而增加复杂度。
