## 1. 它解决什么问题

设计系统常见的两难是：封装得严，业务方要改一处样式就得层层包裹或提 PR 等上游；开放得松，团队又各自实现一套按钮，约定形同虚设。当编码代理开始直接生成界面时，这个矛盾更明显——代理读不到隐含的设计约定，只能猜组件怎么拼。Astryx 要解决的正是「既给足能力，又不把人锁在封闭 API 里」。

## 2. 为什么是现在

项目 303 天、16,928 星，本期 +875 为全榜日增第一，pushed_at 就在采集当日。它由 Meta 内部使用八年的体系开源而来，README 称支撑过 13,000 余个应用，属于少见的「先在超大规模内部验证、再对外发布」的设计系统。更值得注意的是它把 agent ready 写进了一句话定位：API、约定、文档与 CLI 一起设计，明确承认组件的主要读者已不只是人。

## 3. 关键能力

- 组件可在任意层级组合，构建块不被封闭的顶层 API 屏蔽
- 样式不锁定：内部用 StyleX 实现，但消费方可用 className、Tailwind 或 CSS Modules 覆盖
- 主题通过一组 CSS 自定义属性覆盖值定义，无需额外包装组件
- API、文档与 CLI 按同一套约定设计，人和 AI 助手走同一条构建路径
- 以「指导优于强制」为原则，设计判断放在文档与示例里，而不是用运行时约束挡住使用者
- 每个组件遵循统一的命名、属性与组合规则，并有完整文档；约定以测量结果而非断言为依据

## 4. 架构与实现

TypeScript 实现、MIT 许可。README 章节依次为 Overview、Getting Started（分别给出 npm、pnpm、yarn 安装）、Packages、Principles、Architecture、Foundations、Components、Patterns、Project Structure、Contributing，说明它是一个按「基础层 → 组件 → 模式」组织的组件库而非单一包。关键取舍有两处：一是把可组合性放在封装强度之前，二是把样式实现（StyleX）与消费接口解耦，主题落在 CSS 变量层。仓库 1,332 fork、651 个 open issue，说明已进入真实协作阶段。

## 5. 上手路径

1. 按 Getting Started 章节选择 npm、pnpm 或 yarn 安装对应包
2. 先照 Packages 与 Foundations 确认基础层与主题变量的覆盖方式
3. 用一个现有页面替换单个组件，验证 className 覆盖是否不需要额外包装
4. 阅读 Principles 与 Patterns，把项目的命名与组合约定对齐后再批量迁移

## 6. 风险与边界

- 设计取向来自 Meta 内部场景，组件约定与既有团队规范可能不一致，迁移前需评估改造成本
- 强调开放可组合意味着约束更少，若团队缺少统一评审，反而更容易出现多套写法
- 主题依赖 CSS 自定义属性覆盖，深度定制时需要对变量体系有整理解
- README 明确主张用实测检验约定，部分设计结论可能随版本调整，升级时需回归验证

## 7. 谁该用 / 谁别碰

需要一套可深度定制组件库、且已有编码代理参与前端产出的团队；以及希望组件约定可被文档与 CLI 一致表达的平台组。若只需要一组开箱即用的标准控件、无意自定义，采用成本可能高于收益。
