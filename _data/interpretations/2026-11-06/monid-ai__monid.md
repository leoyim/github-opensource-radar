## 1. 它解决什么问题

给 agent 接外部能力时，每家供应商都要单独申请密钥、读一套鉴权与限流规则、写一份返回结构适配，还要自己记账。工具数量一多，接入成本不再是写一次代码，而是长期维护几十份彼此不同的适配层；代理侧还得知道每个工具该传什么、会返回什么。

## 2. 为什么是现在

项目 72 天、6,130 星，本期以速度估算热度约 584，位居无基线项目第二。它借用了 OpenRouter 已被验证的心智模型，但把对象从模型换成了工具——这类「统一网关 + 声明式描述」的形态，正对应近期 agent 应用从接一两个模型转向接一批外部能力的趋势。

## 3. 关键能力

- 一个 base URL 与一把 key 触达 72 家以上供应商的 2000 多个工具
- 覆盖网页搜索与抓取、人物与公司信息补全、社交平台、评论与市场数据
- 覆盖视频、图像与语音生成类能力
- 连接器为声明式描述：定义调用方式、入参、返回结构与用量计量
- 把 API 文档与本仓库一起交给编码代理，新增工具接入可沉淀为一次 PR

## 4. 架构与实现

TypeScript 实现、MIT 许可，仓库定位是连接器层而非代理框架或网关服务本身：它用统一的声明式 schema 描述海量端点，把「怎么调、收什么、回什么、怎么计费」从各家 SDK 收敛成一种格式。这个设计让扩展工作变成写描述文件，且描述本身能被编码代理读取和生成，因此贡献门槛远低于传统适配器开发。托管服务的实现细节不在 README 摘录范围内，需以官方文档为准。

## 5. 上手路径

1. 先按 Quickstart 用一个常用工具（如网页搜索）跑通鉴权与返回结构
2. 检查目标工具的计量规则，明确一次调用的计费口径再放量
3. 对照现有 API 文档为缺失工具补一个声明式连接器，走 PR 流程验证扩展路径
4. 在代理侧统一处理错误与限流，不要把各供应商的差异泄漏到业务逻辑

## 6. 风险与边界

- 统一网关意味着所有外部调用集中在一个密钥上，密钥权限与轮换策略需要重点设计
- 2000 多个工具的质量、稳定性与数据合规由各供应商分别负责，网关不为其背书
- README 摘录以导航和定位为主，计费、SLA、数据留存等条款需另行确认
- 连接器由社区声明式贡献，字段准确性需要在使用前抽查

## 7. 谁该用 / 谁别碰

正在给 agent 批量接入搜索、数据补全、生成类能力，且不愿维护几十份供应商 SDK 的应用开发者。
