## 1. 它解决什么问题

AI 生成代码变快之后，提交者未必理解自己推上去的改动；而 lint 与测试只检查代码是否合规，不检查人是否说得清边界条件、失败模式与验证方式。

## 2. 为什么是现在

项目 46 天、373 星、55 fork，热度为速度估算（约 45），评分 2.5 为本期较低档。它把「AI 写代码、人负责解释」这条常见争议直接做成可执行的 git hook，是本期工具方向里观点最鲜明的一件。

## 3. 关键能力

- 读取当前 diff 生成针对性提问，覆盖为何这样实现、哪里会失败、恶意调用者能做什么、如何验证
- 支持终端与浏览器白板两种作答形式
- 由模型按 100 分制评分，低于团队设定分数线则阻止 push
- 兼容 Claude Code、Codex、Cursor 等编码代理
- 把可解释性要求固化进提交流程，而非依赖口头约定

## 4. 架构与实现

Python 实现、BSD-3-Clause 许可，以 git hook 卡在 push 之前，问题生成与评分都走模型调用，因此评分质量取决于所用模型与提示设计，且每次推送都会引入一次外部调用。取舍是有意让流程变慢，用可解释性换提交信心；README 也明确写出「它检查的是开发者，不是代码」，这与 lint、测试是互补而非替代关系。

## 5. 上手路径

1. 在个人分支先装 hook 跑一次，看提问是否贴合实际改动
2. 设定一个宽松的通过线，观察一周内的误伤率
3. 确认模型调用的密钥流向与 diff 数据策略
4. 再决定是否以团队约定形式小范围推广

## 6. 风险与边界

- 评分由模型给出，主观且不稳定，可能阻塞正常提交
- diff 会发送给模型服务，涉及私有代码时需先确认数据策略
- 给 CI 与自动化推送增加不确定的延迟与失败点
- 推广阻力主要来自流程体验，而非技术实现

## 7. 谁该用 / 谁别碰

已大量使用 AI 生成代码、希望强化人工复核纪律的研发团队。
