## 1. 它解决什么问题

传统端到端测试把每一步操作写死，UI 一改测试就碎；完全用自然语言描述测试，又很难给出确定断言与清晰的失败定位。两种做法之间缺一个可控的中间形态。

## 2. 为什么是现在

项目 107 天、13,332 星、693 fork，本期 +193，是有当日基线的项目里增量第四高。它与本期 AI 方向的 agent skills、OpenSpec 一起，反映「代理负责执行、确定性规则负责校验」正在成为测试与开发流程的共同结构。

## 3. 关键能力

- 面向 Web 与移动应用的端到端测试
- 用自然语言描述目标，由 agent 驱动应用达成该目标
- 同一次测试里保留 locator 与断言，用确定性校验收口
- TypeScript 编写用例，README 给出结算升级等场景示例
- 标签关联 Playwright 等既有测试生态

## 4. 架构与实现

TypeScript 实现、Apache-2.0 许可，把「怎么走」交给代理、「有没有走到」交给断言层，因此 UI 路径变化不必然导致用例改写。取舍是用执行期的不确定性换维护成本，代价是可重现性、运行时长与模型调用成本都需要新建约束。README 摘录只给出一段示例代码，代理配置与运行机制需查项目文档。

## 5. 上手路径

1. 用一个稳定的登录或结算流程写第一条用例
2. 把关键状态用显式断言固定，避免全部依赖代理判断
3. 在本地与 CI 各重复运行几次，比较耗时与结果一致性
4. 再评估失败回放与日志是否足以定位问题

## 6. 风险与边界

- 代理执行路径不确定，偶发失败与可重现性需要额外机制
- 每次运行可能引入模型调用成本与额外延迟
- 对外部模型服务的依赖会影响 CI 稳定性
- README 摘录信息有限，接入前应补读文档与源码

## 7. 谁该用 / 谁别碰

UI 变动频繁、维护大量端到端用例且已在引入代理的前端与测试团队。
