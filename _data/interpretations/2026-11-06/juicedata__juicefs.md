## 1. 它解决什么问题

对象存储便宜、容量近乎无限，但它不是文件系统，现有程序不能不改代码直接读写；大数据与模型训练又需要多客户端共享、强一致的 POSIX 视图，两者之间存在一道明显的落差。

## 2. 为什么是现在

项目 2,128 天、14,683 星、1,347 fork，本期 +18，是本期年龄第二长的项目。在 agent 工具与前端框架密集出现的一期榜单里，这类仍在稳定增长的老牌存储基础设施，反映数据与训练侧的底座需求并未被新工具替代。

## 3. 关键能力

- 完整 POSIX 兼容，可像本地文件系统一样挂载使用，现有应用无需改代码
- 文件数据持久化到 S3 等对象存储
- 元数据可接入 Redis、MySQL、TiKV 等数据库引擎
- Hadoop Java SDK 兼容 2.x 与 3.x 生态，另提供 S3 网关
- 提供 Kubernetes CSI Driver，支持成千客户端共享读写与强一致

## 4. 架构与实现

Go 实现、Apache-2.0 许可，核心取舍是数据与元数据分离：文件数据走对象存储换取容量与成本，元数据走独立数据库换取低延迟与强一致，客户端负责把 POSIX 语义翻译到两者之上。好处是业务无侵入，代价是元数据引擎成为整体可用性与性能的关键依赖，运维重心也随之从存储容量转向数据库。

## 5. 上手路径

1. 用本地 Redis 加任意 S3 兼容存储跑通最小部署
2. 挂载后把现有程序接进来做一次读写回归，确认 POSIX 行为
3. 针对小文件与元数据密集操作做压测，观察数据库负载
4. 再评估 CSI Driver 接入 Kubernetes 后的运维与升级方式

## 6. 风险与边界

- 元数据服务的可用性直接决定整体可用性，需按生产标准做高可用
- 小文件与大量随机元数据操作会给数据库带来明显压力
- 对象存储的请求费用与访问延迟会直接体现在文件访问上
- 跨版本升级需核对客户端与元数据格式的兼容性

## 7. 谁该用 / 谁别碰

需要在云原生环境里给大数据分析、模型训练或既有应用提供共享文件视图的平台与数据团队。
