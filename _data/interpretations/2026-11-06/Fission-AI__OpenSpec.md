## 1. 它解决什么问题

直接让代理改代码，最容易出问题的不是写错语法，而是没看清项目既有结构就给出一套自洽但格格不入的方案。规格驱动若做成重型流程，又会退回瀑布式文档；尤其是存量项目，既有约束多、边界模糊，代理往往默认按新建项目的假设推进。

## 2. 为什么是现在

项目 458 天、74,066 星，本期 +111，是本期 AI 类里星标最高者。它把「先探索、后圈范围」做成显式命令，并以暗色模式这种典型存量改动作示例，恰好回应了近期规格驱动开发（SDD）从概念走向可操作命令的转向。

## 3. 关键能力

- 为 AI 编码助手提供规格驱动开发（SDD）工作流
- 以 /opsx:explore 等命令先探索需求与现有实现，再确认改动范围
- 明确面向存量代码（brownfield）而非仅新建项目
- 支持从个人项目扩展到企业规模的迭代式流程
- 示例中助手先查看样式结构，再给出不引入新依赖的最小方案

## 4. 架构与实现

TypeScript 实现、MIT 许可，交付形态是一组作用于编码助手的规范与命令，而非独立 IDE 或编译器。设计原则在 README 摘录里被写成五组对照：流动而非僵化、迭代而非瀑布、简单而非复杂、面向存量而非仅新建、可从个人扩展到企业。核心机制是把「同意做什么」从隐含假设变成对话中的显式确认点，示例里的 dark mode 讨论展示了先读现有样式、再 Scope it? 的收敛过程。

## 5. 上手路径

1. 在现有项目里对一个小改动试跑 /opsx:explore，观察它是否真的先读了代码
2. 确认范围时明确拒绝不符合项目约束的方案，检验其收敛质量
3. 把团队既有约定写进规格，让探索阶段能读取到
4. 逐步从单人小改动扩展到多人协作，观察流程是否变重

## 6. 风险与边界

- 流程收益依赖代理是否忠实执行探索步骤，不同助手表现可能不一致
- 规格驱动若在团队里被当成必填文档，容易退回它试图避免的瀑布式负担
- README 摘录仅 543 字符，命令全集与配置方式需查阅仓库文档
- 「不引入新依赖」一类结论来自示例对话，不能当成所有场景的默认约束
