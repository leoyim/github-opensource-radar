## 1. 它解决什么问题

多数 agent 客户端把产出留在对话流里，用户要自己复制、粘贴、再整理；一旦任务跨多轮、跨文件，过程与产物就混在一起，无法审计也无法继续加工。

## 2. 为什么是现在

126 天、3,045 星、433 fork，Rust、MIT。它把工作、设计与编码放进同一个桌面工作台，工件面板自动收集 agent 创建或修改的每个文件，Markdown 工件可直接编辑，也可选中段落让 agent 改写。

## 3. 关键能力

- 多会话工作台：消息、工具调用与工件随会话持久化，支持标题检索
- 工件面板：自动汇总 agent 产出的文件，可预览、定位、一键打开
- 可编辑 Markdown 工件：直接改，或选中一段交给 agent 重写
- Plan / YOLO 双模式：复杂任务先审计划，明确任务直接执行
- 旁路会话：任务运行中可开只读副会话提问，服务端强制只读
- ACP 接入专业编码 agent，在真实项目里协作

## 4. 架构与实现

Rust 桌面端，围绕会话与工件两个核心对象组织状态；旁路会话在服务端被限制为只读视图，避免副会话越权修改主任务状态；编码能力通过 ACP 协议外接专用 agent，而不是内置一套。

## 5. 上手路径

1. 先用 Plan 模式跑一个两步骤任务，检查计划是否可编辑、可中断
2. 拖入一份 PDF 与一个表格，确认附件解析与工件面板的收集是否完整
3. 在 Markdown 工件上试一次「选中段落让 agent 改写」，验证局部修改不污染全文
4. 需要并行提问时开旁路会话，确认它只能读、不能改

## 6. 风险与边界

- 126 天的新项目，跨平台打包与 ACP 协议演进会带来升级成本
- 工件自动收集会放大误写风险，需配合版本控制使用
- Plan 模式依赖模型对任务粒度的判断，过细的计划反而拖慢短任务
- 433 fork 属健康区间，但生态与插件仍依赖单一团队

## 7. 谁该用 / 谁别碰

交付物是文档、设计稿或代码改动的知识工作者；希望 agent 产出可直接进入既有工程流程的开发者。
