## 1. 它解决什么问题

Go 做桌面长期卡在两头：纯 webview 方案启动慢、内存高，绑定原生控件的方案又常依赖 cgo，交叉编译变成手工活。团队往往被迫在项目级二选一。

## 2. 为什么是现在

61 天、6,940 星、458 fork、日增 +54，MIT。一个窗口可以是网页（走系统自带 WKWebView / WebKitGTK / WebView2），也可以是 package ui 在 GPU 上绘制的原生界面，同一应用内可混用；纯 Go、无 cgo，可从任意机器交叉编译。

## 3. 关键能力

- 双界面模式：webview 网页与原生 UI 可按窗口混用
- 原生绘制：package ui 提供 flexbox / grid 布局、控件与文本渲染
- 纯 Go 无 cgo：跨平台交叉编译不再需要目标平台工具链
- 类型化 IPC：从 Go 服务生成 TypeScript 客户端，页面调用有类型
- 顺带覆盖移动端：同一应用可跑 iOS 与 Android，页面走各自 webview

## 4. 架构与实现

Go 运行时负责窗口、事件循环与服务注册，前端通过生成的 TS 客户端经 IPC 调用 Go 服务并接收 channel 流；原生路径不经过 HTML，由框架直接做布局与绘制，因而启动与内存表现更接近原生应用。

## 5. 上手路径

1. 先用 webview 模式跑通窗口与一次 TS→Go 调用，确认 IPC 生成链路
2. 把同一窗口改成原生 UI，对比启动时间与内存占用，判断是否值得
3. 交叉编译到第二个平台，验证无 cgo 的实际收益
4. 原生界面先只做核心控件，复杂表格仍用 webview，避免过早踩控件覆盖不足

## 6. 风险与边界

- 61 天的新框架，原生控件在表格、富文本、无障碍上覆盖有限
- 两种渲染路径意味着两套调试方式，团队需要同时掌握
- webview 行为随系统版本变化，Windows 依赖 WebView2 运行时
- 6,940 星属早期高热，API 稳定性尚无长期验证

## 7. 谁该用 / 谁别碰

希望用 Go 统一后端与桌面端、又在意启动速度与内存的团队；需要跨平台交叉编译的独立开发者。
