## 1. 它解决什么问题

定制简历的收益明确，但生成式工具最大的问题是会补写不存在的经历；一旦带进面试，代价由求职者承担。另一头是隐私——履历与投递记录散落在第三方服务里。

## 2. 为什么是现在

54 天、5,517 星、1,148 fork、日增 +12，TypeScript、AGPL-3.0。它把「可用事实」限制在用户录入的档案内，按岗位读取招聘描述、给出匹配度，再生成简历与求职信；数据落自己的 PostgreSQL 或单个 SQLite 文件，模型可走本地 Ollama / LM Studio。

## 3. 关键能力

- 结构化档案：基本信息、技能语言、经历、志愿、项目、教育、证书、发表与推荐人
- 基础简历：12 套主题加主题构建器，服务端实时预览并打印 PDF
- 岗位匹配：读取招聘描述，给出与档案的匹配度与差距
- 定制生成：只用档案事实写简历与求职信，可在对话中修改后导出 PDF
- 投递追踪：从草稿到 offer 全流程记录
- 本地模型优先：Ollama / LM Studio，或任意 OpenAI 兼容接口
- 岗位代理：最多保存三个命名搜索并定时运行

## 4. 架构与实现

TypeScript 全栈，Next.js 前端加服务端 PDF 渲染；存储支持 PostgreSQL 与 SQLite 两种后端，便于单机部署；模型层抽象为 OpenAI 兼容接口，本地与云端可切换；配套 Docker 与 CapRover 部署路径。

## 5. 上手路径

1. 先完整录入一份档案，重点补齐可量化的事实，生成质量取决于这层
2. 用本地模型跑一次定制，逐句核对是否有档案里不存在的内容
3. 接一条真实岗位做匹配，检查差距分析是否给出可执行建议
4. 部署在自有服务器上时，先确认备份策略，SQLite 单文件要单独纳入备份

## 6. 风险与边界

- AGPL-3.0 对商用二次分发与网络服务有约束，企业采用前需评估
- 依赖招聘站点抓取，接口变更与反爬会直接影响可用性
- 本地小模型的写作质量与事实约束能力弱于云端大模型
- 档案集中存放全部履历，单机部署需自行处理磁盘加密与访问控制

## 7. 谁该用 / 谁别碰

对履历隐私敏感、愿意自托管的求职者；需要批量定制投递但不愿承担编造风险的职场人。
