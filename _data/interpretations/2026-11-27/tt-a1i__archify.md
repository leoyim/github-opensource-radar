## 1. 它解决什么问题

架构图与方案说明通常是静态图片，读者无法追问，作者也无法证明图上的结论来自哪段代码；换一个 agent 重画一遍，来源就彻底断了。

## 2. 为什么是现在

226 天、100,593 星、6,885 fork、日增 +663，JavaScript、Apache-2.0。产出是单个 HTML 文件，含 10 种图型、架构诊断、Story 视频与 PR 走查，可导出图片或打印 PDF；论断标注编号来源，代码片段钉到具体 commit。

## 3. 关键能力

- 10 种图型覆盖流程、分层、时序、依赖等常见表达
- 结论先行：每块只回答一个问题，答案与理由在前
- 可核查：论断引用编号来源，仓库片段钉到 commit 并可打开源码卡
- Story 模式：为任意图加时间轴与字幕，导出为视频
- PR 走查：把一次变更讲成带图的叙事
- 单文件交付：四种风格、明暗主题，可导出 PNG / WebP / JPG 或打印 PDF

## 4. 架构与实现

以 Agent Skill 形式分发，宿主 agent 负责取数与推理，工具负责版式与交互渲染；输出为自包含 HTML，样式与脚本内联，因此可离线打开、可直接进文档系统。

## 5. 上手路径

1. 先拿一个自己熟悉的仓库生成架构图，对照实际模块划分检查是否有臆造
2. 点开几个节点的源码卡，确认引用确实指向对应 commit 的片段
3. 需要对外分享时用单文件 HTML 或 PNG，避免依赖宿主环境
4. 在长任务里注意上下文预算，图型越多、取数越深，消耗越大

## 6. 风险与边界

- 平台级体量（100,593 星）意味着默认行为可能随版本快速变化
- 图的正确性依赖 agent 对代码的理解，误读会以「看起来很专业」的形式呈现
- 单文件 HTML 便于分发，但大图在低配设备上交互会卡顿
- 引用机制只能证明「取自哪段代码」，不能证明推理本身成立
