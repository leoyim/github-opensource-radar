## 1. 它解决什么问题

开发调试、远程设备维护或临时演示时，服务常跑在没有公网地址的内网里；为这一个需求去申请公网 IP、改路由或搭一整套 VPN 都太重。缺的是一个配置简单、协议覆盖全、并且能按场景选择直连或中转的反向代理。

## 3. 关键能力

- 支持 TCP、UDP 以及 HTTP、HTTPS 协议，可按域名把请求转发到内网服务
- 提供 P2P connect 模式，在特定网络条件下让两端直接建连
- README 给出丰富的示例：SSH 访问内网机器、多个 SSH 服务共享端口、自定义域名访问内网 Web、转发 DNS 查询与 Unix Domain Socket
- 还覆盖暴露简单 HTTP 文件服务、为本地 HTTP(S) 服务启用 HTTPS、以及把服务限定为私有暴露
- 文档含 Development Status、About V2、Architecture 与 Example Usage，便于按版本核对行为

## 4. 架构与实现

Go 实现的客户端/服务端反向代理：frps 部署在有公网地址的节点，frpc 运行在内网侧并按需注册代理规则，控制面协商后转发流量。Apache-2.0 许可，README 篇幅较大，按协议与场景分节给出配置片段。

## 5. 上手路径

1. 在公网节点部署服务端，先只开放一个测试用的 TCP 端口，确认认证与 TLS 配置已启用
2. 内网侧用最小配置注册一个 SSH 代理，验证连通性与断线重连行为
3. 按需要补 HTTP 自定义域名或 P2P 模式，每次只加一种规则并观察日志
4. 上线前把暴露范围、访问白名单与审计日志固定下来，避免长期留下未登记的入口

## 6. 风险与边界

- 把内网服务暴露到公网本质上扩大了攻击面，认证、TLS、白名单与端口回收必须由部署方负责
- V2 相关说明与旧版配置不完全一致，跨大版本升级前需逐项核对配置格式
- P2P 打洞成功率受 NAT 类型与网络环境限制，生产链路应准备中转回退
- 代理规则分散在各客户端配置里，缺少集中台账时容易留下无人认领的入口
- 内网穿透在部分组织与网络环境下有合规限制，部署前应确认使用政策

## 7. 谁该用 / 谁别碰

需要远程调试内网服务、维护边缘设备或做临时演示的开发者与运维；也适合作为理解反向代理与 NAT 穿透的教学材料。有正式公网接入规范的生产系统应优先走既有网关方案。
