## 1. 它解决什么问题

前端与 Node 的请求写法长期不统一：拦截器、超时、取消、错误归一、上传进度各有一套，团队容易在不同运行时里写出行为不一致的封装。缺的是一个两边都稳定、配置项足够细、又不必引入整套框架的基础库。

## 2. 为什么是现在

4,469 天的老项目本期仍 +55，是本期 11 个千日以上项目之一。值得留意的是 README 目录里新增了「Security notice: decompression-bomb protection is opt-in」一节——老牌依赖的维护重点已从功能扩展转向明确的安全默认值边界。

## 3. 关键能力

- 同一套 API 覆盖浏览器 XMLHttpRequest 与 Node http 适配器，Promise 化请求与响应
- 请求方法别名、实例化、实例方法、请求配置与拦截器，可统一注入鉴权与错误处理
- 支持取消请求、上传下载进度、超时与响应数据转换，配置项粒度较细
- 可导出与第三方生态集成；README 含 CDN、包管理器安装与大量请求配置示例
- 维护方在文档中明确列出解压炸弹防护为可选开启项，把安全默认值的取舍交给使用方判断

## 4. 架构与实现

JavaScript 实现的无框架依赖 HTTP 客户端，核心是适配器层 + 拦截器链 + 请求配置合并；浏览器与 Node 各自走不同底层传输，但对外暴露同一接口。MIT 许可，README 篇幅很大，含 Features、Browser support、Request config、Concurrency (deprecated) 等章节。

## 5. 上手路径

1. 按所用包管理器安装，先封装一个带 baseURL 与超时的实例，避免每处调用重复配置
2. 在实例拦截器里统一处理鉴权、错误码与日志，明确哪些字段不能写进日志
3. 阅读安全章节，按业务场景决定是否开启解压炸弹防护，并核对重定向与响应体大小限制
4. 对浏览器与 Node 两条路径各跑一组错误与超时用例，确认行为一致

## 6. 风险与边界

- README 标注 Concurrency 相关能力已弃用，新项目不应照旧示例使用
- 解压炸弹防护为 opt-in，处理不可信响应体时默认配置可能不够，需要主动设置
- 浏览器与 Node 适配器的行为差异（如进度事件、代理、cookie）仍需在集成测试中覆盖
- 109,395 星、12,020 fork 的庞大生态意味着升级会影响大量间接依赖，锁版本要谨慎
- 默认配置不等于安全配置，超时、重定向与错误暴露策略需团队自行定义
