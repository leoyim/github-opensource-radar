# stablemates/workhorse · 项目解读

> **一句话**：不要 broker 的任务队列：队列状态、调度、重试、恢复全部由 PostgreSQL 的 SQL 函数承担。

## 1. 它解决什么问题

「数据库写成功但任务没入队」和「任务入队了但事务回滚」这两类不一致，是后台系统的经典难题。传统解法是引入 Redis/RabbitMQ 做队列，再靠 outbox 模式补一致性——多一个中间件就多一套运维、一套监控、一套故障模式。如果队列本身就在同一个数据库里、走同一个事务，这类问题从根上消失。

## 2. 为什么是现在

103 天、176 星，无日增基线——规模很小。但它代表的技术取向值得记：在后端普遍「先上消息队列」的惯性下，把队列做回数据库内部是一种反潮流的简化。支持 TypeScript、Python、Go、Rust、Ruby、Java、Kotlin、C# 八种 worker 共用一套 SQL 协议，说明它不是玩具——多语言一致性恰恰是自制队列最容易翻车的地方。当前处于 public beta，0.x 版本可能有行为变更。

## 3. 关键能力

- 以版本化 SQL 函数实现队列，队列状态、调度、重试、恢复、不可变历史全部由 PostgreSQL 持有
- 入队与业务写入走同一事务，回滚时两者一起撤销
- 八种语言的 worker 共用同一套 SQL 协议：TypeScript、Python、Go、Rust、Ruby、Java、Kotlin、C#
- fence token 机制：丢失租约后恢复的 worker 无法覆盖更新的工作
- 至少一次投递语义，记录持久化进度与结果
- 自带 dashboard，展示任务活动、生命周期事件、系统健康、worker 容量、队列与调度
- 有序迁移，同一大版本内迁移只增不改，支持原地升级

## 4. 架构与实现

核心洞察是「数据库已经是一个可靠的、有事务的、有持久化的调度器」。所有队列操作以 SQL 函数形式存在于库内，worker 通过轮询/长等待认领任务，认领时拿到带 fence token 的租约；任务完成后写回结果，历史表只追加。因为不引入外部 broker，事务一致性与故障恢复都变成数据库的既有能力。代价是吞吐受限于数据库轮询与行锁竞争，高并发场景下 Postgres 会成为瓶颈——这是「简化」必须付的账。

## 5. 上手路径

1. 先压测你的目标吞吐：数据库队列的上限取决于轮询频率与锁竞争，别按消息队列的量级预期
2. 理解 at-least-once 的边界——外部副作用仍需幂等键或补偿，README 对此有明确说明
3. public beta 阶段锁定小版本，升级前读 changelog
4. dashboard 走独立连接与只读账号，别让它和 worker 抢连接池

## 6. 风险与边界

- 吞吐与延迟受数据库限制，高并发任务场景下会成为瓶颈
- public beta，0.x 小版本可能改变行为
- 任务负载会直接压在业务库上，重任务可能影响线上查询
- 至少一次投递意味着必须自行处理重复执行，误以为恰好一次会导致数据错乱

## 7. 谁该用 / 谁别碰

已经有 PostgreSQL、不想再引入消息队列的中小团队、需要跨语言 worker 的后端工程师、以及想把后台任务纳入同一事务边界的开发者。
