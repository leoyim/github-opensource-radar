## 1. 它解决什么问题

Ubuntu 桌面上的日常操作长期处于碎片状态：调音量要一个扩展、改媒体播放要一个、剪贴板历史要一个、查 agent 的调用配额又得另开网页或翻日志。每装一个都是一次 GNOME 扩展版本赌局。Veronica 想做的是把这些收进一个原生窗口：系统工具、媒体控制、剪贴板、emoji、GNOME 集成，外加一个越来越重要的新类目——agent 使用量与速率限制。

## 2. 为什么是现在

75 天、321 星、单日 +123，增量在比例上很突出（接近总量的四成）。它其实是 macOS 上 Edith 那个控制中心的 Linux 移植，README 明确说保留了 Edith 的模型层（能力地图、扩展目录、限流算法、用量 schema），只重写平台层，用量采集器逐行共用。这个细节值得注意：它说明「agent 用量监控」已经成为一个跨平台的产品需求，而不是某个工具的特例——当一个人同时用 Claude Code、Codex、Copilot 时，配额查询确实需要一个统一入口。

## 3. 关键能力

- 系统工具聚合：音量、媒体播放、剪贴板历史、emoji 选择等常用控制
- GNOME 集成，作为原生桌面组件而非网页壳
- agent 使用量与速率限制展示（复用 Edith 的限流算法与用量 schema）
- 单应用内提供全部功能，无许可证密钥、无账号、无付费档
- Rust + Tauri 构建，GPL-3.0 开源

## 4. 架构与实现

Tauri 外壳（Rust 后端 + 前端界面）套 GNOME 服务调用。关键设计是「模型层与平台层分离」：能力地图、扩展目录、限流算法、用量数据结构这些与操作系统无关的部分直接沿用 Edith，Linux 侧只实现读取系统状态、控制媒体、访问剪贴板等平台接口。这种移植策略让功能对齐成本大幅降低，但也意味着某些交互范式是从 macOS 带过来的，在 GNOME 上未必最顺手。

## 5. 上手路径

1. 先确认 GNOME 版本与扩展依赖，Tauri + GNOME 集成的坑主要集中在 Shell 版本差异
2. agent 用量那部分要核对数据来源：它是读本地日志还是调远端 API，前者受文件路径影响，后者受凭据影响
3. 321 星的小项目，别急着替换现有工作流，先并行跑两周看稳定性
4. GPL-3.0，若要集成进自有分发产品需评估条款

## 6. 风险与边界

- 项目规模小、单点维护，GNOME 大版本升级后可能长期不兼容
- 从 macOS 移植的交互模型在 Linux 上存在水土不服
- 用量采集依赖具体 agent 工具的日志格式，上游一改就可能读不到
- 剪贴板类功能天然接触敏感数据，需确认是否有持久化与上传

## 7. 谁该用 / 谁别碰

Ubuntu/GNOME 桌面用户、同时使用多个编码 agent 需要看配额的人、以及喜欢单应用聚合而非装一堆扩展的用户。
