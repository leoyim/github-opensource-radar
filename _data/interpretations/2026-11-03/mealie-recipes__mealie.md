## 1. 它解决什么问题

食谱散落在收藏夹、截图、聊天记录和十几个菜谱网站里，真正要做饭时找不到；找到了还要自己算份量、列采购清单、按超市货架分区分组。商业 App 要么订阅收费，要么把家庭数据锁在云端。Mealie 的定位就是把这套东西搬回自己家的服务器上：一个链接导入配方，结构化存储，再围绕它做周计划与购物清单。

## 2. 为什么是现在

1.38 万星、2,157 天，单日仅 +17——它不是靠爆发上榜的，而是长期稳定被检索到。这类项目出现在日报里的意义在于提供一个参照：本期前后端两类几乎全是 agent、浏览器指纹、加密隧道这些高压话题，而 Mealie 代表另一种需求——把日常生活的一小块数字化并放到自己手里。自建生态（Docker + 反向代理 + 家庭 NAS）在过去两年成熟得很快，这类工具的实际可用性已经跨过了「折腾」的门槛。

## 3. 关键能力

- URL 导入配方：抓取网页并自动解析食材、步骤、份量等结构化字段
- 周计划（Meal Planner）：按天/餐次安排，可复用历史配方
- 购物清单：食材自动按超市分区归组，支持与周计划联动
- Cookbook：按自定义条件把配方分组
- 35+ 语言本地化，含中文界面
- 完整 REST API，便于第三方客户端与自动化脚本接入
- Docker 部署，官方镜像发布在 GitHub Container Registry

## 4. 架构与实现

前后端分离的单体：后端 Python（FastAPI 一系）提供 REST 接口并负责抓取解析，前端 Vue 做响应式界面，数据落 SQLite/Postgres。URL 导入是它的核心链路——抓 HTML、按站点适配器或结构化数据（JSON-LD Recipe）提取字段，失败才退回手工编辑。这个设计让它对主流食谱站点命中率高，但对纯图片或无结构化的页面无能为力，仍需人工补录。

## 5. 上手路径

1. 部署前先定存储后端：SQLite 够家庭用，但要备份方便还是上 Postgres
2. 导入成功率取决于目标站点是否有结构化数据，先拿你常看的几个站点试一轮再决定是否批量迁移
3. 购物清单的分区逻辑按本地超市习惯调，默认分区是西式卖场布局
4. 公开到公网前务必配反向代理与鉴权，它的账号体系面向家庭而非互联网

## 6. 风险与边界

- URL 抓取依赖目标站点结构，站点改版会让导入静默失败或字段错位
- 抓取行为可能触及目标站点的使用条款
- 家庭账号体系较简单，直接暴露公网存在风险
- AGPL-3.0 许可，二次分发或提供托管服务需遵守其条款

## 7. 谁该用 / 谁别碰

有 NAS 或常驻服务器的自建爱好者、需要多人共享食谱的家庭、以及想把饮食数据握在自己手里的用户。
