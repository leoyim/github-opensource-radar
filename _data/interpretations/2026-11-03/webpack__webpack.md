## 1. 它解决什么问题

浏览器不认识模块系统，也不擅长管理成百上千个源文件之间的依赖。打包器要解决的问题始终没变：把散落的模块按依赖图合并、转换（TS/JSX/CSS/图片）、切分、产出可缓存的静态资源。webpack 是把这个模型（entry/output/loader/plugin）定义清楚并推到主流的那一个，至今绝大多数构建配置的心智模型仍源自它。

## 2. 为什么是现在

5,351 天、6.6 万星、单日 +3——它的出现与「热度」无关，只是长期活跃仓库在 Trending 长尾里的正常曝光。放进本期语境反而有意思：前端类另外四席分别是自建食谱应用、零框架项目管理工作台、反检测浏览器和城市数字孪生，全是应用层；webpack 是唯一的基础设施。这也侧面说明当前前端注意力已经从「构建工具怎么选」转移到「用构建工具做出什么」。

## 3. 关键能力

- 基于依赖图的模块打包，支持 ESM / CommonJS / AMD 等混合模块体系
- loader 机制把任意资源（CSS、图片、JSON、CoffeeScript、LESS 等）纳入依赖图
- plugin 机制扩展构建生命周期，覆盖压缩、资源注入、离线缓存等
- 代码分割与按需加载，配合动态 import 实现路由级拆包
- 持久化缓存与增量构建，大项目二次构建显著加速
- Module Federation 支持跨应用运行时模块共享

## 4. 架构与实现

核心是一条「编译 → 生成 chunk → 输出资源」的流水线，围绕 Compiler 与 Compilation 两个对象组织。loader 负责单文件级变换（链式、从右到左），plugin 挂到编译生命周期的钩子上做图级别操作。这套抽象极灵活，代价是配置面积极大，团队往往需要专人维护；这也是 Vite 等后来者用「开发期不打包」绕开其复杂度的直接原因。

## 5. 上手路径

1. 新项目优先考虑 Vite/Rspack 一系，只有在需要深度定制 loader/plugin 或维护存量工程时才选 webpack
2. 先开持久化缓存，再看构建分析（stats / bundle analyzer），优化顺序别搞反
3. loader 顺序是从右到左执行，配置写反是最常见的静默错误来源
4. 升级大版本前锁定 plugin 生态的兼容矩阵，webpack 本身升级通常不是瓶颈

## 6. 风险与边界

- 配置复杂度高，团队知识集中在个别人身上会形成维护瓶颈

- 生态插件质量参差，部分长期无人维护
