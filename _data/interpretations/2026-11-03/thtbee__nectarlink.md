## 1. 它解决什么问题

安卓与 Windows 之间的互联工具长期是碎片化的：Phone Link 管通知与消息，KDE Connect 管剪贴板与部分控制，LocalSend 管文件传输，屏幕镜像又是另一个。三个应用、三套配对、三种连接状态，任何一环掉线都要单独排查。商业方案则要求账号与云端中转，把最私密的通讯内容送上第三方服务器。

## 2. 为什么是现在

29 天、1,759 星、单日 +1,022，冷启动速度仅次于 NOIR。作者在 README 里把动机写得很直白——被三个工具来回切换逼出来的。这类「合并碎片」的项目能快速起量，说明痛点足够普遍；而它选择 local-first + 端到端加密 + 无账号无云，正好对上当下对「数据不经第三方」的偏好。技术上用 Kotlin/Jetpack Compose（Android）+ Rust/Qt（Windows）跨栈实现，也解释了为什么它能同时覆盖通知、通话、文件与投屏这么多面。

## 3. 关键能力

- 通知与消息同步到 Windows
- 来电处理
- 双向剪贴板
- 文件与照片传输
- 屏幕镜像
- 在 Windows 内直接运行手机应用
- Windows 10 (2004+) 与 Windows 11 支持
- local-first、端到端加密、无账号、无云端中转

## 4. 架构与实现

两端原生 + 直连协议：Android 侧 Kotlin + Jetpack Compose，Windows 侧 Rust + Qt，通过局域网直连建立加密通道，按功能划分通道（通知、剪贴板、文件、投屏）。无云端意味着配对与发现必须在本机完成（局域网发现 + 密钥交换），这也决定了它只能在同一网络下工作。多面功能共用一条加密链路是它的结构优势，代价是任一层出问题都会影响整体连接，且跨平台原生实现让维护成本翻倍。

## 5. 上手路径

1. 先确认两端在同一局域网，local-first 意味着跨网段不可用
2. 首次配对时核对密钥指纹，端到端加密的价值取决于你是否验证过对方
3. 按功能逐个启用，先跑通通知与剪贴板，再上投屏与文件传输
4. 许可证标为 NOASSERTION，商用或二次分发前需先确认实际授权条款

## 6. 风险与边界

- 项目仅 29 天，多面功能同时推进，稳定性与兼容性未经验证
- 无云端意味着无法远程使用，且依赖局域网发现机制的可靠性
- 通知与通话同步会接触最敏感的通讯数据，加密实现需自行评估
- 许可证状态不明确（NOASSERTION），法律边界不清
- 单人维护且同时维护 Android 与 Windows 两套原生实现，长期可持续性存疑

## 7. 谁该用 / 谁别碰

安卓 + Windows 双端用户、不愿把通知与文件交给云端中转的人、以及受够在三个互联工具间切换的用户。
