## 1. 它解决什么问题

老游戏的生命周期被引擎锁死：原作引擎闭源、绑定旧版 DirectX、在新系统与新硬件上越来越难跑，社区修 bug 只能靠打补丁。真正彻底的方案是重写引擎——读取玩家自己拥有的游戏数据文件，用现代引擎重新实现规则、渲染与脚本，从而让游戏可以被修复、被移植、被扩展。这类项目在《模拟城市》《运输大亨》《上古卷轴》上都有先例，工程量以年计。

## 2. 为什么是现在

30 天、213 星，无日增基线（快照未覆盖）。放在本期榜单里，它属于「技术理想主义」那一类：不解决任何商业问题，纯粹因为原版值得被保存下来。它出现的时间点也有意思——AI 辅助编程大幅降低了逆向与重写的边际成本，过去需要十几人年的大型引擎重写，现在小团队甚至个人也开始尝试。这条路线能否被 agent 显著加速，未来一年会有答案。

## 3. 关键能力

- 从玩家自有的游戏数据文件中加载资源，不附带任何版权内容
- Rust + Bevy 引擎重写，目标是与原版行为 1:1 一致，包括原版的缺陷
- 分阶段推进：先完成基础游戏（base game）的地基，再向上叠加
- 面向可修复、可移植、可扩展的架构，而非简单复刻观感

## 4. 架构与实现

ECS 架构（Bevy 的原生范式）：把游戏对象拆成组件，系统按查询组合处理，天然适合把原作中耦合的逻辑重新解耦。资源侧需要解析原版的 BSA/ESM 等私有格式，把数据映射到新引擎的组件模型；脚本层则是最难的部分——原作的脚本虚拟机行为必须被精确复现，否则任务链会断。因此这类项目的真实瓶颈从来不是渲染，而是「规则一致性」。

## 5. 上手路径

1. 先确认你合法持有游戏本体（Steam/GOG），项目明确要求使用自己的数据文件
2. 读 README 的完成度声明：基础游戏地基阶段意味着大部分内容还不能玩
3. 跟进时看 commit 密度而非 star 数，引擎重写的进度只能靠提交量衡量
4. GPL-3.0，若想在此基础上做衍生作品需注意条款与原作 EULA 的交叉约束

## 6. 风险与边界

- 工程量巨大，绝大多数同类项目在中期停摆，可持续性是首要风险
- 脚本虚拟机与任务系统的 1:1 复刻极难，玩家实际体验可能长期停留在「能进游戏」
- 原作 EULA 与 GPL-3.0 的组合存在法律灰区，分发形式需谨慎
- 30 天新仓、单人维护，尚不具备社区承接能力
