## 1. 它解决什么问题

想在本机跑一个开源模型，过去要自己处理量化格式、显存分配、GPU 后端、API 封装。Ollama 把这些压成一条命令：拉模型、跑起来、暴露本地 HTTP 接口。它真正的价值不在推理内核（底下是 llama.cpp 一系的工作），而在于把「本地模型」变成了一个稳定的、有统一 API 的本地服务，让上层应用可以当作依赖来用。

## 2. 为什么是现在

18.5 万星、1,225 天，单日 +143——对一个已经极度成熟的项目来说，这个增量说明有新的使用场景在拉动。看 README 的变化就能定位：现在首屏主推的是「把 Ollama 接上你已有的 agent 与应用」，列出的正是 Claude Code、OpenClaw、OpenCode、Codex、Copilot 这一串。也就是说，它的定位正从「本地聊天工具」转向「agent 的本地模型后端」——在云端推理成本敏感的当下，这个转向很有针对性。

## 3. 关键能力

- 一条命令拉起模型并暴露本地 HTTP API（/api/generate、/api/chat 等）
- 内置模型库按名拉取：Kimi、GLM、MiniMax、DeepSeek、gpt-oss、Qwen、Gemma 等
- 自动识别 GPU / Apple Metal / CPU 后端并按显存卸载模型层
- 官方 Docker 镜像 ollama/ollama，便于容器化与内网部署
- 可作为 Claude Code、Codex、Copilot、OpenCode 等 agent 客户端的本地模型后端
- 支持自定义 Modelfile 调整系统提示、参数与模板

## 4. 架构与实现

本地守护进程 + 命令行客户端。服务端管理模型仓库（blob 分片存储）、调度器（并发请求与显存预算）和推理后端（llama.cpp 系列，按平台编译不同加速路径）；客户端只做拉取与请求转发。对外唯一契约是本地 HTTP API，这个设计让上层生态（GUI、插件、agent 客户端）可以完全解耦地生长——也是它能成为「默认本地后端」的根本原因。

## 5. 上手路径

1. 先确认显存与模型量化档位匹配，7B 用 Q4 与用 Q8 的体验差距远大于模型选择本身
2. 把 OLLAMA_HOST 绑定到 127.0.0.1，默认对外监听会把本地模型变成局域网公开服务
3. 接 agent 客户端时先验证工具调用（tool calling）能力，很多小模型能聊天但不能可靠地调工具
4. 生产用途关注模型许可：同一模型名在不同来源的 license 可能不同，商用前逐个核对

## 6. 风险与边界

- 本地推理的质量上限受模型规模约束，7B–14B 级模型在复杂 agent 任务上仍明显弱于云端大模型
- 默认无鉴权，暴露到非回环地址等于开放推理服务，也容易被扫描滥用
- 各家模型许可不一，部分仅限研究或非商用
- 更新频繁，模型格式与 API 偶有破坏性变更，自动化流程需锁版本

## 7. 谁该用 / 谁别碰

在意数据不出本机的开发者、需要离线/内网推理的团队、以及想给编码 agent 配一个零边际成本后端的个人用户。
