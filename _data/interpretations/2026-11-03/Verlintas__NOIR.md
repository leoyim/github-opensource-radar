## 1. 它解决什么问题

手机隐私的实际状况是：你知道某个 App 有定位权限，但不知道它把定位发给了谁；你知道它要了通讯录，但不知道这份数据流向哪个域名。系统权限面板只回答「给了什么」，不回答「流向哪里」。要搞清楚，得自己拉 APK、解包、查 manifest、抓包、对照域名归属——这套流程对普通用户完全不可行。

## 2. 为什么是现在

2 天、1,328 星、单日 +1,087，是本轮冷启动最快的项目，也是全榜增量第五。它的爆发有明确的结构性原因：一是把「抽取端点」这步做得极省——在设备端用 unzip + strings 从 dex 里提取 URL，只回传几 KB，不把整包拉回电脑，这让批量审计变得可行；二是输出不是「风险列表」而是「可执行处置 + 回滚命令」，把结论变成动作；三是中文 README 直接对准了国产 App 生态的隐私焦虑。对比同类工具，它多做了两件关键的事：共享 UID 的权限并集识别，以及 manifest 层的导出组件与明文流量检查。

## 3. 关键能力

- 盘点：列出所有同时具备网络权限与敏感权限的应用，以及各自拿到了什么
- 端点抽取：在设备端用 unzip + strings 从 APK 的 dex 中提取 URL，只回传几 KB
- 分类与打分：按包名与域名识别厂商（小米 / Google / 腾讯 / 高德等）与类别（遥测 / 广告 / 定位 / 输入法等），结合权限与端点计算风险分
- 数据关联：把权限翻译成「能拿到什么数据」（位置、通讯录、短信、通话、麦克风、相机、屏幕、应用列表、设备标识、文件、日历、账号），再与上报域名配对
- 共享 UID 识别：找出 android.uid.system 这类共享用户，列出实际共享同一套权限并集的包
- 清单层检查：解析二进制 AndroidManifest.xml，找出无权限保护的导出组件、明文流量、备份、debuggable、targetSdk 问题
- 处置建议：区分「可安全自动执行 / 需人工确认 / 不建议动」，每条动作附回滚命令
- deep 模式：把单个 APK 拉到本地用 jadx 反编译，检索 Runtime.exec、setApplicationEnabledSetting、DexClassLoader、MediaProjection 等高风险调用

## 4. 架构与实现

桌面端工具 + 设备端轻量执行。采集层通过 adb 读取应用清单与权限，端点抽取刻意留在设备侧完成（unzip + strings 扫 dex），只把 URL 列表回传，避免整包传输与本地存储风险；分析层做厂商/类别映射、权限到数据类型的语义翻译、权限与域名的交叉配对，并解析二进制 AXML 做组件层检查；输出层生成分级处置建议与回滚命令。deep 模式才把 APK 拉回本地交给 jadx。这个「默认轻、按需重」的分层是它能批量跑起来的关键。

## 5. 上手路径

1. 先在备用机上跑，不要拿主力机做第一次扫描——处置动作虽然可回滚，但误判代价高
2. 从「有网络权限 + 敏感权限」的交集开始看，这是信息量最大的一层
3. 对「需人工确认」类处置逐条评估，不要批量执行自动项
4. deep 模式会拉整包并反编译，注意本地磁盘占用与 APK 内容敏感性
5. 2 天新仓，先在无关紧要的设备上验证脚本行为再扩大范围

## 6. 风险与边界

- 风险评分基于厂商/域名映射与权限组合的启发式规则，误报会导致正常应用被误处置
- 批量禁用组件可能破坏系统应用功能，务必逐条确认回滚路径
- 依赖 adb 与开发者模式，审计本身降低了设备的安全配置
- deep 模式拉取 APK 并反编译，本地会留存第三方应用的完整副本
- 2 天、1,328 星的增长速度异常快，代码尚未经社区审查，谨慎在生产设备上使用
