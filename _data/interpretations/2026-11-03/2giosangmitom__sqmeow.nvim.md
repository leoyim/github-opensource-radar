## 1. 它解决什么问题

终端党的日常割裂：写代码在 Neovim，一旦要「看一眼这几行数据」就得切到 DBeaver 或 DataGrip，等 GUI 启动、重连、找到那张表。频繁的小查询被这类上下文切换拖慢。已有的 vim 数据库插件大多只做「执行 SQL 看结果」，缺少对结果集的操作能力——不能就地过滤排序，也不能改单元格。

## 2. 为什么是现在

54 天、161 星，单日增量为 0。它反映的是编辑器生态的一个持续趋势：把「周边工具」一个个搬进编辑器内，用统一键位与上下文减少切换。值得注意的是它的实现选择——数据库操作放在独立的 Rust 进程里，结果集过滤排序交给 Polars，Lua 只负责 UI 与编排。这个分工让它在 Neovim 插件里获得了接近原生工具的性能，而不是被 Lua 单线程拖住。

## 3. 关键能力

- 多类型数据库：SQL、NoSQL 与分析型数据库（MySQL、MariaDB、MongoDB、ClickHouse、DuckDB 等）统一入口
- 交互式结果集：在 Neovim 内浏览、过滤、排序，并可直接编辑单元格
- 查询历史：无需重跑即可回看之前的结果
- 基于 Polars 的本地结果处理，对已取回的行做过滤与排序
- 项目级连接配置：连接与 scratchpad 跟随项目目录存放
- 数据库感知补全，支持 blink.cmp 与 nvim-cmp
- Rust 引擎在独立进程中执行数据库操作，不阻塞编辑器

## 4. 架构与实现

三段式：Lua 插件层负责 UI、键位与缓冲管理；Rust 引擎进程持有数据库连接并使用 Polars 处理结果集；两者通过进程间通信交换结构化数据。这个设计的收益是重活（驱动、结果集计算）不占用 Neovim 主线程，UI 不掉帧；代价是多一个需要编译/分发二进制文件的环节，跨平台安装比纯 Lua 插件麻烦。项目级连接配置则让「这个仓库连哪个库」成为可版本化的约定。

## 5. 上手路径

1. 先确认 Rust 引擎的安装方式（预编译二进制还是本地编译），这是最容易卡住的一步
2. 连接配置放项目目录前先想清楚：含凭据的文件别提交进仓库
3. 在结果集里直接改数据前，确认目标表有主键——无主键的编辑行为通常不可预期
4. 54 天新项目，先在自己的非生产库上试，别接线上
5. 本地过滤只作用于已取回的行，别把它当成服务端 WHERE 用

## 6. 风险与边界

- 项目极新（54 天、161 星），API 与配置格式都可能变
- 编辑器内直接编辑数据缺少事务保护与预览，误操作会立即落库
- Rust 引擎带来分发复杂度，Windows 等平台的二进制可用性需核实
- 连接凭据以项目内文件形式存在，易被误提交
- 本地 Polars 过滤只处理已拉取的行，大表场景下容易误判「数据不全」

## 7. 谁该用 / 谁别碰

长期在 Neovim 里工作、需要频繁做小查询与数据核对的后端/数据工程师。
