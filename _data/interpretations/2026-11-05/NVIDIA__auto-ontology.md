## 1. 它解决什么问题

agent 查数据库「答得快但答错」，根因通常不在 SQL 生成能力，而在业务定义分散：同一个营收指标在五个系统里有五种算法，模型只能靠猜，猜错也照样给出一个漂亮的数字。

## 2. 为什么是现在

仓库 191 天、5,573 星，本期 +2,050，单日增量接近全榜的一半。这种量级一般来自官方发布与生态位空缺的叠加：MCP 让「上下文层」有了标准出口，而此前的语义层产品（dbt、Cube 一类）并没有面向 agent 的统一暴露方式。

## 3. 关键能力

- Discover：从企业元数据生成本体与知识图谱，也可接入已有的语义模型
- Ground：把指标、实体与关系的业务含义对齐，并调和跨系统的不一致定义
- Validate：用受认证的定义与血缘校验生成结果，每个答案附带出处
- Expose：通过 MCP、CLI 与 API 提供给任意 agent 框架
- Learn：把人工修正与使用反馈回灌本体，让上下文随提问变准

## 4. 架构与实现

Python 库，配语义目录、图存储与 Web UI（聊天、分析、数据目录、设置），含 RBAC 鉴权。设计取舍是「确定性优先」：不鼓励模型自由发挥，而是把问题约束到已认证的定义上。代价是它假设企业已有可用的元数据与语义模型，空环境里价值有限。

## 5. 上手路径

1. 先用自带的文本转 SQL 基准（如 BIRD）验证准确率，再评估接入成本
2. 盘点现有语义模型（dbt、Cube、自建）能否导出为它的输入，这是项目成败的前置条件
3. 在 MCP 侧只暴露必要的指标域，避免一次性开放全库带来的权限与误用风险

## 6. 风险与边界

- 单日 +2,050 对 5,573 的总量意味着近四成星标集中在一天，热度与真实采用必须分开看
- 强依赖元数据质量，脏元数据会被放大成系统性错误，且错得更「自信」
- Python 服务加图存储的运维成本不低，中小团队可能维护不起
- 官方项目不等于长期支持承诺，路线图可能随公司产品战略调整

## 7. 谁该用 / 谁别碰

已有数据仓库与语义层积累、要让 agent 承担分析查询的中大型团队；没有元数据治理的个人项目用不上。
