## 1. 它解决什么问题

一个 agent 任务里绝大部分时间花在等外部工具：构建、测试、HTTP、数据库。传统写法要么开线程阻塞，要么写回调——前者内存与调度成本随并发线性上升，后者让业务代码不可读。并发一上来，机器先被等待占满。

## 2. 为什么是现在

仓库 205 天、705 星，本期 +79。2026 年关于 agent 的讨论已经从「能不能做」转向「跑多少、花多少」。当一个人同时开十几个 agent 会话，等待期的资源占用就成了主要成本项，运行时的价值才被看见。

## 3. 关键能力

- agent 并发执行与主动让出：遇到慢工具不阻塞，等事件到达再恢复
- 休眠（hibernation）：空闲期不占内存，作者称树莓派内存可容纳约 7.5 万个 agent
- Reactive Agent Protocol：工具通过网络提供，结果与订阅事件异步投递，不需保持长连接
- 附带的 Infinity Code：在此运行时上构建的编码 agent，构建与测试在后台跑、输出流式回传

## 4. 架构与实现

Rust 实现的状态机 runtime：每个 agent 是可暂停对象，等待时序列化进存储，由事件唤醒。取舍是「显式状态机换可扩展性」——所有跨等待点的状态必须可序列化，写业务逻辑比普通 async 更啰嗦，换来的是空闲期近似零成本。

## 5. 上手路径

1. 先跑 quickstart 并读架构文档，分清「让出」与「休眠」的语义差异，二者触发条件不同
2. 用内存存储起步，再换持久化实现，借此确认你的状态确实可序列化
3. 工具侧优先接 RAP，避免把长任务塞进同步调用，否则并发优势会被抵销

## 6. 风险与边界

- 705 星的小项目，生态与文档成熟度有限，遇到问题可能只能读源码
- 「7.5 万 agent」是内存占用口径，不等于吞吐能力，两者要分开压测
- 状态可序列化的约束会限制可用的库与写法，迁移成本在后期才显现
- 生产环境需要自行补齐可观测性、故障恢复与限流

## 7. 谁该用 / 谁别碰

需要在一台机器上跑大量长时 agent 的团队，以及自建 agent 平台的基础设施工程师。
