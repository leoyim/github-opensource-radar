## 1. 它解决什么问题

代码评审是研发流程里最容易被压缩的环节：人少、PR 多，review 退化成走过场，问题被推到测试甚至线上。

## 2. 为什么是现在

仓库 1,218 天、14,879 星，本期 +280。老项目回升通常与维护模式变化有关：仓库已迁到 The-PR-Agent 组织，README 开头几段专门澄清与 Qodo 商业产品、以及 Qodo 面向开源项目的免费版之间的区别——需要专门澄清，说明品牌混淆已经影响到使用者判断。

## 3. 关键能力

- PR 描述自动生成，按 diff 归纳改动意图与影响面
- 逐行评审与改进建议，可配置严格度
- 针对 PR 的问答式交互，追问某处改动的原因
- 支持多种模型，也可指向本地推理服务
- 可作为 CI 动作或自托管服务运行

## 4. 架构与实现

Python 实现，核心是把 diff 与仓库上下文组装成提示，再按工具（描述、评审、改进、问答）分发到不同模型。取舍是「用上下文窗口换评审质量」：大 PR 必须裁剪或分块，而裁剪策略直接决定漏检率，这一层没有通用最优解。

## 5. 上手路径

1. 先在低风险仓库只开描述生成，跑一周观察误报率，再开逐行评审
2. 配置忽略规则（生成文件、锁文件、vendor 目录），否则噪音会淹没有效意见
3. 取一批历史 PR 做回归，比较开启前后人工评审意见的重合度，用数据决定是否扩大范围

## 6. 风险与边界

- README 自述为社区维护的旧项目，功能演进与官方商业版不同步，长期支持存在不确定性
- 评审误报会快速消耗团队信任，且一旦被关掉很难再推第二次
- 把代码 diff 发往第三方模型涉及代码合规与数据出境，需要事先确认
- 14k 星的老仓库文档与实现可能存在偏差，以代码与近期提交为准
