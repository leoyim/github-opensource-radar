## 1. 它解决什么问题

React 只解决视图层。路由、服务端渲染、数据获取、构建与部署要自己拼，每家拼出来的组合都不一样，跨项目复用几乎为零。

## 2. 为什么是现在

仓库 3,682 天、143,328 星，本期 +124。这类项目的日增不由事件驱动，而由基本盘驱动：任何前端新范式最终都要回答「在 Next.js 里怎么写」。工具链的重要部分已用 Rust 重写，说明竞争点从 API 设计转向了构建性能。

## 3. 关键能力

- App Router 与 React 最新特性（服务端组件、流式渲染）
- 服务端渲染、静态生成与增量再生成并存
- Rust 化的编译器与打包链路，压缩大型项目的构建时间
- 内置图片、字体与缓存优化
- 与 Vercel 平台深度集成，同时支持自托管

## 4. 架构与实现

编译期（Rust/SWC、Turbopack）加运行期（Node 或 Edge runtime）双层结构。取舍是「约定优于配置」：目录即路由、缓存语义内建，代价是运行时行为与部署平台耦合较深，自托管时要自己补齐缓存与增量再生成所需的基础设施。

## 5. 上手路径

1. 用官方 Learn 课程跑通服务端组件与客户端组件的边界，这是新架构最容易误用的地方
2. 先定部署形态（托管或自托管），再决定使用哪些缓存与再生成特性
3. 升级前读迁移指南，跨大版本的路由与缓存语义变更最容易在无感知的情况下改变线上行为

## 6. 风险与边界

- 大版本迁移成本高，生态插件常滞后于框架版本
- 自托管时图片优化与增量再生成的行为与托管平台不同，需要额外实现
- 「默认缓存」历史上多次引发预期外行为，关键路径应显式声明缓存策略
- 框架与商业平台同属一家，选型时需评估供应商依赖程度

## 7. 谁该用 / 谁别碰

需要 SEO、首屏性能与服务端能力的 React 团队。纯内部后台不一定需要它带来的复杂度。
