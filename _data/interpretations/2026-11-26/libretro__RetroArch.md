# libretro/RetroArch · 项目解读

> **一句话**：十六年的参考前端：把模拟器统一成动态库，前端只管音视频、输入与生命周期。

## 1. 它解决什么问题

模拟器各写各的界面与输入处理，跨平台移植重复劳动极多；用户侧则要为每个模拟器学一套操作。缺少一层稳定的 ABI，让核心与前端各自演进。

## 2. 为什么是现在

14,707 星、2,396 fork、2,972 issue、C、GPL-3.0，仓库自 2010 年 5 月持续维护至今。它的做法是把模拟器与游戏引擎编译成动态库（libretro core），由前端统一处理视频输出、音频、输入与生命周期；接口只暴露通用的音视频与输入回调，可移植 C 或 C++ 写的 core 几乎不需改动即可跨平台。

## 3. 关键能力

- libretro ABI：核心以动态库加载，前端与核心解耦
- 四套菜单驱动：XMB、rgui、glui、ozone，适配不同输入方式
- 着色器生态：Cg/HLSL、slang、GLSL 三套着色器仓库配套
- 跨平台覆盖：从 Android 到 macOS、Linux、Windows 与主机改机环境
- 配置与存档统一：由前端集中管理，换核心不丢设置

## 4. 架构与实现

前端进程加载 core 动态库，通过 libretro.h 定义的回调完成帧与音频提交、输入轮询与状态保存；渲染走可插拔的视频驱动，滤镜以着色器链实现。构建产物由 buildbot 分发，官方文档中心另设。

## 5. 上手路径

1. 首次运行先只配一个核心与一个游戏，确认视频驱动与音频同步正常
2. 需要画面增强时再引入 slang 着色器，逐步叠加避免一次全开
3. 把配置与存档目录固定到自定义路径，便于备份与迁移
4. 遇到问题先查文档中心与 issue 检索，2,972 个 issue 中多数场景已有答案

## 6. 风险与边界

- 配置项极多，默认值不一定适合所有硬件，调优成本高
- 2,972 个开放 issue 反映生态规模，也意味着部分边缘平台响应较慢
- GPL-3.0 对商业分发有约束
- 核心质量参差，同一游戏在不同 core 上表现可能差异明显

## 7. 谁该用 / 谁别碰

需要统一管理多平台模拟环境的用户；做前端与输入层、希望复用既有核心生态的开发者。
