> **一句话**：让搜索引擎写一段小程序去核对事实，答不出就明确返回 UNKNOWN。

## 1. 它解决什么问题

常见 RAG 是「检索到文本 → 交给语言模型组织答案」，秒级延迟和每次提问的成本都来自模型，而且模型会把检索噪声补成看似通顺的答案。对代码、日志、指标这类需要精确计数与比对的数据，这种「生成式回答」既慢也不可核验。

## 2. 为什么是现在

本期 18,013 星、1,189 fork、126 个 issue，Apache-2.0、Rust 单二进制。README 用 XERJ Query-1 提出反过来的一条路径：读问题后写一段短程序，由引擎在已存事实上运行，查找与比较都指向带引用片段的具体事实，计数返回程序哈希而非记录；数据不支持就给 UNKNOWN、事实冲突就给 CONFLICT。这是把「可验证性」写进检索接口的设计。

## 3. 关键能力

- 单个 Rust 二进制为代码、文档、日志、JSONL/CSV 与 PDF 建索引，提供 BM25 全文、向量与混合检索，以及无需 grep 的代码搜索
- Query-1 把问题编译成短程序，在已存事实上执行查找、比较、计数，四核 CPU 离线运行、无需构建 embedding 或 GPU
- 查找与比较步骤指向具体事实及其引用片段，计数返回程序哈希；证据不足返回 UNKNOWN，事实冲突返回 CONFLICT
- 提供 Elasticsearch 兼容 API，以及 Corpus Hub 上百份参考记忆语料，可作为 agent memory 与 RAG 后端

## 4. 架构与实现

把「检索」与「作答」拆开：索引层用 Rust 单进程维护 BM25 / 向量 / 混合索引；查询层不直接生成自然语言，而是先由 Query-1 把问题编译为一段可执行的查证程序，程序在事实库上运行并返回带引用的结果或明确的状态码。由于答案来自程序执行而非文本生成，引用片段与程序哈希构成可复核的证据链；对外以 ES 兼容 API 暴露，便于替换现有检索端。

## 5. 上手路径

1. 用一个小型代码库与几份文档建索引，先用 BM25 与混合检索比对命中质量
2. 提一个需要计数或跨来源比较的问题，确认返回的是程序结果而非模型复述
3. 故意制造两份互相矛盾的事实，验证 CONFLICT 是否按预期触发，以及引用片段是否可回溯
4. 通过 ES 兼容 API 把它替换到现有检索链路，压测四核 CPU 下的延迟与并发

## 6. 风险与边界

- Query-1 依赖「问题可编译为查证程序」这一前提，开放域、含糊或需要常识推理的问题容易落到 UNKNOWN
- 项目自述为 rc.101 候选发布，API 与行为仍可能变动，生产接入需锁版本
- UNKNOWN / CONFLICT 的判定质量取决于事实入库时的切分与去重，脏数据会把问题前移到索引阶段
- ES 兼容不等于完整兼容，复杂查询语法与既有插件需要逐项验证

## 7. 谁该用 / 谁别碰

要给 agent 或内部问答系统提供可核验检索、且主要在代码/日志/结构化数据上提问的团队；以开放域创作为主、或已重度依赖生成式摘要的场景收益有限。
