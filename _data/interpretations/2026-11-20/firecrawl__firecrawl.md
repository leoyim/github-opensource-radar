## 1. 它解决什么问题

给 agent 接外部知识时，抓取、解析、结构化、搜索往往各是一套服务：网页里的导航与脚本要清洗，PDF 与动态页面要单独处理，多来源检索还要自己拼。结果是同一份语料在 RAG 链路里被反复转换，格式不一致，维护成本落在接入方。

## 2. 为什么是现在

本期 204,264 星、10,702 fork、843 个 open issue，当日 +825 居 AI 方向首位。README 把三种用法并列写在第一屏——本机单个二进制、托管服务、自托管完整服务端——说明关注点已从「能不能抓下来」转向「同一套接口在不同部署形态下是否一致」。AGPL-3.0 许可下，本地与自托管路径都可自行审阅。

## 3. 关键能力

- 本机以单个二进制运行，把网站转成干净 Markdown，作为 MCP server 直接接入 AI agent，并在 localhost 提供 Firecrawl API
- 托管服务在同样能力之上提供规模化运行、搜索，以及 Alexandria 里 550+ 数据源的知识接入，超出单纯抓取
- 自托管可从 apps/api 部署完整服务端，自带队列、worker 与数据库，数据留在自己的基础设施上
- 仓库同时包含本地实现、自托管服务端与各语言 SDK，三种用法共用同一套接口语义

## 4. 架构与实现

分层在「接口」而不是「部署」上统一：上层是供 agent 调用的抓取/搜索 API 与 MCP 入口，下层是可替换的执行形态——本机二进制、云端托管池、或自建的 queue + worker + database。网页内容在进入上层前被归一为 Markdown 等适合模型消费的结构，因此换部署形态不需要改 agent 侧的调用方式。SDK 与各形态解耦，仓库以 monorepo 方式同时维护。

## 5. 上手路径

1. 先在本机跑单个二进制，抓一个含导航与脚本的页面，确认输出 Markdown 是否已去掉噪声
2. 把它作为 MCP server 挂到日常用的 agent 上，让 agent 自主完成一次「检索 → 抓取 → 引用」的任务
3. 换到托管服务，比对同一 URL 的输出与搜索结果，评估 550+ 数据源是否真能补足单站抓取
4. 若数据不能出内网，按 apps/api 自托管一套，压测队列与 worker 在并发抓取下的表现

## 6. 风险与边界

- AGPL-3.0 对网络服务有较严格的开源义务，做二次分发或 SaaS 封装前需核对许可边界
- 托管形态的搜索与 550+ 数据源属服务侧能力，自托管并不自动获得，口径上要区分清楚
- 843 个 open issue 说明抓取覆盖面广、边缘站点多，特定页面的解析质量需要自行验证
- 把抓取结果直接送进模型会引入外部内容，提示注入与内容可信度需要在 agent 侧设防

## 7. 谁该用 / 谁别碰

正在给 agent 或 RAG 链路接外部网页语料、且希望本机验证与生产部署共用一套接口的开发者；只需要抓少量固定静态页、或已自建成熟清洗管线的团队收益有限。
