## 1. 它解决什么问题

大规模或持续更新的数据做可视化，常见做法是把聚合查询放在服务端、前端只画图：每次改维度都要往返，交互卡顿；而把全量数据拉到前端又受内存与 JS 性能限制。

## 2. 为什么是现在

本期 11,605 星、1,370 fork、29 个 open issue，当日 +36，Apache-2.0、已有 3,304 天历史。README 给出的是一套相当完整的工程答案：C++ 写的流式查询引擎编译为 WebAssembly（含 memory64 构建、列分页到磁盘/内存映射），上层是可拖拽配置的 Custom Element 与 WebGL 图表——本期前端方向里技术密度最高的一项。

## 3. 关键能力

- 交互式数据网格、透视表与图表组件，支持拖拽式查询与布局配置
- WebGL 图表引擎含 15+ 图表类型、瓦片式地理图、虚拟滚动可编辑表格、主题与 React 绑定
- C++ 流式查询引擎编译为 Wasm（含 64 位 memory64 构建，支持浏览器内 >4GB 数据集），亦可跑在 Python、Node.js、Rust 服务端
- 表增量更新、视图实时 tick、跨表响应式 join、基于 ExprTK 的列式表达式语言
- 读写与流式支持 Apache Arrow、CSV、JSON，可把查询下推到已有数据库

## 4. 架构与实现

核心是一个 C++ 列式流式引擎，被编译到 Wasm 在浏览器内执行，或通过原生绑定跑在服务端；因此同一份查询语义可以两端复用，也能委托给外部数据库。引擎侧以增量更新与响应式 join 维持视图实时性，内存超限时通过 OPFS（浏览器）或内存映射文件（原生）把列分页到磁盘。UI 侧是标准 Custom Element，拖放配置直接翻译成引擎查询，React 只是其中一种绑定。

## 5. 上手路径

1. 用一个 CSV 建表，先体验拖拽透视与实时 tick，确认交互延迟
2. 换成 Arrow 流式输入，观察增量更新下视图是否稳定不重绘全量
3. 压一份超过内存的数据集，验证 memory64 / 列分页到磁盘是否按预期工作
4. 把同一查询逻辑放到 Python 或 Node 服务端跑一次，核对两端结果一致

## 6. 风险与边界

- Wasm 引擎与 memory64 构建体积较大，首屏加载与浏览器兼容性需要实测
- C++ 引擎 + ExprTK 表达式 + 多语言绑定，深度定制的学习曲线明显高于普通图表库
- 把查询下推到外部数据库时，能力受目标库支持范围限制，跨源一致性与前述本地路径不同
- 仅 29 个 open issue、成熟项目，新需求响应速度可能不如活跃新库

## 7. 谁该用 / 谁别碰

要在前端做大规模/流式数据交互分析、且不愿把每次交互都送回服务端的团队；只是展示少量静态图表的场景用它偏重。
