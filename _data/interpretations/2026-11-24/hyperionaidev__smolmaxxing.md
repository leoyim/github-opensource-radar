## 1. 它解决什么问题

端侧推理的公开材料大多停留在「能跑」的声明：某模型在某设备上可用，但不给可用内存、量化格式与实测吞吐。真正做产品时需要的恰恰是这些约束——1 GB 可用内存的电视盒子必须靠权重流式装载才装得下大模型，而 flash 读带宽会成为新的瓶颈；这些取舍没有统一参照。

## 2. 为什么是现在

1,123 星、上线 20 天、C 实现、MIT，fork 63、issue 4。它与榜单上多数「端侧推理框架」的区别是：仓库主体是测量结果而非抽象层，五台设备的可用内存从 440 MB 到 3 GB，每台都给出「日常可用」与「最大可跑」两档数字，并标注设备规格与量化格式。

## 3. 关键能力

- 五台设备实测矩阵：小米 TV Box S（4×A55、1.9 GB）、iPad Air 2013（A7、1 GB）、一加 Nord CE 2（天玑 900、7.4 GB）、BuzzTV XR4500（32 位 Android 9、2 GB）、Kindle Paperwhite 3（i.MX6、512 MB）
- 权重从 flash 流式读取，突破 RAM 上限：1 GB 可用内存的电视盒子上跑起 16B 的 Ling-mini-2.0（5.1 tok/s）
- 定制内核与内存管理，日常档在电视盒子上做到 Qwen3.5-2B 的 7.7 tok/s
- 无需 root、无需越狱的设备占多数，越狱设备单独标注
- 每项数字附设备规格与量化格式，可直接按同款硬件复现

## 4. 架构与实现

以 llama.cpp 路线为基底做定制内核，模型权重常驻 flash、按层流式装载，配合 KV cache 压缩与显存/内存上限控制；仓库主体是构建脚本与逐设备的结果页，C 代码集中在推理与内存管理路径。

## 5. 上手路径

1. 先挑一台闲置安卓设备（无需 root），按 README 的交叉编译脚本产出二进制
2. 跑日常档（Qwen3.5-2B 级）验证能否达到 7 tok/s 量级，作为链路是否通的判据
3. 再试最大档，观察首 token 延迟与稳态吞吐的差距，判断 flash 带宽是否成为瓶颈
4. 记录 tok/s 的同时记温度与电量曲线，否则不同设备之间不可比

## 6. 风险与边界

- 数字强依赖具体闪存的随机读性能与散热条件，同型号不同批次可能差异明显
- 16B 级模型靠流式装载，首 token 延迟远高于稳态吞吐，交互式场景体验受限
- 越狱/越权路径只在个别设备验证，通用性未证，升级系统后可能失效
- 上线 20 天的新仓，脚本与设备清单仍在快速变动，复现文档需对应到具体 commit

## 7. 谁该用 / 谁别碰

手上有闲置电视盒子、旧平板与开发板，想验证端侧推理实际上限的工程师；不适合需要稳定产品级 SDK 与售后支持的团队。
