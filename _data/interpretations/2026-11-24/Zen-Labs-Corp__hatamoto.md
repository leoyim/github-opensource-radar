## 1. 它解决什么问题

主流 CMS 有两个结构性负担：一是技术栈绑定，PHP 或 Node 的插件生态决定了运维方式；二是功能碎片化，SEO、缓存、表单、重定向各是一个插件，插件数量增长直接推高运维面与升级风险。自托管团队往往在被插件拖垮之后才开始考虑替换。

## 2. 为什么是现在

488 星、上线 28 天、Go、Apache-2.0。它的做法是把上述能力全部内建到单体二进制里——页面构建器、SEO、缓存、表单、重定向、AI 分析、自动内链、实体与 schema、媒体优化，再加一个供 agent 操作的 MCP 接口；插件体系改为签名的 WebAssembly，在沙箱中运行并支持自动更新。

## 3. 关键能力

- 可视化页面构建器，桌面/平板/手机三档预览同时可见
- 内建 SEO、缓存、表单、重定向，无需插件
- 实体与 schema 建模，列表页与结构化数据由同一模型驱动
- 媒体优化与自动内链
- MCP 接口，供 agent 读取与操作内容
- 签名的 WebAssembly 插件 + 自动更新，插件在沙箱内运行

## 4. 架构与实现

Go 单体二进制 + Postgres；插件以 WASM 沙箱运行并要求签名校验，站点数据以实体模型组织；启动方式为 docker compose（连带 Postgres）或二进制指向自有数据库，管理端位于私有地址。

## 5. 上手路径

1. docker compose up 起一套环境，从日志里的 setup 地址创建账号与站点
2. 先建一个实体与对应列表页，核对生成的 schema 是否符合预期
3. 用 MCP 客户端列一次工具清单，确认 agent 能读、写操作有明确边界
4. 装一个 WASM 插件并观察签名校验失败时的行为，确认沙箱策略生效

## 6. 风险与边界

- README 明示安装统计默认开启，自托管场景应第一时间关闭并核对外联地址
- 上线 28 天的新仓，插件生态与升级路径都还很薄，长期维护能力待验证
- WASM 插件签名的安全性依赖密钥管理，密钥泄露等于插件信任链失效
- AI 分析若接外部模型，内容会离开自有环境，需先确认数据处理条款

## 7. 谁该用 / 谁别碰

想要一套不背插件债、能用 Go 运维、且希望 agent 通过 MCP 操作内容的团队；适合内容型站点而非复杂业务系统。
