## 1. 它解决什么问题

自动驾驶的感知与规划研究需要可控、可重复、带真实城市资产与传感器模型的环境。实车采集成本高且不可复现，自建仿真又要同时解决渲染、物理、传感器噪声与场景编辑，几乎不可能由单个团队从零承担。

## 2. 为什么是现在

14,692 星、约 9 年、C++、MIT，日增 16。老牌基础设施仍在日榜，说明仿真依旧是这个领域的公共底座；而它从设计之初就为自动驾驶的训练与验证而生，除代码与协议外还提供了专门制作的开放数字资产（城市布局、建筑、车辆），可自由使用。

## 3. 关键能力

- 开放数字资产：城市布局、建筑与车辆模型，可按场景自由组合
- 传感器套件灵活配置，包括相机、激光雷达、毫米波雷达与 IMU 等
- 环境条件可调，天气与光照变化可参数化，用于鲁棒性验证
- 服务端-客户端架构，客户端提供 Python 与 C++ API，便于与研究代码集成
- 与 ROS、SUMO 等生态的桥接组件，可接入既有工具链

## 4. 架构与实现

C++ 仿真服务端（基于 Unreal 渲染）负责世界模拟与传感器数据生成，客户端通过 RPC 通信；场景与资产以独立包分发，地图与车辆可替换。README 给出的运行门槛是 i7/i9 或 Ryzen 7/9、32 GB 内存、RTX 3070 起与 16 GB 显存、Ubuntu 22.04/24.04 或 Windows 11。

## 5. 上手路径

1. 先按 README 核对自己的显卡与显存，低于门槛时不要尝试渲染完整场景
2. 用预编译包启动服务端，再跑一个 Python 示例确认 RPC 端口连通
3. 先跑内置场景，确认基准行为后再改天气、光照与传感器配置
4. 多人协作时把资产包与场景配置分开管理，避免地图版本互相覆盖

## 6. 风险与边界

- 渲染与物理开销大，笔记本与核显基本不可用，硬件门槛会直接筛掉一部分团队
- 版本间 API 有过破坏性变更，网上教程与代码容易和当前版本错配
- 仿真到实车的域差异仍是核心未解问题，仿真里的指标不能等价于实车表现
- 9,000+ fork 意味着大量分支已偏离主线，碰到问题要确认是否为主干行为

## 7. 谁该用 / 谁别碰

高校与研究机构的自动驾驶感知/规划团队，以及需要合成数据做闭环验证的工程团队；不适合只想跑一个轻量 demo 的个人项目。
