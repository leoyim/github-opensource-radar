## 1. 它解决什么问题

语音能力通常分散在多个 Python 框架里，训练与推理一体，部署到端侧几乎要重写；云端 API 又要求联网，无法处理敏感音频，也难在弱网与离线设备上使用。端侧团队真正需要的是「一套二进制、多种任务、多平台」。

## 2. 为什么是现在

16,176 星、约 4 年、C++、Apache-2.0，日增 70。它基于新一代 Kaldi + onnxruntime，把语音识别、合成、声源分离、说话人识别/分离/验证、语种识别、音频打标、VAD、关键词唤醒、标点恢复、语音增强与强制对齐收敛到同一套 C++ 实现，平台覆盖到 RISC-V 与多类 NPU，并提供 12 种语言绑定与 WebAssembly。

## 3. 关键能力

- 语音识别与语音合成，支持流式与非流式两条路径
- 声源分离、语音增强、VAD 与关键词唤醒
- 说话人识别、说话人分离与说话人验证
- 语种识别、音频打标、标点恢复与强制对齐
- 平台覆盖 Android、iOS、Windows、macOS、Linux、HarmonyOS，含 RISC-V 与 RK/Axera/Ascend NPU
- 12 种语言绑定（C++/C/Python/JS/Java/C#/Kotlin/Swift/Go/Dart/Rust/Pascal）+ WebAssembly，另有 Flutter 与 Tauri 预编译示例

## 4. 架构与实现

C++ 核心 + onnxruntime 推理后端，模型以 ONNX 格式独立分发；各语言绑定为薄封装，移动端提供预编译 AAR 与 Framework，服务端支持 websocket 客户端/服务端两种形态。

## 5. 上手路径

1. 先用预编译 CLI 跑一次离线识别，确认模型路径与采样率匹配
2. 再接 Flutter 或 Tauri 示例，验证端上集成与权限（麦克风）
3. 按任务选模型（流式 vs 非流式）并压一次首字延迟与实时率
4. 最后才考虑替换为自训练模型，注意导出 ONNX 的算子兼容性

## 6. 风险与边界

- 模型与二进制分开分发，版本错配是最常见故障，需锁定配套版本
- 跨平台组合极多，官方示例覆盖不到的组合需自行编译，工具链成本高
- 端侧性能强依赖 CPU 指令集与量化选择，同一模型在不同芯片上差异可达数倍
- 功能面广导致文档分散在多个子项目页，检索成本不低

## 7. 谁该用 / 谁别碰

需要在端侧或内网做离线语音能力的硬件与客户端团队；也适合需要多语言绑定、不想被单一生态绑定的服务端项目。
