## 1. 它解决什么问题

古典文集有纸本与影印本，但机器可读的结构化版本稀缺；想做一个诗词类应用，光是「把诗从网页或 PDF 里抠出来、清洗成字段」就要耗费数周，且各家清洗口径不一，拼出来的数据集无法互相校对。

## 2. 为什么是现在

仓库自 2016 年持续维护至今（3,722 天、5.4 万星、1.09 万 fork），本期日增 53，说明它仍在被新项目引用。它的价值不在代码量，而在「数据即产品」：目录按文集组织，字段结构稳定，配套采集过程记录与贡献规范，使下游可以按版本锁定语料。

## 3. 关键能力

- 唐诗、宋诗、宋词三大主集，另含五代花间集、南唐二主词、论语、诗经、幽梦影、四书五经、蒙学、纳兰性德、御定全唐詩等子集
- 统一 JSON 结构分发，按作者、标题、段落组织，便于直接建索引或导入数据库
- 附高频词、词牌名、作者作品榜等分析示例，可作为语料处理的教学样本
- 提供贡献规范：诗句纠错需标明出处，争议数据由社区投票决定是否收录
- 配套案例覆盖 Web 站、Android 离线应用、Char-RNN 生成、诗词周历等多种下游形态

## 4. 架构与实现

以 JSON 文件为存储形态、按文集分目录，仓库语言标注为 JavaScript（主要用于校验与工具脚本），MIT 许可。设计取舍是「不提供数据库、不提供 API」，只保证数据文件的结构与可读性——这降低了使用门槛，也把索引与查询性能的责任交给下游。README 明确记录采集来源为互联网且过程曾中断超过一周，属于对数据来源的诚实披露。

## 5. 上手路径

1. 先按文集目录浏览 JSON 结构，确认字段是否满足自己的数据模型
2. 把所需子集导入 SQLite/PostgreSQL 或建全文索引，不要直接在原始目录上做查询
3. 用贡献规范核对异文与错字，标注出处后再提 PR
4. 在应用中固定引用某个提交哈希，避免上游更新导致数据漂移
5. 做 NLP 任务时先做繁简、异体字与标点的归一化，语料本身保留原始形态

## 6. 风险与边界
