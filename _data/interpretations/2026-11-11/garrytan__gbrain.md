## 1. 它解决什么问题

每个 agent 各记一份上下文，换个客户端记忆就断；记忆里的事实没有出处，错了追不回来，删也删不干净。团队想共用一份「公司大脑」，又不想把全部知识塞进某家厂商的托管服务里。

## 2. 为什么是现在

作者是 YC 总裁，公开了自己在生产环境里的规模：15.5 万页、2.4 万人、5,340 家公司、66 个 cron 任务在自动跑。这类「先自用、再开源」的项目通常不缺真实负载打磨；219 天累计 806 个 issue，也说明它被当作长期基础设施在维护，而不是一次性发布。

## 3. 关键能力

- 显式事实存储，每条带来源，支持更正与撤回（不是只追加的日志）
- 从零依赖的关键词检索起步，按需开启语义检索、综合成文与后台富化
- 跨 agent 共享同一份记忆：以 MCP 为对外协议，Claude Code、Codex、Cursor、Grok Bot 等均可接入
- 一条命令把本地 brain 发布到 Tailscale 内网（gbrain mcp expose，--funnel 可对云端 agent 开放）
- 类型化知识图谱：人物、公司、交易、想法之间的引用在写入时自动抽取
- 技能与知识同仓存放，agent 可加入经授权的目录，仅批准的编辑者能发布

## 4. 架构与实现

TypeScript，MIT 许可，本地优先、托管（gbrain.io）可选。对外以 MCP 暴露能力，授权模型区分 source 与 operation 授权加可见性过滤。README 明确写了一句自我限定：本地文件与共享数据库凭据属于不同信任边界，仅靠 source 并不能隔离这些调用者——这种把「做不到什么」写在明处的表述，比笼统的「企业级安全」可信。

## 5. 上手路径

1. 按推荐路径把它加到现有 agent：保留 agent 自己的身份，记忆存在其运行环境内，不新建个人 agent
2. 需要跨设备访问时执行 gbrain mcp expose，把 brain 发布到自己的 tailnet
3. 先在 Claude Code / Codex 里接 MCP，存 20 条带出处的事实，手动试一次更正与撤回
4. 确认检索质量后再开启语义检索与综合层，避免一上来就被后台富化的成本淹没

## 6. 风险与边界

- 自托管与托管版的能力边界不同，README 用大量篇幅区分两者，误配的概率不低
- 806 个 open issue 说明边界情况多，处于快速演进期，接口与行为可能变动
- 共享 brain 的授权模型需要读懂架构文档才敢多人使用，仅凭 source 过滤不足以防越权
- 作者身份带来额外关注度，星标增长未必等同于成熟度，建议先小规模验证再依赖

## 7. 谁该用 / 谁别碰

同时使用多个编码或对话 agent、希望记忆不绑死在单一客户端的人；需要「事实可溯源、可撤回」的知识工作团队与小型公司。
