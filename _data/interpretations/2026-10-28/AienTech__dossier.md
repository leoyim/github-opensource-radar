> **一句话**：自托管的求职流水线：一份履历，对每个岗位生成一份只讲真话的简历。

## 1. 它解决什么问题

求职的实际工作量不在投递，在于为每个岗位改写简历与求职信：同一段经历要按不同 JD 换措辞、换重点，写多了就开始注水，最后连自己都记不清投过哪家。通用 AI 写作工具的问题是它不认识你的完整履历，容易编造。dossier 的前提是「先把你的职业历史存成结构化 profile」，之后所有生成都只允许引用 profile 里的事实。

## 2. 为什么是现在

今日 +999 星（快照口径，24 天新库）。它踩中的是「AI 生成内容不可信」这个具体痛点：不是让模型更会写，而是给它划定事实边界——只用 profile 里的事实。同时它把模型选择权交出去（Ollama / LM Studio 本地跑，或 OpenAI 兼容、Anthropic、Mistral 云端），并明确写出「隐私上什么数据去哪」，这种透明度在同类里少见。

## 3. 关键能力

- 单一 profile 驱动：职业历史集中维护，简历由它派生而非各自维护
- JD 匹配分析：读岗位描述，给出你与该岗位的匹配点与缺口
- 定制生成：只用 profile 事实产出简历与求职信，可在对话里继续改
- 导出 PDF，并按「草稿 → 投递 → 面试 → offer」跟踪每份申请
- 模型自选：本地 Ollama / LM Studio，或任一家 OpenAI 兼容 / Anthropic / Mistral
- 单人小服务器定位：一个密码、数据在自己的 PostgreSQL

## 4. 架构与实现

Next.js 单体 + PostgreSQL，LLM 通过可配置 provider 接入（本地或托管）。关键设计是把「事实来源」与「生成层」分离：profile 是唯一可信数据源，生成环节被约束为只能引用它，这也让隐私边界变得可描述——发出去的只是「模型为写这份文档所需要的内容」。

## 5. 上手路径

1. 用 Docker 起一份，先把自己的履历完整录进 profile——这一步的质量决定后面所有产出
2. 先用本地模型（Ollama）跑一遍，对比托管模型在「不编造」这件事上的差异
3. 拿一个真实 JD 走完整流程：匹配分析 → 生成 → PDF → 投递跟踪，确认闭环可用再批量用

## 6. 风险与边界

- 生成质量强依赖 profile 的完整度与结构化程度，录得不细就退化成通用套话
- 本地小模型在长文本改写上容易丢失细节，需逐份核对
- 自托管意味着备份、升级、安全都归你自己；数据库里是完整履历，属高敏感数据

## 7. 谁该用 / 谁别碰

在意履历数据不外流、同时海投多个岗位的个人；团队或猎头场景不匹配它的单人定位。
