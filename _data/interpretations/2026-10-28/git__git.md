## 1. 它解决什么问题

这件事已经不需要解释：几乎所有的代码协作都建立在 Git 之上。它解决的问题是分布式的版本管理——每个副本都是完整仓库，可以在离线状态下提交、分支、合并，再与他人同步。二十年来这个模型没有被取代。

## 2. 为什么是现在

今日 +31 星（6,670 天）。它上榜的原因通常不是 Git 有新特性，而是某个版本发布或某个广泛影响的操作被讨论。真正值得记录的是它的协作方式：这是发布用镜像，PR 不会直接被合并，补丁需经 GitGitGadget 转成邮件列表形式，并按 Documentation/SubmittingPatches 的流程走。这种「拒绝 GitHub 工作流」的坚持，本身就是一份关于项目治理的教材。

## 3. 关键能力

- 分布式版本控制：完整历史在本地，离线可用
- 极强的分支与合并模型，支持复杂工作流
- 底层管道命令可编程，能构建上层工具
- 跨平台（Linux/macOS/Windows）与多传输协议支持
- GNU GPL v2 许可（部分组件为兼容许可）

## 4. 架构与实现

内容寻址的对象数据库（blob/tree/commit/tag）+ 可变的引用（refs）+ 索引（index）三层结构。所有操作都是对这套对象图的读写，因此历史不可变、分支极轻。理解这一层之后，rebase、reset、reflog 的行为都不再需要背。

## 5. 上手路径

1. 要向 Git 本体提补丁：先读 Documentation/SubmittingPatches，用 GitGitGadget 提交，不要开 PR 等合并
2. 日常使用不必读源码，但建议理解对象模型——它能把 90% 的「危险操作」变成可预测操作
3. 关注安全公告渠道，Git 的漏洞影响面覆盖几乎所有开发流程

## 6. 风险与边界

- 核心维护者集中，治理结构变化会影响长期走向
- 历史遗留的命令语义不一致（如 checkout 身兼数职），新命令（switch/restore）仍在推广期
