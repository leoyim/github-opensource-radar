## 1. 它解决什么问题

终端里的编码 Agent 大多背着一整套运行时：Node、Python 环境、依赖树，部署到新机器先解决环境问题。FuXi 选择 Go，编译成单个静态二进制，无运行时依赖，拷过去就能跑。另一处差异是模型调度：不是在设置里选一个 provider 就固定，而是按任务做成本感知路由，并在失败时自动切换到备用 provider。

## 2. 为什么是现在

85 天、3,204 星，按速度口径入选。最抓眼球的说法是「约 200 万行代码全部由 FuXi 自己写成」——这个数字无法从 README 验证，应视为项目方的自述而非事实。剔除这一点，它的工程取向是清楚的：终端优先、provider 无关、自带 key、MCP client、自更新。这套组合瞄准的是「不想被某个 IDE 或某家模型绑定」的人。

## 3. 关键能力

- 终端 TUI 交互：读代码、改文件、跑命令、驱动工具
- 单静态二进制，无运行时依赖，跨机器可直接拷贝
- 成本感知路由：按任务复杂度选择不同 provider 与模型档位
- 自动 failover：主 provider 失败时切换备用，不中断会话
- 自带 MCP client，可接外部工具服务
- 自更新机制

## 4. 架构与实现

Go 单体 + TUI 层 + 工具执行层 + provider 抽象层。provider 抽象是它的核心差异点：把「模型调用」变成可路由的资源，于是成本与可靠性策略可以独立于业务逻辑调整。MCP client 的接入说明它把外部能力当作插件而非内建。

## 5. 上手路径

1. 先下载对应平台二进制，用自己的 API key 跑通一次「读文件 → 改一行 → 跑测试」的最小闭环
2. 配置两个 provider（一主一备）验证 failover 是否如描述那样无感切换
3. 接 MCP 服务时逐个加，不要一次挂满——工具过多会显著降低 Agent 的选择准确率

## 6. 风险与边界

- 85 天的新项目，工具调用的边界情况（大文件、二进制、权限）覆盖度未知

## 7. 谁该用 / 谁别碰

偏好终端工作流、需要跨多个模型 provider 做成本与可靠性调度的开发者。
