## 1. 它解决什么问题

很多编码助手绑定单一厂商的模型与 IDE 界面，工作流难以复用到脚本、CI 或非编码任务；工具扩展也常依赖私有插件格式，团队想统一工具链与执行边界缺少可审阅的载体。

## 2. 为什么是现在

56,620 星、6,591 fork 与 813 天历史说明它已过早期试验阶段，本期仍 +72。README 把桌面应用、CLI、API 三种入口并列，并标注 ACP 与 MCP 协议，正对应本期多条项目都在为 agent 定义「可互操作协议」而非提升单个模型能力的共同取向。

## 3. 关键能力

- 桌面应用、CLI 与 API 三种形态，覆盖交互使用、脚本批处理与服务化集成
- 可接任意 LLM，不绑定特定模型供应商，便于本地模型或私有网关接入
- 不止给代码建议，能实际执行安装、编辑、运行与测试等完整动作
- 通过 MCP 与 ACP 协议扩展外部工具，工具面与运行时解耦
- Rust 实现、Apache-2.0 许可，源码与构建链可自行审阅

## 4. 架构与实现

Rust 实现的 agent 运行时，向下通过可替换的模型适配层对接 LLM，向侧通过 MCP/ACP 接入外部工具，向上分别暴露桌面 UI、CLI 与 API 三种入口；动作执行落在本地环境，因此权限边界由运行时与配置共同决定。

## 5. 上手路径

1. 从 Get started 安装桌面端或 CLI，先用一个只读任务观察它调用了哪些工具、改动了哪些文件
2. 在配置里切换一次模型供应商（可先接本地模型），验证既有工作流是否仍可运行
3. 把一个 MCP 工具接进来，确认工具声明与 agent 的实际调用是否一致
4. 需要自动化时改用 CLI 或 API，并在隔离目录里验证退出码与副作用

## 6. 风险与边界

- agent 具备执行与写文件能力，必须在沙箱或专用工作目录中先跑，避免直接指向生产仓库
- 换模型会改变工具调用稳定性与长任务表现，工作流需按模型分别验证
- 协议扩展带来便利的同时也扩大了可触达面，第三方 MCP 工具应视同外部代码审阅
- README 主体偏入门与社区链接，架构与权限模型的细节需从文档站与源码补齐

## 7. 谁该用 / 谁别碰

适合想把 agent 能力纳入自有工具链、或需要本地/私有模型接入的工程团队；不适合只想要一个开箱即用 IDE 补全、且不打算管理工具权限的个人用户。
