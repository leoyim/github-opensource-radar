## 1. 它解决什么问题

传统静态分析要么依赖复杂的 AST 遍历与 DSL，规则难写难维护，要么需要接入重型平台；安全团队想快速表达「这类写法不允许」时，成本往往高于问题本身。

## 2. 为什么是现在

17,683 星、1,000 个开放 issue、2,529 天历史，本期 +37，属于稳定型基础设施而非热度 spike。README 明写可在 IDE、pre-commit、CI/CD 三处运行，并给出 CLI 与 Appsec Platform 两条起步路径，覆盖面比单一扫描器更完整。

## 3. 关键能力

- 规则形如源代码，支持语义级匹配（如把常量传播后的表达式也算命中），无需手写 AST 或正则
- 覆盖 30+ 语言，可运行在 IDE、pre-commit 钩子与 CI/CD 流水线中
- 用于发现 bug 变体、落实安全护栏与团队编码规范
- 提供 Semgrep Rules 规则库、Extensions 编辑器扩展、Metrics 指标与文档体系
- README 列出 pipx、uv tool 等安装方式与 Upgrading 说明，便于纳入现有工具链

## 4. 架构与实现

以模式匹配引擎解析源码并按语义查找变体，规则以声明式 YAML/代码式模式描述，扫描器作为 CLI 本地运行或对接平台；结果可在 IDE 插件、pre-commit 与 CI 三种不同时机输出，规则库与扩展围绕引擎形成生态。

## 5. 上手路径

1. 按 Getting started 的 CLI 路径安装，对一个小仓库跑默认规则集，先看误报率
2. 写一条团队自身的编码规范规则，验证语义匹配能否覆盖写法变体
3. 把扫描挂到 pre-commit，确认增量提交时的耗时可接受
4. 再接入 CI，按 Metrics 与文档调整规则级别与豁免清单

## 6. 风险与边界

- README 明确说明社区版在安全场景下只能分析单函数/单文件边界，会漏掉不少跨文件的真实问题
- 规则写得宽会带来误报，长期需要维护豁免清单，否则容易被团队整体关闭
- 多语言支持深度不一致，冷门语言的规则成熟度需单独验证
- CLI 与平台能力存在差异，评估时应固定使用同一条路径做对比

## 7. 谁该用 / 谁别碰

适合需要把安全与编码规范落地到提交流程的工程团队、平台工程与安全工程师；不适合期待开箱即用完成完整跨文件污点分析的场景。
