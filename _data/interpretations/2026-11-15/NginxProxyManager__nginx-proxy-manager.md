## 1. 它解决什么问题

自建服务要暴露到公网，通常需要手写 Nginx 配置、处理 Let's Encrypt 续期与访问名单；对家庭网络或小型团队而言，这些细节的学习成本远高于「加一条转发规则」本身。

## 2. 为什么是现在

34,715 星、3,973 fork、3,251 天历史，本期 +14，属于长期稳定型基础设施。README 明写项目目标是「简单到猴子都能用」，且高级选项保持可选——在自托管持续升温的背景下，这种把复杂度主动收进默认值的取向仍有稳定需求。

## 3. 关键能力

- 预构建 Docker 镜像，无需掌握 Nginx 或 Let's Encrypt 细节即可配置反向代理
- 自动申请与管理免费 SSL 证书，支持转发域名、重定向等常见场景
- 基于 Tabler 的管理界面，提供访问列表等可选高级能力
- README 给出 Project Goal、Features、Quick Setup 与 Getting Support 路径
- MIT 许可，部署形态单一，便于纳入现有容器编排

## 4. 架构与实现

容器内部把 Nginx 配置生成、证书申请与续期、以及一个 Web 管理界面组合在一起；用户在界面上的操作被翻译成底层配置并重载服务，因此常规使用不需要直接编辑 conf 文件，但深度定制仍需理解生成结果。

## 5. 上手路径

1. 按 Quick Setup 起容器，先只暴露管理界面并修改默认凭据
2. 添加一条到本地服务的转发规则，确认 HTTP 与 HTTPS 路径都通
3. 申请一张证书并检查自动续期是否生效
4. 需要更细的控制时，查看生成的 Nginx 配置，确认它不会与既有手写配置冲突

## 6. 风险与边界

- 管理界面一旦暴露到公网即成为高价值入口，必须改默认凭据并限制访问来源
- 抽象层在简化常规场景的同时也隐藏了配置细节，复杂路由或特殊 header 需求可能受限
- 证书申请依赖外网与 ACME 可达性，纯内网环境需另配方案
- 把多个服务统一收在一个反向代理下，也意味着它成为单点故障

## 7. 谁该用 / 谁别碰

适合家庭实验室、小型自托管服务与不想维护手写 Nginx 配置的团队；不适合需要细粒度定制、或已有成熟网关体系的规模化生产环境。
