## 1. 它解决什么问题

常见笔记应用建立在 WebView / Electron 之上，长文档输入与滚动容易受 DOM 与 JS 主线程影响；同时云端同步让「笔记存在哪、能不能离线打开」变成需要额外确认的问题。

## 2. 为什么是现在

本期移动/跨端方向里最年轻的项目之一，14 天、1,865 星、164 fork，尚无前一日基线，属于典型的新仓首发。README 用一组具体数据（百万字符文档下输入、删除、滚动 P95 < 6ms/帧）而不是形容词说明性能，并明确写出无 WebView、无 Electron，是本期「原生化」取向最直接的一例。

## 3. 关键能力

- Rust + GPUI 原生绘制界面，不使用 WebView 或 Electron
- 本地优先，笔记作为文件保存在本机，采用 Feishu（Lark）DocxXML 格式
- 覆盖 macOS、Windows、Linux 三平台
- 提供富文本编辑与笔记管理能力，README 单列 Performance 章节给出量化数据
- MIT 许可，附 Download、Features、Contributors、Recent updates 等章节

## 4. 架构与实现

界面层由 GPUI 直接在 GPU 上绘制，文本编辑与文件读写留在 Rust 侧，因此渲染路径不经过浏览器排版引擎；存储层把笔记写成可移植的 DocxXML 文件，数据留在本地，不引入服务端依赖。

## 5. 上手路径

1. 从 Download 安装对应平台版本，先建几篇短文验证基本的编辑与保存
2. 导入或粘贴一篇长文档，观察滚动与输入的实际手感，对照 README 的性能口径
3. 检查笔记文件落盘位置与格式，确认它符合自己对「可迁移」的要求
4. 阅读 Recent updates 与 License，评估这个 14 天项目的更新节奏是否适合作为主力笔记工具

## 6. 风险与边界

- 项目仅 14 天，功能完整度、数据迁移与长期维护都还在早期阶段，不建议立刻承载唯一笔记副本
- 自述性能数据来自作者环境，不同 GPU 与驱动上的表现需自行复测
- 采用 DocxXML 作为存储格式意味着与其它 Markdown 笔记生态的互通需要额外转换
- 原生绘制跨平台应用在各系统的字体渲染与输入法行为上可能存在差异

## 7. 谁该用 / 谁别碰

适合关注本地优先与输入延迟、愿意尝鲜并自行备份的重度笔记用户；不适合需要成熟同步生态与长期数据保障的团队场景。
